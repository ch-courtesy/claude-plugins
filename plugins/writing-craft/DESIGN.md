# writing-craft 설계 (W-429, 2026-11-16)

> 이 문서는 구현 전 설계다. 구현(W-430)이 끝나면 README로 줄이고 이 파일은 지운다.

## 1. 왜 만드나

- 오너 요구(2026-11-15): "소설, 수필, 설명문, 논설문 등 블로그에서도 쓸 수 있는 글쓰기 방법론과, 이렇게 완성된 스킬을 통해서 소설 등 글을 작성할꺼야."
- 합격선(HQ D-062): 현업 10년차 이상 편집자·작가가 자기 이름으로 낼 수 있는 초안과 진단.
- blog-craft는 **블로그 글 한 종류의 공정**(주제 관문 → 초안 → 첨부 시험 → 교차 리뷰 → 채점)이다. writing-craft는 **장르별 작법의 기반**이다. 블로그 밖(소설·수필·칼럼)에서도 쓰고, blog-craft `post-draft`가 장르 규칙을 빌려 쓴다.

두 조사의 공통 경고를 스킬 규칙으로 그대로 가져온다.

1. 구조 공식·분량 비율·합격 점수는 **검증된 표준이 아니다**. 스킬은 하나를 강제하지 않고 고르게 한다.
2. "AI 초안의 실패 신호"는 편집 가설이다. AI 작성 여부 판정에 쓰지 않는다.
3. 자료가 없으면 유창한 문장으로 메우지 않는다. 작업 표시(`[경험 확인 필요]` 등)를 남긴다.
4. 플랫폼 정책은 원문·날짜·적용 범위(일반 연재/공모전/표지/본문)를 확인한 것만 쓴다.

```
    genre-rubric/                장르별 0·1·2점 채점(외부 모델)

    story-ledger/                긴 글 장부(설정·인물·지식·시간선·회차·장면) 관리와 기계 점검
      SKILL.md
      references/schema.md
      scripts/ledger_check.py
```

### 왜 스킬 4개인가

- **장르마다 초안 스킬을 따로 두지 않는다.** 수필·설명문·논설문·리뷰는 입력 명세와 작성 절차(조사 nonfiction 8.1·8.2)가 같고 뼈대·규칙만 다르다. 스킬 하나 + 장르별 reference가 설명 토큰을 덜 쓰고, 혼합 글("일화로 시작해 제도 변경을 주장")을 한 곳에서 판정할 수 있다. 소설은 장면 카드·장부 루프가 있어 절차 자체가 달라 따로 둔다.
- **채점은 하나로 묶는다.** 절차(외부 모델이 항목마다 점수·근거 문장·수정 행동, 적용 불가는 분모 제외, 총점으로 상쇄 못 하는 결함 먼저)는 같고 표만 다르다.
- **장부는 따로 둔다.** 장편·웹소설 연재처럼 여러 세션에 걸친 작업에서 초안 스킬 밖에서도 부른다(설정 변경 추적, 연재 전 점검).
- 플랫폼 정책 확인은 스킬로 만들지 않고 `fiction-draft/references/platform-policy.md`(확인 카드 양식 + 2026-11-15 확인 표)로 둔다. 연재할지 말지는 사업 판단이라 HQ가 따로 한다(W-431).

## 4. 스킬 명세

각 SKILL.md 뼈대는 이 브랜치의 `skills/*/SKILL.md`에 있다. 아래는 구현 기준이다.

### 4.1 nonfiction-draft

- **입력**: `brief`(조사 nonfiction 8.1 공통 입력 + 장르별 추가 입력), `materials_dir`(선택), `rules_doc`(선택, 매체 규칙이 이긴다), `out_path`.
- **절차**: ① 주 장르와 중심 질문 판정(1.2 표, 혼합 글은 결론에 맞는 장르) ② 자료를 역할별로(장면·정의·근거·반론·측정·작품 대목) ③ 장르 reference의 뼈대 하나 임시 선택, 부분마다 "독자에게 하는 일" 한 줄 ④ 초안(관계·논리 먼저) ⑤ `genre-rubric`과 같은 표로 **자기 진단만**(점수는 외부 채점이 낸다) ⑥ 구조→문단→문장→단어→교정 ⑦ 출처·인용·체험 최종 대조, 작업 표시 처리(확인/삭제/범위 제한).
- **장르 reference 구성**(조사에서 옮김): 핵심 한 문단, 뼈대 템플릿, 시니어 규칙(E-01~14 등, 출처 기호 유지), 실패 신호 표, 좋은 예시와 읽는 이유. 논설문은 4.4 오류→수정 지시, 4.5 데이터·인용 최소 기록 단위를 포함. 리뷰는 5.4 비교 기준 세우는 절차를 포함.
- **금지**: 제공되지 않은 개인 경험·직접 사용 경험·대사 창작, 존재하지 않는 출처·통계, 무조건 추천.
- **출력**: 초안 + 끝에 `## 작업 메모`(남은 작업 표시, 사용한 뼈대, 자기 진단에서 1점 이하 항목). 작업 메모는 발행본에서 뺀다.

### 4.2 fiction-draft

- **입력**: 조사 fiction 10절 목록(형식·세부 장르 조합 / 독자 / 목표 효과 / 분량 / 발표 방식 / 시점 / 인물표 / 세계 규칙 / 구조 선호 / 금지 요소 / 기존 본문·장부 / 플랫폼 조건) + `ledger_dir`(선택, 장편·웹소설은 필수).
- **절차**: ① 사용자 형식·의도를 먼저 따른다(구조 공식 자동 강제 금지) ② 전체 약속·인물의 선택 조건·결말 방향 요약 ③ `story-ledger`에서 이번 구간에 필요한 확정 사실·인물 상태·정보 접근권을 불러 장면 카드 작성 ④ 장면(또는 회차) 초안 ⑤ 새 사실·변화·약속 후보 추출 → 장부와 대조(모순·중복·정보 누출) → 수정 ⑥ 본문 확정 뒤 **본문과 분리한** 장부 갱신안 출력. 폐기 초안의 사실은 장부에 넣지 않는다.
- **reference**: `craft-core.md`(조사 2절: 인물표 필드, 주 구조 하나 고르기, Scene/Sequel, 시점·거리, 대사, 보여 주기·페이싱), 형식별 `short-story/novel/webnovel.md`(뼈대, 규칙 12개, 실패 신호, 웹소설은 회차 끝 선택지·분량 확인 수치와 그 한계), `korean-fiction.md`(6절 표와 말투 카드), `revision.md`(8절 퇴고 순서), `platform-policy.md`(9절).
- **웹소설 분량**: 숫자는 플랫폼·공모전 원문을 입력으로 받는다. 입력이 없으면 장면 단위로 쓰고 분량을 확정하지 않는다. 글자 수를 반복 설명으로 채우지 않는다.
- **금지**: 실존 작품의 인물·설정·문장 복제(장르 관습·구조만 쓴다), 확인 안 된 플랫폼 정책을 "허용"으로 판정.

### 4.3 genre-rubric

- blog-craft `post-rubric`과 같은 방식: `recipe:oneshot`으로 **글을 쓴 모델과 다른 회사 모델**이 채점. 입력 `post_path`, `genre`(7개 중 하나, 혼합이면 주 장르 + 보조 장르 표 일부), `brief_path`(선택, 창작 의도 — 의도와 맞는 이탈은 감점 안 함), `reviewer`.
- **출력**(조사 nonfiction 8.3 형식): 항목별 `{item, score, evidence(문장 인용), reason, fix, needs_check}`, `applicable_total`(적용 불가 제외 분모), `blockers`.
- **총점으로 상쇄하지 않는 결함(blockers)**: 존재하지 않는 출처·인용·통계 / 제공 안 된 경험·직접 사용 경험 창작 / 중심 설명을 무너뜨리는 사실 오류 / 결론을 뒤집는 반대 증거 누락 / (소설) 확정 설정의 중대 충돌, 제한 시점의 핵심 정보 누출, 결말을 성립시키는 근거 부재. blocker가 있으면 점수와 상관없이 "고칠 것"이다.
- **합격선 없음**: 20점 만점 점수만 낸다. 합격선은 W-430 평가와 실제 사용 5건 뒤 정한다.
- **scripts/auto_checks.py**(표준 라이브러리만, 결정적 검사, 점수 안 매김 — 후보만 낸다): ① 따옴표·괄호 짝(“” ‘’ 「」 『』 ()) ② 남은 작업 표시(`[경험 확인 필요]`, `[원자료 확인 필요]`, `[직접 시험하지 않음]`, `TODO`) ③ 문단별 서술체 혼용 후보(해라체/합니다체/해요체, 따옴표 안 제외) ④ 같은 종결 형태 3문장 연속 후보(경고만, 자동 교체 금지) ⑤ 사물 높임 후보 목록 일치. 출력은 JSON.

### 4.4 story-ledger

- **장부 형식**: 프로젝트 폴더 아래 TOML 파일(파이썬 3.11+ `tomllib`로 읽는다, 쓰기는 모델이 직접). `bible.toml`(설정 ID·사실·적용 조건·예외·상태·최초 근거 위치), `characters.toml`(욕망·전략·관계·말투 카드·신체·소유 상태·상태 `alive|dead` + 근거), `knowledge.toml`(정보 ID·실제 사실·인물별 인지·독자 공개 시점·근거), `timeline.toml`(사건 ID·날짜/상대 시간·지속·장소·이동), `episodes/E###.toml`(실제 사건·선택과 비용·새로 확정·미해결·다음 계획), `scenes/E###-S##.toml`(조사 7.4 장면 카드), `foreshadow.toml`(설치·재등장·회수·폐기 위치).
- 모든 사실에 `status = "confirmed" | "planned" | "belief"`. 계획은 이야기 속 사실이 아니다. 인물의 믿음은 진실과 다를 수 있다.
- **scripts/ledger_check.py 검사**(조사 7.6 '규칙으로 검사하기 좋은 것'만): ① ID 중복·참조 누락·필수 필드 ② 명시 날짜 선후(사건 순서와 회차 순서 대조) ③ `dead` 처리된 인물이 이후 장면 카드 참여자에 있음 ④ 같은 시점에 한 물건의 소유자가 둘 ⑤ 설치된 복선 중 회수·폐기 기록 없이 N회차(기본 30) 넘은 것 ⑥ 회차 본문 글자 수(공백 포함/미포함 둘 다)와 입력한 플랫폼 하한 대조. 출력 JSON, "이상 없음"에도 검사한 장부 파일 해시를 남긴다.
- **사람·모델이 판정할 것**(스크립트가 하지 않음): 설명 없는 정보 획득, 말투 변화, 능력의 자의적 예외, 동기 급변, 같은 깨달음 반복. SKILL.md에서 모델 점검 질문으로 둔다 — "문제 문장·충돌 근거·최소 수정안"을 함께 내게 한다.

## 5. blog-craft와의 연결

- blog-craft `post-draft`(W-421, R-065 승인 대기)는 고치지 않는다. W-430은 writing-craft만 만든다.
- 연결은 병합 뒤 따로(blog-craft 0.3.0): `post-draft` 1절 갈래 판정 뒤 "writing-craft가 설치돼 있으면 `writing-craft:nonfiction-draft`를 불러 해당 장르 reference를 읽는다"를 넣는다. 대응: B 재미·이목(직접 측정 비교) → `review.md`, C 경험기 → `essay.md`(성찰 규칙) + 기존 C 뼈대, A 안의 개념 설명 부분 → `explainer.md`. 설치 안 돼 있으면 기존대로 동작한다(약한 의존).
- 한국어 문체 규칙이 두 플러그인에 겹친다. 당분간 blog-craft 쪽이 블로그에서는 이긴다(매체 규칙 우선). 합칠지는 두 플러그인을 실제로 같이 써 본 뒤 정한다.

## 6. 평가 계획 (W-430, skill-creator 방식)

| 케이스 | 장르 | 입력 자료 | 보는 것 |

# 모델 검사 기준 (13항목)

이 문서는 `rubric` 스킬을 실행하는 에이전트가 **의미적 판정 13개 항목**을 일관되게 채점하기
위한 기준이다. 결정적 17개 항목은 `rule_checker.py`가 이미 처리하므로 여기서 다루지 않는다.

각 항목은 `check_type: "model"`로 기록하며, 판정 결과를 다음 형태로 만든다:

```json
{ "id": "V-REPEAT", "section": "타당성", "item": "반복 워크플로우",
  "check_type": "model", "severity": "MAJOR", "passed": true,
  "evidence": "근거 한 줄 (왜 통과/실패인지, 구체적으로)" }
```

판정 원칙:
- 확신이 없으면 **보수적으로 FAIL**하고 evidence에 불확실성을 적는다(품질 게이트는 엄격할수록 낫다).
- evidence는 일반론이 아니라 그 SKILL.md의 **실제 문장·구조**를 인용한다.
- description과 body 전체, 그리고 필요하면 `references/`까지 읽고 판단한다.

---

## 1. 타당성 (Validity) — 3항목, 모두 MAJOR

스킬로 만들 가치가 있는가를 본다.

### V-REPEAT — 반복되는 워크플로우인가
- **PASS**: 여러 번·여러 상황에서 다시 쓰일 절차를 담는다(예: "PR 리뷰", "SPEC 작성").
- **FAIL**: 일회성 작업이거나 한 번 쓰고 버릴 내용.
- 함정: 거창해 보여도 실제로는 단발성이면 FAIL.

### V-GENERIC — 범용성(특정 프로젝트 한정이 아님)
- **PASS**: 다른 저장소·맥락에도 적용 가능한 일반 절차.
- **FAIL**: 이 저장소의 특정 파일 경로·내부 사정에만 묶여 재사용 불가.
- 함정: 조직 고유 운영 규칙(C-ORG에서 권장)과 혼동하지 말 것 — 여기서는 "한 프로젝트에만
  묶여 스킬화할 가치가 없는가"를 본다. 내부 룰을 담되 절차 자체가 재사용 가능하면 PASS.

### V-IRREPLACEABLE — 대체 불가능성
- **PASS**: 에이전트의 기본 능력만으로는 일관되게 수행하기 어려운, 고유한 절차·지식을 더한다.
- **FAIL**: "코드를 읽어라", "테스트를 실행하라" 수준의 기본 능력 재기술.

## 2. 트리거 (Trigger) — 4개 모델 항목, 모두 MAJOR

description만으로 에이전트가 **언제 호출할지** 판단할 수 있는가를 본다.
(Body-only·argument-hint는 규칙 검사기가 처리한다.)

### T-WHATWHEN — WHAT + WHEN 모두 포함
- **PASS**: description에 "무엇을 하는가(WHAT)"와 "언제 쓰는가(WHEN)"가 모두 있다.
- **FAIL**: 기능 설명만 있고 호출 시점이 없거나, 반대로 시점만 있고 기능이 모호.
- 예: "PR diff를 다관점으로 리뷰해 판정을 낸다 — 작업 완료·머지 전 검증이 필요할 때 사용" → PASS.

### T-KEYWORDS — 트리거 키워드 충분
- **PASS**: 사용자가 실제로 쓸 법한 표현·동의어가 description에 충분히 담겨 매칭이 잘 된다.
- **FAIL**: 키워드가 빈약해 관련 요청에도 호출이 안 잡힐 위험.

### T-SEMANTIC — description과 본문 의미 일치
- **PASS**: description이 약속한 동작과 본문이 실제로 시키는 동작이 일치.
- **FAIL**: description은 A를 한다는데 본문은 B를 시킨다(과장·불일치).

### T-SCOPE — 트리거 범위가 과도하지 않음
- **PASS**: 적절히 좁아, 무관한 요청까지 빨아들이지 않는다.
- **FAIL**: "어떤 작업이든", "항상" 류로 과도하게 넓어 오발동 위험. (단, 진입점 성격의
  라우팅 스킬은 의도적으로 넓을 수 있으니 맥락을 본다.)

---

## 3. 콘텐츠 (Content) — 2개 모델 항목

### C-SPECIFIC — 구체성 (MINOR)
- **PASS**: 수치·코드·임계값·"왜(Why)"·구체 시나리오가 있다.
  예: "N > 100이면 SCAN 사용 (응답 300ms → 5ms)".
- **FAIL**: "Redis는 인메모리 DB입니다" 같은 일반론·교과서 서술.

### C-ORG — 조직 고유성 (MAJOR)
- **PASS**: 일반 상식이 아니라 이 조직·프로젝트의 내부 운영 규칙·관례·결정을 담는다.
- **FAIL**: 어디서나 찾을 수 있는 일반 베스트프랙티스만 나열.

---

## 4. 리소스 (Resource) — 4개 모델 항목

### R-SPLIT — 본문/참고 분리 (MAJOR)
- **PASS**: 핵심 절차는 SKILL.md 본문에, 상세·레퍼런스는 `references/`에 분리.
- **FAIL**: 모든 상세를 본문에 욱여넣어 본문이 비대하거나, 반대로 본문이 비고 전부 참고로 빠짐.

### R-LINKWHEN — references 읽는 시점 명시 (MINOR)
- **PASS**: "X를 할 때 `references/y.md`를 읽어라"처럼 참고문서를 **언제** 읽는지 본문이 지시.
- **FAIL**: references 파일은 있는데 본문이 그것을 언제 읽어야 하는지 말하지 않음.

### R-NESTED — 중첩 참조 없음 (MAJOR)
- **PASS**: 참조 깊이가 얕다(본문 → references 1단계).
- **FAIL**: A가 B를 읽으라 하고 B가 다시 C를 읽으라 하는 A→B→C 연쇄.

### R-SCRIPTIFY — 실수 가능한 작업의 스크립트화 (MAJOR)
- **PASS**: 손으로 하면 틀리기 쉬운 결정적 작업(파싱·계산·정해진 명령열)은 `references/`의
  스크립트로 고정.
- **FAIL**: 매번 에이전트가 즉흥으로 재현해야 하는, 틀리기 쉬운 절차를 산문으로만 남김.

## 병합·등급 (검사 후)

규칙 17 + 모델 13 = 30항목을 합친 뒤 등급을 매긴다:

- BLOCKER ≥ 1 → **F**
- BLOCKER 0, MAJOR 0 → **S**
- BLOCKER 0, MAJOR 1–2 → **A**
- BLOCKER 0, MAJOR 3–4 → **B**
- BLOCKER 0, MAJOR 5+ → **C**

MINOR 개수는 등급을 가르지 않으나 리포트에 함께 표시한다.

# 컨텍스트 관리 지침

AI 에이전트 간 작업 컨텍스트를 영속화하는 규칙입니다. 세션 기억에 의존하지 않고 다음 에이전트가 이어받을 수 있어야 합니다.

이 프로젝트는 **파일시스템 백엔드**를 사용합니다. 모든 태스크는 `.tasks/` 아래에 마크다운 파일로 저장하고 git에 커밋합니다.

## 태스크 우선 원칙 (no-task-no-work)

비자명한 작업은 **관련 태스크 파일이 있을 때만 시작합니다**. 없으면 먼저 태스크를 만듭니다. `backlog`는 제목 + 1-2줄 설명만으로 충분하며, "작다"·"즉흥적"이라는 이유로 생략하지 않습니다.

### 작업 시작 신호

- 첫 `Edit`/`Write` 호출
- `git add`/`git commit` 호출
- 외부 상태를 바꾸는 도구 호출 (외부 API, 인프라 변경 등)
- 한 카테고리에서 다파일 변경을 시작할 때

신호 발생 시 태스크가 없으면 작업 중단 → `.tasks/T-NNN.md` 생성 → 작업 재개. 사용자에게 생성 사실을 알립니다.

### 예외

- 사용자가 명시적으로 "이번엔 태스크 없이"·"룰 무시"처럼 면제해준 경우.
- 단순 정보 조회(파일 read, `git log`, 검색)는 작업 시작 신호가 아닙니다.

### 계획 섹션 채움

- `backlog`는 제목 + 1-2줄 설명만 있어도 됩니다.
- `in_design` 또는 `in_progress`로 전이할 때는 목표·배경·제안·검증 계획·완료 기준을 채웁니다. 빈 섹션이나 `TBD`로 전이하지 않습니다.
- 짧아도 명확해야 합니다. 시작 후 알게 된 사항은 진행 로그·결정 섹션에 추가하고, 필요하면 계획 섹션도 갱신합니다.

### 위반 발견 시

작업 중 태스크 누락을 발견하면 즉시 멈추고 retroactive 태스크를 만듭니다. 진행 로그의 `[handoff]` 항목에 사유를 남긴 뒤 재개합니다.

## 태스크 파일

- 위치: `.tasks/T-NNN.md`
- ID: `T-NNN` 일련번호. 한 번 부여하면 바꾸지 않습니다. 빈 번호는 재사용하지 않습니다.
- 한 파일 = 한 태스크. 디렉토리 중첩 없이 평평하게 둡니다.
- 부모-자식 관계는 frontmatter `parent:`로만 표현합니다.

### Frontmatter 스펙

```yaml
---
id: T-001
title: <짧은 제목>
status: in_progress       # backlog | in_design | in_progress | blocked | review | done | cancelled
parent: T-000             # 상위 태스크 ID (없으면 생략)
depends_on: [T-002]       # 차단 의존 (없으면 생략)
owner: <agent-or-user>    # in_progress·blocked일 때만 채움 (선택)
created: 2026-04-28T10:00:00Z
refs:                     # 태스크 전체와 연관된 핵심 산출물 1~3개 (없으면 생략)
  - path/to/file.ts
  - https://github.com/.../pull/42
---
```

수정 시각·마지막 활동은 git 메타데이터(`git log`)로 확인합니다. frontmatter에 별도 필드를 두지 않습니다.

### 본문 섹션 (순서 고정)

```markdown
## 목표
측정·확인 가능한 결과 상태를 1~3문장으로 작성.

## 배경
문제·상황·리스크를 처음 보는 사람도 이해할 만큼 작성.

## 제안
접근, 구현 순서, 도구·라이브러리, 대안과 선택 이유를 이어서 실행 가능하게 작성.

## 검증 계획
테스트·도구·관찰 지표·수동 단계로 DoD 확인 방법을 작성.

## 완료 기준 (Definition of Done)
- [ ] ...
- [ ] ...

## 진행 로그 (append-only)
- 2026-04-28T10:00:00Z @agent-a: 시작. ...
- 2026-04-28T11:00:00Z @agent-a: ... 발견.

## 결정 (Decisions)
- 2026-04-28: X 대신 Y 선택. 이유: ...
```

- 목표는 무엇, 제안은 어떻게, DoD는 끝났는지의 체크리스트입니다.
- 검증 계획은 DoD를 확인하는 방법입니다.
- 진행 로그에는 결정·차단 사유·놀라운 발견·외부 영향이 있는 변경만 적습니다.
- `refs:`는 태스크 전체와 관련된 핵심 산출물 1~3개만 둡니다. 임시 참조는 진행 로그에 적습니다.

## 상태와 전이

기본 흐름: `backlog` → `in_design` → `in_progress` → `review` → `done`

보조 상태: `blocked`(차단, 해소 시 직전 상태 복귀), `cancelled`(사유 기록 후 종료)

Status 전이는 작업 에이전트 책임입니다. 아래 이벤트가 발생하면 직접 `status:`를 갱신합니다.

| 이벤트 | 전이 |
|---|---|
| 첫 작업 시작 신호 (Edit/Write, `git add`/`git commit`) | `backlog` 또는 `in_design` → **`in_progress`** |
| DoD 모두 체크 + 검증 PASS + 변경 commit | `in_progress` → **`review`** |
| 사용자의 명시적 "완료"·"Done"·"닫아줘" 신호 | `review` → **`done`** |
| 차단 사유 발견 | Any → **`blocked`** (진행 로그에 `[blocked]` 항목으로 사유 기록) |
| 차단 해제 | `blocked` → 직전 상태 |

`review` → `done`은 사용자 명시 신호가 있을 때만 수행합니다.

## 운영 규칙

1. **시작 전**: 관련 태스크를 확인하고 없으면 만듭니다. 대상 파일과 마지막 `[handoff]`를 먼저 읽습니다.
2. **시작 시**: `status: in_progress`, `owner`를 설정하고 시작 로그를 추가합니다.
3. **진행 중**: 의미 있는 발견·결정·차단을 즉시 기록합니다. 계획이 바뀌면 갱신합니다.
4. **commit 전**: 자동화 가능한 검증 계획을 모두 실행합니다. 실패하면 commit하지 말고 수정 후 재검증합니다. 수동 검증은 `[handoff]`에 담당자·시점을 남깁니다.
5. **완료 시**: DoD 점검 → `review` 또는 `done` 전이 → `[handoff]` 추가 → `owner` 비움.
6. **append-only**: 진행 로그·결정은 삭제하지 않습니다. 정정은 새 항목으로 추가합니다.

## 태스크 단위

- 1 태스크 ≈ 한 에이전트가 한 세션에 끝낼 수 있는 분량.
- 더 크면 하위 태스크로 분할합니다. 부모 태스크는 하위 태스크의 진행 상황을 요약해 둡니다.
- 깊이는 2~3 단계 이내를 권장합니다.

## 공통 규칙

- 태스크 파일은 git에 커밋합니다.
- 시각은 ISO 8601 UTC를 사용합니다 (예: `2026-04-28T10:00:00Z`).
- ID는 한 번 부여하면 바꾸지 않습니다. 잘못 만들었으면 `cancelled` 처리하고 새 ID로 다시 만듭니다.

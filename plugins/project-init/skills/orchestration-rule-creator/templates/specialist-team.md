# 오케스트레이션 지침

여러 에이전트(메인 + subagent)가 함께 작업할 때의 구성·위임·합성 규칙입니다. subagent는 같은 대화를 공유하지 않고 한 번의 브리프와 한 번의 보고로만 소통하므로, 다음 규율이 필요합니다.

이 프로젝트는 **전문가 팀 모델**을 사용합니다. 메인 에이전트는 팀 리드(PM)로서 조율·합성·사용자 대화를 담당하고, subagent는 특정 관심사·도구 셋을 가진 외부 전문가로 다룹니다.

## 역할 매핑

| 개념 | 팀 비유 | Claude 매핑 |
|---|---|---|
| 메인 에이전트 | 팀 리드(PM) | 사용자와 직접 대화하는 세션 |
| subagent | 외부 전문가(컨트랙터) | `Agent` 도구로 호출되는 격리 에이전트 |
| 브리프 | 작업 의뢰서 | subagent 호출 시 전달하는 prompt |
| 보고서 | 컨트랙터 결과물 | subagent의 최종 응답 1건 |
| 팀 채팅 | 비공유 | subagent는 메인 대화를 모름 |
| 합성 | 리드의 책임 | 메인이 보고서를 검증·종합 |

핵심 비대칭: **subagent는 메인 대화를 보지 못하고, 사용자와 직접 대화하지도 않는다.** 한 번 출근한 시니어처럼 대한다 — 무엇을·왜·이미 시도한 것·결과 형식을 브리프에 모두 담는다. 사용자에게 가는 답변은 항상 메인이 작성한다.

## 위임 우선 원칙 (no-skim-no-delegate)

다음 신호가 보이면 **메인이 직접 처리하지 않고** subagent에 위임합니다. 메인 컨텍스트를 보호하고 신호를 격리하기 위함입니다.

### 위임 트리거 (이 중 하나라도 해당하면 위임 검토)

- **3쿼리 이상의 탐색·조사** — 결과물이 크거나 중간 단계가 많아 메인 컨텍스트를 오염시킬 작업
- **독립적으로 진행 가능한 일이 둘 이상** — 병렬화로 시간을 줄일 수 있는 경우
- **독립적 시각이 필요한 검증·리뷰** — 메인의 가설에 오염되지 않은 판단이 필요할 때
- **도구·권한 셋이 다른 작업** — read-only 탐색, 격리된 변경, 외부 API 호출 등 도구 프로파일이 분리될 때
- **산출물이 길어 메인에 머무르면 안 되는 작업** — 보고서·로그·diff가 컨텍스트를 점유할 때

### 위임하지 않을 때 (예외)

- **한두 번의 쿼리로 끝나는 단순 조회** — 알려진 경로 read, 단일 grep, `git log` 한 줄.
- **결정·합성이 메인의 책임인 단계** — 위임하면 책임이 누락됩니다.
- **사용자 응답을 즉시 반영해야 하는 대화 흐름** — subagent는 사용자를 보지 못합니다.

### 위반 발견 시

본 지침의 룰 위반(병렬 가능한데도 직렬화, 위임 과잉, 합성 책임 떠넘기기, 자기 위임·중첩 호출 등)을 인지·지적당하면, 즉시 작업을 멈추고 결과의 신뢰성을 다시 검토합니다. 같은 세션에서 같은 패턴을 두 번째 반복하지 않습니다.

## 브리프 작성 (위임 시 반드시 포함)

subagent의 출력 품질은 브리프 품질에 정비례합니다. **명령형 단문은 얕은 결과를 부릅니다.** 자기완결 브리프는 다음을 모두 포함합니다.

- **무엇을** — 목적, 결과 형식, 응답 길이 제약
- **왜** — 상위 작업의 맥락 (subagent가 판단을 내릴 수 있도록)
- **이미 시도한 것·확정된 것** — 반복·역행 방지
- **건너뛸 영역** — 범위 밖, 다른 에이전트 담당, 보고 불필요한 부분
- **응답 포맷** — 파일 경로 + 라인 번호, ≤200자, 표 형식 등 후행 처리에 필요한 형태

브리프 한 줄짜리("X를 분석해 줘")는 충분치 않습니다. **새로 출근한 시니어 동료가 콜드 시작으로 작업할 수 있을 만큼**의 정보를 담습니다.

## 병렬 호출 vs 순차 호출

- **데이터 의존성이 없으면 같은 메시지에서 병렬 호출.** 한 메시지에 여러 도구 호출 블록을 묶습니다.
- **한 호출의 출력이 다음 호출의 입력일 때만 순차.** 그 외에는 직렬화 자체가 결함입니다.
- 사용자가 "병렬로"라고 명시했는데 직렬로 처리하면 즉시 결함. 한 메시지에 묶어 다시 호출합니다.

## 합성은 호출자(메인)의 책임

subagent의 보고서는 휘발성이므로, 프로젝트에 영속 채널(예: issue comment, PR 본문, 노트 파일)이 있으면 영속이 필요한 결정·발견은 메인이 영속 채널에 기록합니다. 보고를 받는 시점에 메인이 합성·검증·영속화를 함께 처리합니다.

- subagent의 보고서는 **의도**이지 **사실**이 아닙니다. "변경 완료"라고 주장하면 실제 diff를 본인이 확인합니다.
- 여러 subagent의 결과가 충돌하면 메인이 최종 판단합니다 — subagent에게 합의를 위임하지 않습니다.
- "subagent 결과를 바탕으로 다음 작업을 해 줘"라는 자기 위임은 금지. **합성은 호출자 본인의 일**입니다.
- 보고서를 사용자에게 그대로 전달하지 않습니다. 사용자에게 가는 답변은 메인이 검증·요약합니다.
- 위임한 일을 메인이 다시 수행하지 않습니다 — 이중 수행은 자원 낭비이자 결과 신뢰성 저하의 원인입니다.
- 위임 결정 자체를 subagent에 맡기지 않습니다 — "이 일을 누구에게 시킬지 정해 줘"는 메인의 판단입니다.

## subagent는 단일 패스 워커

subagent는 한 번의 브리프를 받아 한 번의 보고로 끝내는 외부 컨트랙터입니다. **반복은 호출자(메인)의 책임**이며, subagent 내부에서 자체 루프를 돌리지 않습니다. 이 경계가 무너지면 다음이 깨집니다.

- **관찰 가능성**: 메인이 중간 상태를 볼 수 없는 사이 작업이 표류
- **비용 통제**: 인간 체크포인트 없이 토큰 누적
- **계층 분리**: "루프 드라이버"의 책임이 워커에 섞임
- **재현성**: 동일 브리프가 매번 다른 깊이의 작업을 만듦

따라서:

- **한 호출 = 한 브리프 → 한 보고.** 끝.
- 추가 작업이 필요하면 메인이 결과를 읽고 **새로운 호출**을 시작합니다 (같은 호출의 연장이 아님).
- subagent에게 "끝까지 알아서 진행" 식의 지시를 하지 않습니다 — 자기 위임은 루프 드라이버 책임을 워커에 떠넘기는 것입니다.
- **중첩 위임 금지**: subagent 내부에서 다시 subagent를 호출하지 않습니다. 합성·관찰 책임이 메인에서 이탈합니다.

## 역할 카탈로그 (확장 가능)

새 역할은 다음 4축이 모두 명확할 때만 추가합니다 — 목적, 도구 셋, 신호 독립성, 응답 형식.

| 역할 | 주된 책임 | 도구 프로파일 | 응답 형식 (구체) |
|---|---|---|---|
| 탐색가 (Explorer) | 코드베이스에서 정의·참조 위치 찾기 | read-only | 매칭 항목 N건. 각 항목당 `path:line` + 1줄 컨텍스트. 추측·해석 없이 발견 사실만 |
| 검증자 (Reviewer) | 변경·설계 독립 평가 | read-only + 분석 | 발견 1~5건. 각 항목당 위치·근거·심각도(blocker/major/minor) + 수정 권고 1줄 |
| 작업자 (Implementer) | 격리된 변경 수행 | write 권한 | 변경 파일 목록 + 변경 단위로 묶어 요지 1~2줄 + 검증 결과(어떤 명령으로 확인) |
| 계획가 (Planner) | 구현 전략 설계 | read-only + 분석 | 단계 N개. 각 단계당 변경 대상·핵심 접근·예상 위험. 의사코드 가능, 실제 코드 작성 금지 |

축이 흐릿한 역할(예: "잘 알아서 처리하는 만능 에이전트")은 추가하지 않습니다 — 합성 책임이 흐려집니다.

## 금지 (요지)

본문 규율의 슬로건 모음. 자세한 근거는 위 본문을 참조합니다.

- 결정 위임 ("적절히 판단해 진행")
- 사용자 직접 대화 지시
- 보고 우회 전달 (검증·요약 없이 그대로)
- 단문 브리프 ("X 해 줘")
- 이중 수행 (위임 후 메인이 재실행)
- 직렬화 (병렬 가능한데도)
- 자기 위임·내부 반복·중첩 호출

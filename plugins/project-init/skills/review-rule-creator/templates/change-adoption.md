# 변경 반영 판단 지침

리뷰, 제안, 자체 점검에서 나온 항목은 바로 반영하지 말고 먼저 성격을 분류한다. 목표는 모든 지적을 수용하는 것이 아니라, 실제 품질·안전성·유지보수성을 높이는 변경만 반영하는 것이다.

(리뷰를 *어떻게 수행하는가*는 `rules/review/principles.md`. 본 문서는 거기서 *나온 지적을 반영할지* 판단하는 기준이다.)

## 반드시 반영할 항목

다음 중 하나에 해당하면 수정한다.

- 실제 버그, 오동작, 데이터 손상, 보안 문제를 만들 수 있다.
- 요구사항, 계약, 공개 API, 사용자 흐름과 충돌한다.
- 테스트, 검증, 완료 조건, 권한, scope 같은 안전 경계를 약화한다.
- 문서나 지침에서 참조 대상이 사라져 모순 또는 dangling reference가 생긴다.
- 절차 설명이 빠져 독자가 다음 행동을 재현할 수 없다.
- 중복 제거 과정에서 원래 보장하던 중요한 의미가 사라졌다.
- 미래 변경자가 잘못 해석할 가능성이 높고, 그 오해의 비용이 크다.

## 후속으로 분리할 항목

맞는 지적이지만 현재 변경의 목표·scope를 넘어서거나 별도 설계가 필요한 경우, 현재 작업에 섞지 말고 후속 task/issue로 분리한다. 단, 보안·데이터 손상·계약 위반처럼 즉시 위험한 항목은 후속으로 미루지 않는다.

## 반영하지 않아도 되는 항목

다음에 해당하면 수정하지 않거나 더 작게 축약한다.

- 이미 다른 더 강한 규칙, 테스트, 타입, 자동화가 같은 행동을 보장한다.
- 표현 선호, 문체, 강조, 요약, 철학에 가깝고 실행 결과를 바꾸지 않는다.
- 추가 설명이 정확하더라도 본문 흐름을 무겁게 만들고 실무 판단에는 거의 기여하지 않는다.
- 예외적 상황을 지나치게 자세히 설명해 일반 경로의 이해를 방해한다.
- 변경 비용이나 복잡도 증가가 기대 효과보다 크다.
- 문제를 예방하기보다 단지 "좋아 보이는" 완성도를 높이는 수준이다.

## 판단 순서

1. 이 항목을 반영하지 않으면 무엇이 실제로 잘못될 수 있는가?
2. 그 문제는 이미 다른 규칙, 코드, 테스트, 도구가 막고 있는가?
3. 반영하면 핵심 흐름이 더 명확해지는가, 아니면 장황해지는가?
4. 이 변경은 자주 쓰이는 경로를 돕는가, 드문 예외를 과하게 키우는가?
5. 유지 비용이 새로 생기는가?
6. 독자나 실행자가 이 정보 없이도 올바른 행동을 할 수 있는가?

## 결론 규칙

- 행동, 안전, 계약, 재현성을 바꾸는 지적은 반영한다.
- 문체, 중복 강조, 메타 설명, 낮은 영향의 완성도 제안은 반영하지 않는다.
- 애매하면 더 긴 설명을 추가하기보다, 핵심 행동을 보존하는 짧은 문장으로 축약한다.
- "맞는 말인가?"보다 "이 문서나 코드가 이 말을 반드시 품고 있어야 하는가?"를 기준으로 판단한다.

## 적용 가드 (오용 방지)

위 분류는 실제 수정을 회피하는 합리화 도구로 쓰면 안 된다. 다음을 강제한다.

- **안전 경계는 항상 우선 평가.** 테스트·평가 기준·완료 조건·권한·scope·보안에 관한 지적은 낮은 영향으로 분류하지 않는다. 다만 제안된 해결책을 그대로 수용하지 말고, 안전 경계를 보존하거나 강화하는 방향으로만 반영한다.
- **"이미 보장됨"은 추정 금지.** "이미 다른 규칙·테스트·타입이 같은 행동을 막는다" 또는 "영향이 낮다"로 분류하려면, 그 규칙·테스트를 **구체적으로 짚을 수 있어야 한다**. 짚지 못하면 반영 쪽으로 기운다. 자기 변경을 스스로 판정하는 맥락(self-review)에선 합리화로 결함을 skip하기 쉬우므로 이 가드가 특히 중요하다.

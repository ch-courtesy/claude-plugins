# fsd 상시 호스트 무인 운영 가이드

`fsd` 파이프라인(`fsd start` → `fsd poll`)을 **전용 상시 호스트(dedicated always-on host)**에서
무인으로 운영해 spec→dispatch→(dispatch가 소유하는)리뷰·머지를 **완전자율**로 닫기 위한
운영·보안 경계 문서다. 리뷰·머지·통합은 `dispatch` 통합 모드(기본 ON)가 소유하며, fsd 에는
리뷰·머지·승인 게이트가 없다 — 외부 승인 보류·사람 개입 지점이 없는 무인 자율 운영이다.
본 가이드는 호스트별 설정 산출물(systemd 유닛 등)을 만들지 않고 **문서로만** 안내한다.

> 사용자 확정 결정: **런타임은 전용 상시 호스트.** 이 호스트가 무인 `gh` 자격증명의
> 신뢰 경계(trust boundary)다. 개발자 노트북·공용 CI 러너가 아닌, 이 자동화 전용으로
> 격리된 호스트에서만 무인 토큰을 둔다.

---

## 1. 신뢰 경계 한눈에

```
전용 상시 호스트 (trust boundary)
├── 스케줄러 (cron / /schedule / /loop)
│      ├── fsd start  → dispatch start (통합 모드 ON)
│      │        ├── loop (자율 실행기 서브프로세스)        ※ push/merge 권한 미상속
│      │        └── 통합·머지: dispatch 가 소유            push (작업 브랜치) → ff-only 머지
│      └── fsd poll   → dispatch status 관측만 (읽기 전용; 쓰기·머지 없음)
└── 자격증명
       └── BOT_TOKEN  범위 최소화된 자동화 토큰 (push·PR)  ← dispatch 통합이 소비
```

핵심 2대 통제: **(1) 토큰 권한 스코프 최소화 · (2) 자율 실행기 서브프로세스 권한 격리.**
완전자율 direct 머지(분리 승인 신원 없이 ff-only 머지)이므로 별도 승인 신원·승인 게이트는
두지 않는다. 머지는 `dispatch` 통합 모드가 ff-only 로만 수행하며(force 금지), fsd 는 그
결과를 `dispatch status` 로 관측만 한다.

---

## 2. 무인 자격증명 토큰의 권한 스코프

무인 `gh` 토큰(`BOT_TOKEN`)은 **최소 권한 원칙**으로 발급한다. dispatch 통합이 실제로
호출하는 forge 동작에 필요한 스코프만 부여하고, 그 외는 명시적으로 배제한다.

### 2.1 필요한 최소 스코프

| 동작 (소유 주체) | 필요한 권한 스코프 |
|---|---|
| 작업 브랜치 push (dispatch 통합) | `contents: write` — **단, 작업 브랜치/대상 브랜치 네임스페이스로 제한** |
| PR 생성/조회 (dispatch forge 서브모드) | `pull_requests: write` |

- forge 미구성(direct 서브모드)이면 dispatch 는 PR 없이 로컬 ff-only 머지 후 대상 브랜치를
  push 한다 — 이때 필요한 것은 `contents: write` 뿐이다.
- Fine-grained PAT 또는 GitHub App 설치 토큰을 권장한다(classic `repo` 광역 스코프 지양).
- **대상 저장소를 이 레포 하나로 한정**한다(조직 전체 토큰 금지).
- 토큰은 호스트의 비밀 저장소(예: `gh auth login` 의 OS 키체인, 또는 파일 권한 `600`
  의 환경 파일)에만 둔다. 레포·로그·`.fsd/` 상태 디렉토리에 절대 커밋·기록하지 않는다.
- 만료·로테이션: 짧은 만료(예: 90일 이하) + 주기 로테이션. 유출 시 폐기 절차를 문서화한다.

### 2.2 배제할 권한 (명시적 비-스코프)

- `BOT_TOKEN` 에 **branch protection 우회·force push·admin** 권한을 주지 않는다.
  통합·머지 경로의 어떤 모듈도 force 를 쓰지 않으며(머지는 `--ff-only`), 토큰 수준에서도 막는다.
- 조직 멤버십·secrets·Actions 관리 등 파이프라인과 무관한 스코프는 부여하지 않는다.

## 3. 자율 실행기 서브프로세스 권한 격리

`dispatch start` 는 구현을 **자율 실행기(loop) 서브프로세스**에 위임한다. 이 서브프로세스는
**머지·대상 브랜치 push 권한을 상속해서는 안 된다** — 사고 반경을 구현 작업 공간으로 가둔다.

- **권한 하향(de-privilege)**: 자율 실행기 자식 프로세스의 환경에서 대상 브랜치 push·머지
  권한을 제거한다. 자식에는 작업 브랜치 커밋에 필요한 최소 토큰만, 또는 아예 토큰 없이(로컬
  커밋만) 돌리고 push·머지는 dispatch 통합 단계가 수행한다.
- **머지는 자식이 아니라 dispatch 통합이 한다**: 머지는 자율 실행기 안에서 일어나지 않고,
  dispatch 통합 모드의 머지 단계(`--ff-only`)에서만 일어난다. 자식 코드가 대상 브랜치를 직접
  머지·push 할 수 없게 토큰·브랜치 보호로 막는다.
- **작업 공간 격리**: 자식은 자기 격리 워크트리/작업 공간에서만 쓰고, fsd 상태
  디렉토리(`.fsd/`) 밖을 건드리지 않는다. 정리는 머지 확인 후 dispatch·loop 의 공개 cleanup
  인터페이스로만 위임한다(직접 삭제 금지).

## 4. 폴링 주기·실행 방식

전용 상시 호스트에서 `fsd poll` 을 **주기적으로** 돌려 task 의 dispatch run 을 관측하고
완료된 task 를 `done` 으로 전이시킨다. poll 은 호출 단위 무상태·멱등(읽기 전용 관측 + 멱등
전이)이므로, 크래시·중복 실행에도 안전하다. 다음 중 하나로 스케줄링한다.

### 4.1 권장 주기

- **기본 5–15분 간격.** dispatch run 진행 반응성과 forge API rate limit·비용 사이의 균형값.
  활발한 개발 중이면 짧게(5분), 한산하면 길게(15–30분) 조정한다.
- **단일 실행 보장**: 동시에 두 드레인이 겹치지 않도록 lock(예: `flock`)으로 직렬화한다.
  poll 자체가 멱등이라 겹쳐도 치명적이진 않으나, 불필요한 호출을 막는다.

### 4.2 실행 수단 (택1) — 호스트별 설정 산출물은 만들지 않고 안내만 한다

- **호스트 cron** (전용 상시 호스트의 표준 수단):

  ```cron
  # 10분마다 멱등 드레인 1회 (flock 으로 중복 실행 방지)
  */10 * * * * /usr/bin/flock -n /tmp/fsd-poll.lock \
      bash /path/to/plugins/autopilot/.codex-plugin/skills/fsd/references/poll.sh poll \
      >> /var/log/fsd-poll.log 2>&1
  ```

- **하니스 `/schedule`** (원격 스케줄 에이전트): `fsd poll` 을 cron 식으로 등록.
- **하니스 `/loop`** (간격 반복 실행): 대화형/세션 호스트에서 `poll` 을 주기 반복.

> 어느 수단이든 본 가이드는 **글루(어떻게 주기 실행할지)만 문서화**하고, systemd 유닛
> 같은 호스트별 설정 파일은 산출하지 않는다.

### 4.3 운영 점검 체크리스트

- [ ] `BOT_TOKEN` 스코프 최소화(§2) — force·admin 권한 없음.
- [ ] 자율 실행기 자식에 머지·대상 브랜치 push 권한 미상속 (§3).
- [ ] 머지는 dispatch 통합이 `--ff-only` 로만 수행(force 금지).
- [ ] poll 단일 실행 lock + 주기(§4.1) 설정.
- [ ] 토큰을 레포·로그·`.fsd/` 에 기록하지 않음.

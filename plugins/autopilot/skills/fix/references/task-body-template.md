# 태스크 본문(=SPEC) 구조 + 진단 섹션 (fix 자체 소유)

태스크 본문이 설계의 단일 출처다. 별도 SPEC 파일을 만들지 않는다. 플러그인 자기완결 — 외부 스킬·`rules/`를
참조하지 않는다. 본문 섹션 순서(고정) — 백엔드 공통이며 정규 정의는 플러그인 `task-backend/contract.md`와
일치한다. fix는 공통 본문에 **진단 섹션**을 더한다(권장 위치: 배경 다음, 검증 계획 앞 — 원인 이해가 완료
기준의 앵커가 되도록).

```markdown
## 목표
측정·확인 가능한 결과 상태를 1~3문장으로. WHAT(무엇을 이룰지)만 — 기술 스택·파일 경로 같은 HOW는 제약/제안으로.

## 배경
버그·증상·실패 신호의 맥락을 처음 보는 사람도 이해할 만큼.

## 제안
수정 접근·구현 순서·대안과 선택 이유를 실행 가능하게.

## 진단
### 증상
- 기대 동작: <무엇이 일어나야 하는가>
- 실제 동작: <무엇이 관찰되는가>

### 재현 맥락
- 입력·환경·시점: <어떤 조건에서 나타나는가>
- 빈도: <항상 | 간헐(조건)>
- 신호: <에러 메시지·스택·로그가 지목한 파일:줄, 있으면>

### 근본 원인 가설
- 가설: <X가 근본 원인이다 — 정적 분석 기반 가설(확정 아님)>
- 근거(정적 증거):
  - `<파일:줄>` — <이 코드가 가설을 어떻게 뒷받침하는가>
  - `<파일:줄>` — <…>
- 대안·불확실: <배제한 다른 후보, 또는 [NEEDS CLARIFICATION: ...]>

## 검증 계획
완료 기준을 어떻게 확인하는지(테스트·관찰 지표·수동 단계). 진입 명령 자체는 적지 않는다.

## 완료 기준 (Definition of Done)
- [ ] 해당 버그가 더 이상 관찰되지 않음(관찰 가능·독립 테스트 가능)
- [ ] 회귀를 막는 가드(테스트 등)가 존재
```

## 작성 규칙

- **WHAT/HOW 방어선** — 목표·완료 기준에는 "무엇"만. 기술 선택·경로·라이브러리 같은 "어떻게"는 제안/제약에.
- **진단 섹션**의 근본 원인은 **확정이 아닌 가설**로 프레이밍하고 증거를 `파일:줄`로 싣는다. 정적 분석 한정을
  위반하는 실행·재현 가정을 적지 않는다.
- **완료 기준**은 각 항목이 관찰 가능하고 독립적으로 테스트 가능해야 한다(실행 스킬이 이걸로 검증). "버그
  미관찰 + 회귀 가드"를 인코딩한다.
- 미해결 항목은 `[NEEDS CLARIFICATION: <구체 질문>]` 마커로 남긴다 — 마커가 있으면 무인 실행이 차단된다.
- 본문은 자기완결이어야 한다 — 실행 스킬이 본문만 읽고 중간 질문 없이 구현할 수 있을 만큼.

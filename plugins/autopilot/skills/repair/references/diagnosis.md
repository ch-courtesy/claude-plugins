# 정적 분석 진단 절차 (repair 고유)

repair step 2 의 **단일 방법론 출처**. 증상에서 근본 원인 **가설**로 좁히는 절차를 정의한다. 진단은 **정적 분석으로만** 한다 — 코드·로그·증상·에러 메시지·스택·최근 변경을 **읽고 추론**할 뿐, 버그를 실행·재현하거나 디버거를 붙이거나 실패 테스트를 구동하지 않는다.

핵심 원칙: 실행 없이 세운 가설은 틀릴 수 있다. 그래서 결과를 **확정이 아닌 가설**로 프레이밍하고, 모호하면 추정으로 메우지 말고 `[NEEDS CLARIFICATION: <구체 질문>]` 마커로 남겨 잘못된 수정이 자동 진행되지 않게 한다.

## 1. 증상 고정

- 관찰된 증상을 기대 동작 대비 실제 동작으로 한 문장으로 적는다.
- 재현 맥락을 모은다: 어떤 입력·환경·시점에서 나타나는가, 항상인가 간헐인가.
- 에러 메시지·스택·로그가 있으면 **끝까지** 읽고 지목된 파일·줄·심볼을 기록한다.

## 2. 데이터 흐름 역추적

- 잘못된 값·동작이 **처음 발생하는 지점**까지 코드를 거꾸로 따라 읽는다.
- 다층 시스템이면 어느 경계(layer)에서 값이 어긋나는지 코드 읽기로 격리한다.
- 최근 변경을 검토한다: `git log`·`git diff` 로 증상 영역에 닿은 commit·의존성·환경 차이를 본다.

## 3. 패턴 대조

- 같은 코드베이스에서 **정상 동작하는 유사 지점**을 찾아 끝까지 읽는다.
- 작동하는 것과 깨진 것의 차이를 사소한 것까지 나열한다 — 그 차이가 원인 후보다.

## 4. 가설 수립

- 근본 원인을 "X 가 근본 원인이고 근거는 Y" 형태의 **단일 가설**로 명시한다.
- 가설을 뒷받침하는 증거를 모두 `파일:줄` 참조로 싣는다(정적 증거만 — 실행 결과 아님).
- 후보가 둘 이상이거나 증거가 한 지점을 모호성 없이 가리키지 못하면, 그 자리에 `[NEEDS CLARIFICATION: <구체 질문>]` 마커를 남긴다. "모른다"는 모른다고 적는다.

## 산출

이 절차의 결과(증상·재현 맥락·근본 원인 가설·증거·미해결 마커)는 `spec-diagnosis-section.md` 형판에 담겨 산출 SPEC 의 진단 섹션이 된다. 가설에서 도출되는 수정의 완료 조건은 "버그 미관찰 + 회귀 가드"로 SPEC 완료 조건에 인코딩한다(진입 명령은 `rules/`).

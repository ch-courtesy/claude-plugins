# 범위 분해 게이트 (optimized)

step 3 뒤 사용자 의도가 다중 독립 서브시스템인지 검사한다. 이 게이트는 **추천을 가르지 않고 발행 문서 개수만 결정한다** — 구현 스킬 추천은 개수와 무관하게 항상 dispatch다(SKILL.md step 8).

## 감지 신호

2개 이상이면 다중 가능성이 높다.

- 접속사 다중: "그리고", "+", "and" 등이 서로 다른 명사를 잇는다.
- 명사 영역 다양성: auth/payment/notification/analytics처럼 도메인이 다름.
- 파일 트리 분산: 관련 코드가 3개 이상 최상위 디렉터리에 분산.
- 수용 기준 셋 분리: 부분별 EARS 수용 기준이 서로 독립적이다.

컨텍스트-윈도우 fit 등 런타임 실측이 필요한 분해 기준은 저작 휴리스틱으로만 쓰고, 실제 측정은 실행 측(loop/dispatch)에 잔류시킨다.

## 질문

다중 감지 시 `AskUserQuestion`으로 묻는다.

- (a) 분해 발행: 각 독립 서브시스템마다 별도 SPEC 문서를 **이번 한 호출에서** 발행한다(N개). 단위 간 의존성을 각 문서 frontmatter `depends_on`에 함께 기록한다.
- (b) 단일 강행: 하나의 SPEC 문서로 진행. Risks에 "다중 영역이나 사용자 확인 후 단일 문서 진행" 기록.
- (c) 다른 task로 분리: 현재 호출 abort.

## 발행 규칙

- (a) 선택 시 **한 번의 명확화 인터뷰**로 모든 단위를 수집한 뒤, 단위마다 SPEC 문서를 작성한다(step 6). 각 문서의 frontmatter `depends_on`에 선행 단위 slug를 기록해 단위 간 의존성 메타데이터를 남긴다.
- 분해가 감지되지 않거나 (b)를 고르면 **정확히 하나**의 SPEC 문서를 발행하고 `depends_on` 줄을 제거한다.
- 발행 문서 개수가 1이든 N이든 구현 스킬 추천은 동일하게 dispatch다(step 8).
- (b)는 위양성 대응으로 항상 제공한다.

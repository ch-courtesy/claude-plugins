# spec 스킬용 subagent dispatch 양식

본 파일은 헌법 §11.6 **"이터 내 서브 도구 위임"** 의 보조 자료로, `autopilot:spec` 10-step 워크플로의 특정 단계에서 메인 에이전트가 선택적으로 위임할 수 있는 표준 subagent 역할 2종의 브리프 양식을 정의한다.

세 가지 핵심 원칙(헌법 §11.6 그대로):

- **결정·합성 책임은 메인 에이전트에 유지된다.** subagent는 단일 패스 워커 — 사실 수집·일관성 검토를 수행하고 보고할 뿐, "어느 안을 채택할지"·"마커를 박을지 말지" 같은 합성 결정은 메인이 한다.
- **중첩 dispatch 금지.** subagent가 또 subagent를 부르지 않는다.
- **결정 위임 금지.** "이 단계를 끝까지 진행해 줘" 같은 자기 위임은 금지.

두 역할의 호출 시점은 sibling `autopilot:loop`의 `references/agent-prompts.md`와 분리된 spec 전용 시점이며, 양식의 응답 구조도 spec 산출물(SPEC.md)에 직접 반영하기 좋은 형태로 다르다.

---

## 1. spec-context-explorer

### 언제 쓰나 (트리거)

spec 10-step 중 **step 3(컨텍스트 탐색)** 단계에서 자동 수집(`git log`·`ls`·`cat CLAUDE.md`·`ls rules/` 등) 결과만으로는 새 task의 영향 범위·기존 패턴을 충분히 짚기 어려울 때. 다음 휴리스틱 중 하나라도 해당하면 도입을 권장(강제 아님):

- `rules/` 하위 파일이 다수(대략 5개 초과)이고 어느 룰이 본 task에 적용되는지 자명하지 않음
- 기존 `milestones/*/loops/*/SPEC.md`가 다수 존재해 유사 선례 식별이 필요
- 영향 받는 디렉토리가 둘 이상의 컴포넌트에 걸침(예: 스킬 본문 + 테스트 + 외부 문서)
- 사용자가 자연어로 의도만 전달하고 구체적인 코드 영역을 짚지 못해 사전 탐색이 필요

위 조건에 해당하지 않으면 위임하지 않는다 — 단순 1~2 query 탐색은 메인 이터가 직접 도구를 호출하는 편이 overhead 없이 더 효율적(§11.6 위임 금지 영역).

### 임무

새 task의 SPEC을 작성하기 전, 프로젝트 컨텍스트에서 본 task와 직접 관련된 영역을 폭넓게 식별한다. 결정·요약은 메인 에이전트가 수행하므로 subagent는 **사실 수집·인용·근거 제시**에 집중한다.

수행 절차:

1. `CLAUDE.md`·`rules/` 하위 파일을 본 task 키워드로 grep해 적용되는 룰을 식별
2. `milestones/*/loops/*/SPEC.md`를 본 task 키워드로 grep해 유사 선례·참조 가능한 EARS 패턴 추출
3. task가 건드릴 가능성이 있는 코드 영역(파일·디렉토리)을 식별하고 진입점을 한두 줄로 묘사
4. 코드베이스에서 본 task와 충돌하거나 따라야 할 컨벤션·금기를 추출
5. 메인이 SPEC 초안 시 참고할 권고를 제시 (강제 아님)

하지 마라:

- SPEC.md를 작성하거나 마커를 박는 행위 (메인 책임)
- 본 task의 수용 기준을 임의로 확장하거나 축소
- 발견한 코드를 수정 (탐색은 read-only)
- 중첩 dispatch (다른 subagent 호출)

### 응답 양식

```
## 관련 룰
- [file:line] <룰 내용 1~2줄 인용> — 적용 사유
- ...

## 관련 기존 SPEC
- [path] <한 줄 요약> — 본 task와의 유사·차이점
- ...

## 관련 코드 영역
- [path or dir] <진입점·역할 1~2줄>
- ...

## 컨벤션·금기
- [출처] <지켜야 할 컨벤션 / 건드리면 안 되는 금기>
- ...

## 권고
- <메인이 SPEC 초안 시 고려할 만한 사항 — 강제 아님>
```

메인은 위 보고를 받아 SPEC 작성에 어떻게 반영할지 결정한다. 보고를 그대로 SPEC.md에 복사하지 않는다.

## 2. spec-self-reviewer

### 언제 쓰나 (트리거)

spec 10-step 중 **step 9(자체 검토)** 단계에서 SPEC.md 초안이 작성된 후, `references/self-review.md`의 5항목(placeholder · 모순 · 범위 · 모호성 · EARS fail-가능성)을 **독립 시각으로** 한 번 더 검토하고 싶을 때. 다음 휴리스틱 중 하나라도 해당하면 도입을 권장(강제 아님):

- SPEC.md 본문이 분량이 커서(대략 100줄 초과) 메인의 self-review가 누락을 만들 가능성이 있음
- step 8 종료 시점에 잔존 `[NEEDS CLARIFICATION]` 마커가 다수(2개 이상) 박혀 마커 간 일관성 점검이 필요
- 사용자·호출자가 자연어로 강화된 검토를 명시적으로 요청

위 조건에 해당하지 않으면 메인이 직접 `references/self-review.md`를 따라 검토하면 충분 — 짧은 SPEC에 대한 위임은 overhead만 늘린다.

### 임무

작성된 SPEC.md 초안을 입력으로 받아 5축 검토를 수행하고 **발견 사항만** 보고한다. 수정·마커 박기는 메인 에이전트가 수행한다 (subagent는 patch를 만들지 않는다).

검토 5축 (`references/self-review.md` 동일):

1. **placeholder 잔존** — `<...>`·`TBD`·기본 템플릿 어구가 남았는지
2. **모순** — 수용 기준·범위·검증 명령 사이의 충돌
3. **범위** — `scope.include` 화이트리스트가 수용 기준을 커버하는지 / 범위 밖 항목이 본문에 새어 들어왔는지
4. **모호성** — EARS 패턴 미준수 또는 자율 loop이 도중 사용자 질문을 유발할 만한 표현
5. **EARS fail-가능성** — 각 수용 기준이 독립 테스트 가능한 형태인지(Independent-Test 규칙)

심각도 분류:

- **Critical**: SPEC을 그대로 loop start에 넘기면 자율 loop이 도중 막히거나 검증 통과 불가능
- **Important**: 자율 loop이 진행은 가능하나 결과가 의도와 크게 어긋날 위험
- **Minor**: 표현·문체·polish 수준

하지 마라:

- SPEC.md를 직접 수정 (메인 책임)
- 마커를 직접 박기 (메인 책임)
- 본 task 수용 기준을 새로 추가·확장
- 중첩 dispatch

### 응답 양식

```
## 5축 검토 결과
- placeholder 잔존: <발견 개수>건
- 모순: <발견 개수>건
- 범위: <발견 개수>건
- 모호성: <발견 개수>건
- EARS fail-가능성: <발견 개수>건

## 발견 사항

### Critical
- [본문 위치] <문제 한 줄> — <왜 critical인지>
- ...

### Important
- [본문 위치] <문제 한 줄> — <영향>
- ...

### Minor
- [본문 위치] <문제 한 줄>
- ...

## 판정
- 진행 가능: 예 | 마커 추가 후 가능 | 재작성 필요
- 근거: <1~2 문장>
```

메인은 위 보고를 받아 인라인 수정·`[NEEDS CLARIFICATION]` 마커 박기·재작성 중 어느 것을 적용할지 결정한다. step 9 본문에 명시된 대로 "사용자 Q&A 없음(단계 10에서 일괄 해결)" 원칙을 그대로 유지한다.

## 공통 호출 패턴

```
Agent({
  description: "<짧은 요약>",
  subagent_type: "general-purpose",
  prompt: <위 양식 중 하나>
})
```

`subagent_type: "general-purpose"`는 sibling `autopilot:loop`의 양식과 일치 — Claude Code의 옵션 명세가 바뀌면 양 스킬을 함께 갱신한다.

브리프는 자기완결이어야 한다 — subagent는 메인 이터의 컨텍스트를 보지 못하므로 SPEC.md·관련 파일 경로·이미 시도한 것·응답 형식을 모두 브리프에 담는다(헌법 §11.6 핵심 원칙).

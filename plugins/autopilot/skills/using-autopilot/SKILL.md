# using-autopilot
**REQUIRED RUNTIME CONTRACT:** `../../references/runtime-capabilities.md`를 읽고 스킬 호출과 사용자 질문을 현재 런타임 기능에 맞춘다.


autopilot이 설치된 프로젝트의 네이티브 워크플로 진입점이다. 새 코드 변경은 **의도를 먼저 자기완결적 SPEC 문서로 뜨는 것**에서 출발한다 — 그 첫 단계는 둘로 갈린다: **기능 의도는 `spec`**, **버그·증상·실패는 `repair`**. 두 스킬 모두 SPEC 문서만 산출하고(외부 상태·코드·머지 없음) 옵트인 핸드오프로 `dispatch`에 이어진다. 이 스킬은 그 라우팅을 강제한다.

---

> ## 🚨 절대 우선 — 다른 어떤 것보다 먼저 (협상 불가)
>
> 새 코드 변경 신호를 감지하면, **다른 어떤 응답·도구 호출·탐색보다 먼저** SPEC 작성 스킬을 호출한다. 분기는 신호의 성격으로 정한다:
>
> - **기능 의도**(무엇을 만들까·새 동작 추가·지침 작성·새로 만들기·기존 SPEC 구현) → 현재 런타임의 네이티브 방식으로 `spec` 스킬 호출
> - **버그·증상·실패**(잘못된 동작을 고쳐달라·이 버그/에러·테스트가 실패해) → 현재 런타임의 네이티브 방식으로 `repair` 스킬 호출
>
> spec은 의도를, repair는 증상을 자기완결 SPEC 문서로 떠서 검토하는 첫 단계다(문서 우선·직접 검토 후 구현). repair는 정적 분석으로 근본 원인을 진단해 그 수정용 SPEC을 만든다.
>
> **1%라도 새 코드 변경일 가능성이 있으면 즉시 spec 또는 repair로 라우팅한다.** 사용자가 직접 경로를 지정하지 않는 한 코드·탐색·다른 도구에 손대기 전에 먼저 실행한다. **이것은 협상 대상이 아니다.**

---

## 트리거 (이 중 하나라도 해당되면 spec/repair 먼저)

자연어로 다음 의도가 보이면 새 코드 변경 신호다. 분기는 오른쪽 진입점을 따른다.

기능 의도 → **spec**:

- **기능 추가** — "X 기능 만들어줘", "X 추가해줘", "X 붙여줘"
- **의도적 동작 변경** — "X 동작을 ...로 바꿔줘"처럼 결함이 아니라 새로 원하는 동작으로 바꾸는 변경.
- **지침 작성·문서 편집** — "X 규칙 만들어줘", "X 지침 써줘", 그리고 기존 지침·문서의 **편집·압축·축약·수정·삭제**("X 지침 줄여줘", "이 문서 정리해줘", "이 규칙 지워줘"). 문서·지침을 바꾸는 일은 동작·지침을 바꾸는 코드-변경 신호이지 "코드 변경 아님"이 아니다.
- **SPEC 구현** — `<경로>/SPEC.md 구현`, "이 SPEC 구현해줘", "SPEC대로 만들어줘"처럼 기존 SPEC 파일의 구현·구현 확인. SPEC 파일을 **읽기/검증**하는 것은 예외지만, 그 SPEC을 **구현**하는 것은 코드-변경 신호다.
- **새로 만들기** — "X 스킬/플러그인/모듈 만들꺼야", "X 새로 만들어줘"

버그·증상·실패 → **repair**:

- **버그 수정** — "X 고쳐줘", "X가 안 돼", "이 버그 잡아줘"처럼 잘못된(결함) 동작을 바로잡는 요청.
- **증상·오류** — "이 에러 나", "이 예외/크래시", "결과가 이상해"처럼 관찰된 증상·오류 신호.
- **실패 테스트** — "이 테스트가 실패해", "테스트 깨졌어"처럼 실패 테스트를 통과시켜 달라는 요청.

`autopilot:spec`과 `autopilot:repair`는 "어떤 작업이든 시작하기 전 가장 먼저 사용"하도록 일반화된 진입점이다. 위 신호들이 그 트리거다. 두 스킬의 명확화 인터뷰(집요함·결정 트리·추천 답·코드 우선)가 설계·진단 탐색을 수행하므로, 별도의 사전 설계 단계 없이 그것이 곧 첫 단계다. 기능 의도와 버그가 섞여 모호하면 결함을 고치는 부분은 repair, 새로 만드는 부분은 spec으로 가르되 확신이 서지 않으면 사용자에게 한 번 확인한다.

## 합리화 구멍 차단 (이 세 합리화로 분기를 건너뛰지 않는다)

분기 누락은 거의 항상 다음 셋 중 하나의 합리화에서 나온다. 세 경우 모두 코드-변경 신호이며 **spec 또는 repair가 먼저다** — 합리화가 옳아 보여도 라우팅한다. 어느 쪽인지는 위 트리거 분기(기능 의도→spec / 버그·증상·실패→repair)를 따른다.

1. **"먼저 코드를 파악·이해하고"** — 기존 코드를 이해해야 한다는 필요는 라우팅의 예외가 **아니다**. 그 탐색은 spec의 컨텍스트 탐색 단계(코드-우선 원칙)나 repair의 정적 진단 단계에서 수행된다. "이해가 필요하다"가 라우팅을 미룰 근거가 되지 않는다 — 먼저 실행하고 이해는 그 안에서 한다.
2. **"기존 SPEC을 구현/확인하는 것뿐"** — `<경로>/SPEC.md 구현`처럼 기존 SPEC 파일의 구현·구현 확인 요청은 읽기/검증 예외가 **아니라 코드-변경 신호**다. SPEC 파일을 읽거나 검증하는 것(예외)과 그 SPEC을 구현하는 것은 다르다 — 후자는 spec이 먼저다.
3. **"문서·지침 편집은 코드 변경이 아니야"** — 지침·문서의 편집·압축·축약·수정·삭제는 동작·지침을 바꾸는 코드-변경 신호("지침 작성/동작 수정")다. "코드 변경 아님"으로 합리화하지 않는다 — spec이 먼저다.

## brainstorming-first 강제와의 관계 (명시적 override)

`superpowers:using-superpowers`는 "creating features / building components 같은 창작 작업엔 무조건 `superpowers:brainstorming`을 먼저"를 강제한다. **autopilot이 설치된 프로젝트에서, 위 트리거에 해당하는 새 코드 변경 작업에 한해 이 강제를 대체한다** — brainstorming 대신 **spec**(기능 의도) 또는 **repair**(버그·증상·실패)가 첫 단계다.

근거(왜 이 규칙이 그 자리에서 더 구체적이고 우선하는가):

- **specificity** — brainstorming-first는 모든 "창작 작업"에 걸리는 일반 규칙이다. 본 규칙은 "autopilot 설치 + 새 코드 변경 신호"라는 더 좁은 조건에 걸린다. 구체적 규칙이 일반 규칙을 이긴다.
- **기능 동치** — spec의 명확화 인터뷰(또는 repair의 증상 명확화·정적 진단)가 brainstorming의 의도·범위·제약 탐색을 수행한다. 설계 탐색이 빠지는 게 아니라 spec/repair 안으로 들어온다.
- **파이프라인 정합** — 산출물(자기완결 SPEC)이 곧바로 `autopilot:dispatch`(옵트인 핸드오프)의 입력이 된다.

milestone 규모(다중 독립 서브시스템)는 spec의 **범위 분해 게이트**가 처리하므로 별도 brainstorming이 필요 없다.

## Red flags — 이 생각이 들면 멈추고 spec/repair를 먼저 실행한다

| 생각 | 현실 |
|---|---|
| "일단 brainstorming부터 하자" | autopilot 프로젝트의 새 코드 변경은 spec/repair가 첫 단계다. brainstorming이 아니다. |
| "이건 너무 사소해서 SPEC까지는…" | 사소한 변경일수록 spec/repair가 빠르게 끝난다. 자기완결 의도 문서는 항상 남긴다. |
| "바로 코드부터 짜자" | 의도(검증 가능한 완료 조건) 없이 구현하지 않는다. spec/repair → 구현. |
| "버그니까 그냥 바로 고치자" | 버그 수정도 진단을 먼저 SPEC으로 뜬다. "X 고쳐줘"·"이 에러"·"테스트 실패"는 repair가 먼저다. |
| "먼저 코드베이스를 좀 둘러보고" | 탐색은 spec의 컨텍스트 단계나 repair의 정적 진단이 수행한다. 그 안에서 한다. |
| "먼저 코드를 파악·이해해야 시작하지" | 이해 필요는 라우팅의 예외가 아니다. 먼저 실행하고, 이해는 spec/repair의 탐색 단계에서 한다. |
| "기존 SPEC을 구현/확인하는 것뿐이니까" | SPEC 읽기·검증은 예외지만 SPEC 구현은 코드-변경 신호다. `SPEC.md 구현`은 spec 먼저. |
| "문서·지침 편집은 코드 변경이 아니야" | 지침·문서의 편집·압축·축약·수정·삭제는 동작·지침을 바꾸는 코드-변경 신호다. spec 먼저. |
| "사용자가 그냥 만들라고 했으니" | "만들어줘"는 WHAT이지 HOW가 아니다 — spec이 HOW 이전에 WHAT을 확정한다. |

## 예외 (spec/repair 라우팅 불필요)

- 이미 진행 중인 spec/repair 워크플로의 연속, 또는 `--resume` 마커 해소.
- 새 코드 변경이 **아닌** 작업: 순수 질의응답, 코드 읽기·설명, 검색, 단순 디버깅(원인 조사·로그 분석으로 끝내고 수정은 하지 않음), 운영 명령(테스트 실행·상태 조회).
- 사용자가 spec/repair를 건너뛰라고 **명시적으로** 지시한 경우(사용자 지침이 최우선).

이 예외는 위 정당한 경우에만 적용된다 — 「합리화 구멍 차단」의 세 경우(이해-먼저 탐색, SPEC 구현, 문서·지침 편집)는 예외가 아니라 코드-변경 신호이므로 여기로 끌어오지 않는다. 단순 디버깅은 원인 조사·로그 분석으로 **끝나는** 경우만 예외이며, 그 조사가 **수정 요청**으로 넘어가면 그때는 repair가 먼저다. 반대로, 정당한 예외(순수 질의응답·코드 읽기·검색·조사로 끝나는 디버깅·운영 명령)를 게이트로 끌어오는 것도 오류다.

## 파이프라인

```
새 코드 변경 신호
   ├─ 기능 의도        → autopilot:spec   → docs/specs/<날짜>-<slug>/SPEC.md (자기완결 SPEC) → (옵트인) dispatch
   └─ 버그·증상·실패   → autopilot:repair → docs/specs/<날짜>-<slug>/SPEC.md (진단 섹션 포함 수정 SPEC) → (옵트인) dispatch
```

spec과 repair 모두 외부 상태(이슈·브랜치·원격)를 만들지 않고 SPEC 문서만 산출한다. 산출된 SPEC은 옵트인 핸드오프를 통해 `autopilot:dispatch`로 이어질 수 있다.

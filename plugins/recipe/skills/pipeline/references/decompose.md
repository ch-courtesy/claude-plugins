# 분해 기준

- 노드 하나는 **입출력 계약 하나로 서술되는 일** 하나다. 계약을 한 문장으로 못 적으면 과병합 — 쪼갠다(입력 하나로 무관한 출력 셋을 내는 계약이 그 예다). 과분해는 **그 스킬을 단독으로 불러도 의미가 있는지**로 판정한다 — 사람이 직접 불렀을 때 아무 쓸모가 없는 계약은 앞뒤와 한 단계로 묶는다(합치기는 별도 연산이 아니라 재분해다). 선형 체인에서 출력이 다음 구성 요소로만 가는 것은 정상이다
- 승인 화면의 수정 요청이 구성을 바꾸면 그 해석은 2단계 재분해뿐이다 — 그 자리부터 다시 돈다
- 도구를 실행하거나 판단이 필요한 일은 **노드**로. LLM이 조건을 판정해야 하면 판정을 수행해 값을 내는 계획 노드로 두고, transform 다중 출력이 그 값으로 가른다 — 실행 중에 그래프에 없는 갈래를 만들지 않는다
- 값 가공(거르기·뽑기·잇기)은 **transform 식**으로. 개수는 식 중간 비교(`size(x) == 0`)로만 쓴다 — 개수 자체를 포트 값으로 내야 하면 노드로. 깊이만 벗기는 출력도 입력과 이름을 달리 짓는다
- 반복은 **컨테이너**로 — 병렬 가능하면 항목 규칙, 순차·수렴이 필요하면 조건 규칙에 `carry`. 다단계 루프 본문은 별도 워크플로로 컴파일해 노드로 감싼다
- 실패를 다뤄야 하면 실패를 `ok{bool}` 같은 **값**으로 내는 노드로 표현하고 transform으로 대안 경로를 배선한다
- 처리하면서 대상이 늘어나는 형태는 그래프가 맡지 않는다 — 목록을 뽑는 노드 하나가 배열을 내면 컨테이너가 돈다
- 부수효과의 선후는 order 엣지로. 회차 직렬화는 조건 컨테이너로
- **포트 값은 자기완결이어야 한다** — 소비자가 실행 환경(cwd 등) 없이 그대로 쓸 값을 낸다. 경로면 전체 경로를 내고, 결합이 필요하면 transform 식이나 계약 설계(두 입력)로 그래프에 명시한다

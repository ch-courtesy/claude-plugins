    worktree_dir: { shape: text }

## 입력
- `worktree_dir` — 글이 있는 저장소(또는 worktree) 전체 경로. 리뷰어가 블로그 규칙 문서(`AGENTS.md`·`CLAUDE.md`·글쓰기 규칙)를 여기서 읽는다
- `post_path` — 리뷰할 글 파일 전체 경로. 없으면 오류로 끝낸다
- `materials_dir` — (선택, 원소 0~1개 배열) 자료 폴더 전체 경로. 사실 대조와 첨부 내용 확인의 근거. 없으면 자료 대비 사실 관점은 글 안의 근거와 공개 자료로만 본다
- `reviewer` — 쓸 CLI. `codex`, `claude`, `agy` 중 하나. 글을 쓴 모델과 다른 회사 모델을 고른다

## 실행
`recipe:oneshot` 스킬의 래퍼로 한 번 실행한다. 리뷰어는 글을 쓴 세션과 컨텍스트를 공유하지 않는다. 호출하는 쪽의 결론(이 글이 좋다/나쁘다, 이미 찾은 문제)을 프롬프트에 넣지 않는다 — 넣으면 리뷰어가 그 결론을 확인해 주는 쪽으로 기운다.

1. **준비.** 실행마다 새 임시 디렉터리(`mktemp -d`)를 만들어 프롬프트·stdout·stderr 파일을 그 안에 둔다. 여러 리뷰가 병렬로 돌므로 고정 파일 이름을 공유하면 서로 덮어쓴다. 프롬프트 파일은 BOM 없는 UTF-8 로 쓴다.
2. **글 원문을 빠짐없이 넘긴다.** 프롬프트 끝에 글 파일 원문 전체를 `<<<POST` … `POST>>>` 로 붙인다. 공개 페이지 HTML 을 텍스트로 뽑아 넘기지 않는다 — 링크 주소가 빠져 "다운로드 링크가 없다" 같은 거짓 지적이 나온다(2026-11-13 agy 리뷰에서 실제로 났다). 읽기 명령이 막혀도 원문으로 리뷰하게 한다.
3. **프롬프트에 담을 내용.**
   - 역할: 그 분야 현업 10년차 이상 시니어 리뷰어. 수정하지 말고 지적만. 기준은 "이 글을 시니어가 자기 이름으로 내도 되는가"
   - 읽을 것: `post_path`, `worktree_dir` 의 블로그 규칙 문서와 최근 글 2개, `materials_dir`(있으면. zip 은 내용 목록만), 글에 링크된 첨부·스크립트 소스
   - 관점 여덟 — **앞의 셋이 가장 중요하다.** 문장 다듬기 지적은 이 셋을 다 본 뒤에 한다
     1. **쓸모(usefulness)** — 누가 어떤 검색어로 이 글에 오는가. 그 독자가 이 글로 문제를 실제로 푸는가. 같은 검색어의 검색 결과 첫 쪽(웹 검색으로 확인)보다 나은 것이 있는가. 작성자 쪽 내부 운영 기록을 독자가 쓸 수 있는 판단으로 바꾸지 않고 늘어놓았으면 P1. 쓸모가 없다고 보면 고칠 안 대신 "다시 씀/내림"과 이유를 적는다
     2. **독자 위험(risk)** — 관리자 권한, 앱·시스템 파일 교체, 보안 기능 우회(실행 정책 Bypass 등), 제3자·서명 없는 실행 파일, 약관에 걸릴 수 있는 조작, 데이터 덮어쓰기, 구버전 고정을 시키는가. 시킨다면 조작마다 위험과 되돌리기 방법을 적었는가. 배포 파일의 출처를 독자가 검증할 수 있는가(해시는 손상 확인일 뿐 안전성 증명이 아니다). 첨부 스크립트 소스를 읽고, 두 번 실행·다른 빌드로 재실행·복원을 두 번 할 때 원본이 지워지거나 덮어써지는 경로가 없는지 본다
     3. **단정 일치(claims)** — 제목·요약 표·소제목·마무리의 단정 수준이 본문 근거와 같은가. 본문은 추정인데 마무리가 단정하면 P1. 한 환경·한 버전에서 본 것을 일반화했는가. 대안 가설을 배제하지 않은 원인 단정이 있는가
     4. **절차 재현성(repro)** — 명령을 쓰인 그대로 실행하면 되는지(폴더 이동, 상대 경로, 압축 구조), 앞 명령의 산출물이 뒤 명령·스크립트가 읽는 위치에 놓이는지(스크립트 소스에서 확인), 단계마다 받는 곳·성공 확인법·흔한 실패 분기가 있는지
     5. **다운로드 검증(download)** — 글에 있는 다운로드 링크를 실제로 받아 본다. 응답 코드, 받은 파일 크기·해시가 글의 표와 같은지, 서버가 압축 전송(gzip)하거나 리다이렉트해 브라우저와 curl 결과가 다른지. 큰 파일(200MB 넘음)은 헤더만 본다
     6. **자료 대비 사실(fact)** — 자료에 근거가 없거나 범위를 넘는 단정. 해시·크기·날짜·개수 같은 값은 자료 파일에서 직접 계산해 대조. 공식 동작에 대한 주장은 공식 문서로 확인하고 출처를 적는다
     7. **저장소 규칙(rules)** — 프론트매터 필수 항목, 길이, 카테고리/태그 관례(최근 글들과 대조), 소제목 형식(질문형·문장형 금지), 문체 규칙
     8. **링크(link)** — 문서 안 앵커는 대상 제목에서 생성기 규칙(Hugo: 소문자, 공백→하이픈, 문장부호 제거)으로 만든 ID 와 대조, 외부 링크 응답, 이미지 alt
   - 호출자가 "다운로드·첨부 실행 검증은 별도 시험이 맡았다"고 했으면 관점 5와 관점 2의 스크립트 재실행 부분은 빼고, 나머지에 집중한다
   - 출력 형식: JSON 배열만. 항목은 `{"severity": "P1"|"P2"|"P3", "category": "usefulness"|"risk"|"claims"|"repro"|"download"|"fact"|"rules"|"link", "location": "줄 번호나 소제목", "issue": "...", "evidence": "확인한 방법과 결과(명령·출력·출처 URL)", "suggestion": "..."}`. 지적이 없으면 `[]`
   - 심각도: P1 = 독자가 손해를 보거나(원본 손실, 보안), 문제를 못 풀거나, 글이 거짓을 말함. P2 = 막히거나 오해할 수 있음. P3 = 다듬기
   - 확인하지 못한 것은 지적으로 만들지 않고 `"category": "fact", "severity": "P3", "issue": "확인 못 함: ..."` 로 남긴다. 추측을 사실처럼 쓰지 않는다
4. **실행.** `bash <oneshot 스킬 디렉터리>/references/oneshot.sh --mode read --prompt-file <프롬프트 파일> <reviewer>` 를 `worktree_dir` 에서 실행한다. `<oneshot 스킬 디렉터리>` 는 설치된 recipe 플러그인의 가장 높은 버전 경로다(`ls -d ~/.claude/plugins/cache/*/recipe/*/skills/oneshot | sort -V | tail -1`). 다운로드 검증·웹 검색이 필요하므로 codex 는 네트워크가 되는 읽기 모드여야 한다. 네트워크가 막혀 관점 1·5를 못 봤으면 리뷰어가 그 사실을 `확인 못 함` 항목으로 남기게 한다
5. 종료 코드 0 또는 3(강등 — stdout 에 결과 있음)이면 stdout 에서 JSON 배열을 뽑는다. 그 밖이거나 JSON 이 아니면 한 번 다시 실행하고, 그래도 실패하면 `{"severity": "P1", "category": "rules", "location": "-", "issue": "<reviewer> 리뷰 실패: <요약>", "evidence": "", "suggestion": "다른 리뷰어로 대체"}` 하나를 낸다
6. 각 항목에 `"reviewer": <reviewer>` 를 붙인다
7. 1의 임시 디렉터리는 성공·실패와 관계없이 지운다


### 이 관점들이 생긴 이유
- 쓸모: 2026-11-13 사실·문장만 보는 리뷰가 "독자에게 전혀 도움이 안 되는" 글(작성자 회사의 내부 운영 기록)을 통과시켰다. 같은 글을 쓸모부터 물은 리뷰 둘은 "다시 씀"을 냈다
- 독자 위험·단정 일치·다운로드: 같은 날 7.5~8.5점을 받은 좋은 글에서도 세 벤더가 공통으로 짚은 문제가 이 셋이었다 — 설치 스크립트를 다시 실행하면 원본 백업이 지워지는 경로, "본인 책임" 한 줄뿐인 위험 안내, 본문은 추정인데 마무리는 단정, curl 로 받으면 압축본이 저장돼 해시가 어긋나는 다운로드 링크

## 출력
- `findings` — 지적 객체 배열(`severity`·`category`·`location`·`issue`·`evidence`·`suggestion`·`reviewer`). 지적이 없으면 빈 배열

node:
  in:
    worktree_dir: { shape: text }
    post_path: { shape: text }
    findings: { shape: json, list: 1, required: false }
  out:
    clean: { shape: bool }
---

## 입력
- `worktree_dir` — 글이 있는 worktree 전체 경로. 사이트 공통 파일(CSS 등) 수정이 필요할 때 이 안에서만 고친다
- `post_path` — 고칠 글 파일 전체 경로
- `findings` — 지적 배열. 여러 리뷰어의 지적이 이어 붙어 온다(중복 가능)

## 실행
1. 같은 위치·같은 내용의 지적을 하나로 합친다. 서로 다른 리뷰어가 같은 문제를 짚었으면 합친 지적에 리뷰어를 모두 남긴다(여러 벤더가 함께 짚은 문제는 우선순위를 올린다)
   - 처리 순서: `usefulness`(쓸모) P1 → `risk` → `claims` → 나머지. 쓸모 지적이 "다시 씀/내림"이면 문장 지적을 반영하지 말고 사용자 판단으로 올린다 — 내릴 글을 다듬는 데 시간을 쓰지 않는다
2. 지적마다 근거를 직접 확인한다(글·저장소 규칙·자료 폴더). 확인 결과로 셋 중 하나로 가른다:
   - 반영 — 근거가 맞고 고칠 방법이 하나로 정해진다
   - 사용자 판단 — 고칠 방법이 여럿이거나, 글 범위를 넘는 변경(사이트 공통 CSS·다른 글)이거나, 내용 방향을 바꾼다. 묶어서 AskUserQuestion 으로 묻는다
   - 기각 — 근거가 틀렸거나 이미 반영돼 있다. 이유를 기록한다. 리뷰어가 받은 입력 때문에 생긴 오판(예: 링크가 빠진 텍스트를 받아 "링크 없음"이라 함)도 기각하되, 입력을 만든 쪽의 문제로 따로 적는다
   - 첨부 스크립트 버그(`risk`·`repro`)는 글이 아니라 첨부를 고친다. 고친 뒤 `attachment-test` 를 다시 돌려 통과해야 반영으로 친다. 첨부를 다시 만들면 글의 해시 표도 함께 고친다
3. 반영할 것을 고친다. 커밋하지 않는다
   - **작성자가 하지 않은 일을 작성자 목소리로 쓰지 않는다.** 리뷰어·첨부 시험이 확인한 사실(예: "스크립트를 두 번 실행해도 원본이 남는 것을 확인했습니다")을 글에 넣을 때, 작성자가 직접 한 것처럼 쓰면 글이 거짓 경험을 말하게 된다. 확인 주체가 작성자가 아니면 문장을 넣지 말고 사용자 판단으로 올리거나, 작성자에게 직접 확인해 달라고 요청한다
   - 작성자만 아는 사실(빌드 도구 버전, 겪은 상황)이 필요한 지적은 지어내지 않고 사용자 판단으로 올린다
4. 반영 내역(반영·기각·보류와 이유)을 사용자에게 보고한다

## 출력
- `clean` — 이번 회차에 실제로 고친 것이 없으면(지적이 비었거나 전부 기각) `true`, 하나라도 고쳤으면 `false`

node:
  in:
    post_path: { shape: text }
    attachments_dir: { shape: text, list: 1, required: false }
  out:
    findings: { shape: json, list: 1, required: false }
---

## 입력
- `post_path` — 글 파일 전체 경로. 다운로드 링크, 해시 표, 독자에게 시키는 명령을 여기서 읽는다
- `attachments_dir` — (선택, 원소 0~1개 배열) 첨부 원본(배포 zip, 스크립트, 소스)이 있는 폴더. 없으면 글의 링크에서 내려받은 것으로 시험한다

## 실행

### 왜 실제로 돌리나
글을 읽기만 하는 리뷰는 "명령이 쓰인 대로 동작하는가"까지는 보지만, 독자가 같은 스크립트를 두 번 돌리거나 직접 빌드한 파일로 다시 돌렸을 때를 보지 못한다. 2026-11-13 세 벤더가 평가한 글에서, 설치 스크립트가 "현재 파일 해시 = 이번에 넣을 파일 해시"로만 이미 설치됐는지 판단해, 글이 권한 대로 소스를 직접 빌드해 다시 실행하면 원본 백업(`.old`)을 지우고 대체 파일로 덮어쓰는 경로가 발견됐다. 독자는 원본을 잃고 `-Restore` 도 소용이 없게 된다. 이런 결함은 실행해야 보인다.

### 절차
모든 시험은 격리해서 한다. 실제 설치 폴더, 실제 레지스트리, 사용자 데이터에 쓰지 않는다. 관리자 권한이 필요한 시험은 경로를 인자로 바꿀 수 있을 때만 하고(예: `-InstallDir`), 바꿀 수 없으면 "확인 못 함"으로 남긴다.

1. **대상 목록.** 글에서 다음을 뽑는다.
   - 다운로드 링크(클릭 링크와 코드 블록 안 URL), 글에 적힌 크기·해시
   - 독자가 실행하는 스크립트와 그 인자, 스크립트가 바꾸는 파일·폴더
   - 첨부에 소스가 있으면 빌드 명령과 산출물 위치
2. **다운로드 시험.** 링크마다:
   - `curl -sSL -D <헤더파일> -o <파일>` 로 받고 응답 코드, `Content-Type`, `Content-Encoding`, 최종 URL(리다이렉트)을 적는다
   - 크기와 SHA256 을 계산해 글의 값과 대조한다. 다르면 `--compressed` 로 다시 받아 대조해 원인이 압축 전송인지 가른다(브라우저는 풀어서 저장하고 curl 은 그대로 저장한다)
   - 한 번 실패하면 한 번 더 받아 본다(아카이브 서버는 간헐적으로 404 를 낸다). 두 번 결과가 다르면 그것도 지적한다
   - 200MB 넘는 파일은 헤더만 보고 "본문 대조 생략"으로 적는다
   - 서명이 있는 파일(Windows: `Get-AuthenticodeSignature`)은 서명 상태를 적는다
3. **압축 구조.** zip 을 풀었을 때 최상위 폴더가 있는지 본다. 없으면 탐색기 '모두 압축 풀기'(zip 이름 폴더를 만들어 줌)와 7-Zip·반디집 '여기에 풀기'(현재 폴더에 흩어짐)의 결과가 달라, 글의 `cd` 경로가 한쪽에서 틀린다. 글이 어느 쪽을 가정하는지와 맞춰 본다.
4. **스크립트 시험.** 독자가 실행하는 스크립트마다 임시 폴더에 가짜 설치 폴더를 만든다.
   - **원본 역할 파일은 가능하면 진짜 원본을 쓴다.** 글이 안내하는 설치 파일(MSI 등)을 이미 받았으면 설치하지 말고 관리 추출(`msiexec /a <msi> /qn TARGETDIR=<임시 폴더>`)이나 압축 해제로 원본 파일을 꺼낸다. 진짜 원본은 서명·버전 정보가 있어, 스크립트가 원본을 무엇으로 판별하는지(해시, 서명, 버전)를 실제 조건으로 시험할 수 있다. 꺼낼 수 없을 때만 내용이 서로 다른 더미 파일을 쓰고 그 사실을 적는다. 해시는 시작 전에 적어 둔다.
   - 스크립트가 관리자 권한 확인으로 바로 멈추면, 그 확인 줄만 주석 처리한 **사본**으로 시험하고 원본 스크립트는 그대로 둔다. 무엇을 바꿨는지 보고에 적는다. 다음 시나리오를 차례로 돌리고, 매 단계 뒤 폴더 상태(파일 목록, 해시)를 기록한다.
   - S1 처음 설치: 원본이 백업되고 대체 파일이 들어가는가
   - S2 같은 파일로 다시 설치: 아무것도 바뀌지 않는가(멱등)
   - S3 다른 대체 파일로 다시 설치(글이 권하는 직접 빌드, 새 버전 배포본을 흉내 냄): **처음 원본의 해시가 어딘가에 그대로 남아 있는가**
   - S4 복원: 처음 원본으로 돌아가는가
   - S5 복원을 한 번 더: 오류로 멈추고 아무것도 지우지 않는가
   - S6 대상 파일이 없거나 경로가 다른 경우: 멈추고 알리는가
   - 글이 안내하는 다른 경로(예: 업데이트 뒤 다시 적용)가 있으면 그 시나리오를 더한다
   - 처음 원본의 해시가 어느 단계에서든 사라지면 P1 이다
   - 결함을 찾으면 고친 사본을 만들어 같은 시나리오를 다시 돌리고, 통과한 수정안을 지적의 `suggestion` 에 넣는다. 시험하지 않은 수정안은 "시험 안 함"으로 표시한다
5. **빌드 시험.** 첨부에 소스와 빌드 명령이 있고 빌드 도구가 있으면 글의 명령 그대로 빌드해, 산출물이 글이 말한 위치에 생기는지, 배포본과 기능상 같은지(내보내는 함수 목록 등) 본다. 도구가 없으면 "확인 못 함".
6. **제3자 도구.** 글이 독자에게 실행시키는 다른 사람의 도구(패처, 설치기, 유틸리티)는 실행하지 말고 받아서 본다: 어느 릴리스·파일인지, 해시(릴리스 페이지의 digest 와 대조), 서명 유무, 필요한 권한, 무엇을 바꾸는지(소스·README), 바꾸기 전에 백업하는지. 실제 설치를 고치는 도구는 가짜 폴더로 돌릴 수 없으면 실행하지 않는다. 글이 이것들을 알리는지 대조한다.
7. **정적 점검.** 스크립트 소스에서 네트워크 접근, 다른 프로세스 실행, 설치 폴더 밖 쓰기, 실행 정책·보안 설정 변경을 찾아 적는다. 글이 이를 독자에게 알렸는지 대조한다.
8. 임시 폴더는 끝나면 지운다. 실패한 시나리오가 있으면 재현에 쓴 명령과 상태 기록은 지우지 말고 경로를 보고한다.

## 출력
- `findings` — 지적 배열. 항목은 `{"severity": "P1"|"P2"|"P3", "category": "risk"|"repro"|"download", "location": "소제목·스크립트 이름·URL", "issue": "...", "evidence": "시나리오, 실행한 명령, 전후 해시", "suggestion": "...", "reviewer": "attachment-test"}`. 시험할 첨부·링크가 없으면 빈 배열
- 사용자에게는 시나리오별 통과/실패 표와 다운로드 대조 표를 보여 준다

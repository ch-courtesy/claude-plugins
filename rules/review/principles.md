# 리뷰 지침

리뷰(코드·변경·PR·설계·문서·최적화 등 무엇이든)를 수행할 때 따르는 공통 원칙입니다. 무엇을 리뷰하든 판정의 신뢰도와 일관성을 보장하기 위한 최소 규율이며, 특정 도메인에 종속되지 않습니다.

## 9원칙

1. **판정 전 사실 확정 (ground truth first).** 추정으로 리뷰하지 않는다. 대상의 정확한 범위, 기준선(baseline) 대비 diff, 이력과 의도(이전 결정이 무엇을 정했는지, 이것이 초안·아카이브·활성본 중 무엇인지), 소비 방식(누가/무엇이 읽거나 파싱하는지)을 먼저 확인한다.

2. **구속 기준을 명명하고, 그것이 목표를 이긴다.** 모든 변경에는 목표(기능·수정·최적화)가 있지만, 양보 불가한 제약(정확성·동작 보존·계약·보안·발견성)이 함께 있다. 목표와 제약이 충돌하면 제약이 이긴다. 그 기준을 리뷰 서두에 명시한다.

3. **위험도(blast radius)에 비례해 정밀도를 둔다.** 리뷰 대상을 소비 방식·영향 범위로 분류한다 — 항상 로드/실행되는 것(시스템 프롬프트·매 호출 메타데이터), 기계가 파싱하는 것(구조·정확 문자열이 잠긴 데이터), 공개 계약·인터페이스, 내부 산문. 영향이 크거나 계약·잠금이 걸린 부분을 가장 세게, 내부 산문을 가장 가볍게 본다. 실행 코드와 산문 지침을 구분한다.

4. **신뢰하지 말고 검증한다.** 제안된 변경에 대해 테스트·검증 수단을 실제로 실행한다(필요하면 격리 환경에서). 불변식·계약·권한·잠금 문자열이 살아남았는지 grep 등으로 확인한다. 변경이 만들어 낸 dangling 참조(삭제된 절을 가리키는 참조 등)를 찾는다. 주장이 아니라 관찰된 증거로 말한다.

5. **테스트 통과 ≠ 정확.** 자동 검사는 일부만 덮는다. 무엇이 테스트로 커버되지 *않는지*(시스템 프롬프트·산문 계약·UX·행동 규율 등)를 명시하고 그 부분은 수동으로 평가한다.

6. **의도된 구조와 군더더기를 구분한다.** 반복·장황함은 종종 의도적이다(강화, overview↔detail, defense-in-depth). "중복처럼 보인다"가 load-bearing 강화를 제거할 근거가 되지 않는다. 제거를 권하기 전에 *왜* 존재하는지 이해한다.

7. **발견은 구체적·위치 명시·심각도 분류.** "X가 삭제된 Y를 참조하여 dangling"처럼 정확한 파일·증상·이유로 적는다. 막연한 불안은 금지. 블로커(적용 전 필수 수정)와 nit(선택·저위험)을 분리하고, 헤드라인 판정(안전 / 주의 / 차단)을 먼저 낸다.

8. **커버리지·확신을 정직하게 보고한다.** 무엇을 직접 검증했고 무엇을 표본·추정으로 갈음했는지 밝힌다. 거짓 완전성(false completeness)을 연기하지 않는다. 확신의 강도를 증거에 맞춘다.

9. **재리뷰 = 지적 항목 재확인 + 검증 재실행.** 수정본을 다시 볼 때 "고쳤다"는 말을 믿지 않는다. 지적했던 항목이 실제로 해소됐는지, 그리고 그 수정이 다른 것을 깨뜨리지 않았는지(테스트 재실행)를 확인한다.

## 이 프로젝트에서

- 리뷰 작업 시작 전 관련 카테고리 지침(`rules/`)을 먼저 읽는다.
- 자동 검증 수단(테스트·CI·linter)이 있으면 변경에 대해 실제로 실행해 판정 근거로 삼는다.
- 사용자 입력이 필요한 결정·승인·선택·해명 요청은 프로젝트의 사용자 상호작용 규칙이 있다면 그에 따른다. 리뷰 판정 자체는 근거를 제시해 작성한다.

# Claude Code 동적 워크플로우 — 리서치 & 벤치마크

> 작성일 2026-06-03 · 대상: Claude Code 네이티브 **Workflow 도구** + **`/loop` dynamic 모드** · 모델: claude-opus-4-8[1m]
> 이 문서는 외부 도구(Workflow 런타임)의 동작을 조사·실측한 리서치다. 이 repo의 autopilot 워크플로는 대비용으로만 다룬다.

## 0. TL;DR

- **동적 워크플로우 = JS 스크립트로 서브에이전트를 대규모 오케스트레이션하는 백그라운드 런타임.** Claude가 task 설명을 받아 스크립트(`agent()`/`parallel()`/`pipeline()`/`phase()`/`log()`)를 쓰고, 격리 환경에서 실행하며, **최종 결과만 대화 컨텍스트로 복귀**한다. v2.1.154(2026-05-28) 리서치 프리뷰.
- **실측 헤드라인 (8개 파일 추출, N=8 × 5전략 × 2회):**
  - **동시성이 거의 공짜 속도다** — 순차 8에이전트(70s) → 병렬 8에이전트(17.7s), 토큰 거의 불변. **벽시계 ~4배 단축.**
  - **`pipeline()`(무배리어)이 `parallel()`+배리어보다 빠르다** — 동일 작업·토큰에서 단계 배리어 대비 ~17% 단축.
  - **토큰 비용은 에이전트 수에 거의 비례한다** — 에이전트별 컨텍스트(시스템 프롬프트) 오버헤드가 지배. 1/8/16 에이전트 = ~33k/128k/263k 토큰.
  - **품질은 작업 난이도에 종속** — 쉬운 추출에선 80/80 정답, 팬아웃·검증 단계가 정확도를 바꾸지 않음. 검증 패턴의 값은 더 모호·고위험 작업에서 나온다.
- **선택 규칙**: 독립 작업이 많고(수십~수백) 중간 산출이 컨텍스트를 더럽히면 Workflow. 단계 사이 사람 개입이 필요하거나 몇 개뿐이면 일반 서브에이전트/agent-team.

집계표: [`benchmark/results/summary.md`](./benchmark/results/summary.md) · 원시 데이터: [`benchmark/results/runs.jsonl`](./benchmark/results/runs.jsonl)

## 1. Workflow 도구 — 메커니즘

### 1.1 정체와 실행 모델

동적 워크플로우는 **JavaScript 스크립트가 서브에이전트들을 오케스트레이션**하는 기능이다. 사용자가 task를 설명하면 Claude가 스크립트를 작성하고, 전용 런타임이 **대화와 분리된 격리 환경**에서 백그라운드로 실행한다. 중간 결과는 Claude의 컨텍스트가 아니라 **스크립트 변수**에 머물고, 오직 최종 답만 세션으로 돌아온다 — 이것이 "수백 파일을 읽어도 컨텍스트가 안 터지는" 핵심이다.

- 실행은 background-async: 워크플로 실행 중에도 메인 세션은 자유롭고, 완료 시 `<task-notification>`으로 통지된다. `/workflows`로 라이브 진행을 본다.
- 모든 런의 스크립트는 세션 디렉토리(`~/.claude/projects/...`) 아래 파일로 저장되고, 그 경로가 런 시작 시 반환된다 → 읽기·diff·편집 후 재실행 가능.

**실측 확인:** 본 벤치의 10개 런 모두 launch 즉시 task ID를 반환하고 백그라운드 실행됐으며, 완료 알림이 `duration_ms`·`subagent_tokens`·`agent_count`와 스크립트 반환값(`<result>`)을 격리 측정해 돌려줬다.

### 1.2 동시성 모델

- **동시 에이전트 상한**: `min(16, CPU코어-2)`. 그 이상은 큐잉돼 슬롯이 나면 실행.
- **총 에이전트 백스톱**: 런당 1,000개(런어웨이 방지). 실제 워크플로 규모를 훨씬 상회하는 안전장치.
- `parallel()`/`pipeline()`에 100개를 넘겨도 모두 완료되지만 동시 실행은 ~상한 개수.

**실측 확인:** S2(8 에이전트)는 17.7s, S3/S4(16 에이전트)는 34~42s. 8개는 동시 상한 내라 단일 wave로 거의 동시 처리됐고, 16개도 상한(min(16,…))에 걸려 단계별로 흘렀다.

### 1.3 resume / 저널링

- 런타임이 **각 `agent()` 결과를 진행하며 저널링** → 중단·편집 후 재개 시 **완료된 에이전트는 캐시 결과를 즉시 반환**하고 미완·신규만 라이브 실행.
- `Workflow({scriptPath, resumeFromRunId})`. **동일 세션 한정**(Claude Code 종료 시 런 상태 소실, 다음 세션은 fresh).
- 동일 스크립트+동일 args → 100% 캐시 히트. 편집한 첫 `agent()` 호출과 그 이후만 재실행.

### 1.4 structured output / 격리 / 모델 / budget

- **structured output**: `agent(prompt, {schema})`로 JSON Schema를 주면 서브에이전트가 강제로 구조화 출력을 내고, 검증은 도구 호출 계층에서 일어나 불일치 시 모델이 재시도. → 파싱 불필요, 본 벤치의 신뢰성 기반.
- **worktree 격리**: `{isolation:'worktree'}`. 에이전트가 파일을 병렬 변경해 충돌할 때만(비쌈). 본 벤치는 읽기 전용이라 미사용.
- **모델 오버라이드**: `{model}`로 단계별 모델 라우팅. 기본은 세션 모델 상속(대개 정답). 약한 단계만 작은 모델로 내리는 게 비용 최적.
- **budget**: `budget.total`(사용자의 "+500k" 타깃, 없으면 null)·`budget.spent()`(이번 turn의 출력 토큰, 메인루프+모든 워크플로 공유)·`budget.remaining()`. 동적 루프(`while budget.remaining()>…`)·정적 스케일(`Math.floor(total/100k)`)에 사용.

### 1.5 `parallel()` vs `pipeline()` — 배리어의 비용

| | `parallel(thunks)` | `pipeline(items, s1, s2, …)` |
|---|---|---|
| 세만틱 | **배리어** — 모든 thunk 완료까지 await | **무배리어** — 아이템이 단계를 독립적으로 통과 |
| 다단계 시 | 단계 N은 단계 N-1 **전부** 끝나야 시작 | 아이템 A가 stage3에 있는 동안 B는 stage1 가능 |
| 벽시계 | sum(단계별 가장 느린 항목) | 가장 느린 단일-아이템 체인 |
| 언제 | 단계 N이 N-1의 **전체** 결과를 교차 참조(dedup/merge/early-exit) | 그 외 거의 전부의 다단계 작업 (기본값) |

핵심: 단계별 항목 처리 시간에 편차가 있으면, 배리어는 빠른 항목들을 가장 느린 항목이 끝날 때까지 놀린다. pipeline은 끝나는 대로 다음 단계로 흘려보낸다. **본 벤치 S3 vs S4가 이 차이를 실측**(아래 §4).

## 2. `/loop` dynamic 모드 (정성)

`/loop`는 번들 스킬(v2.1.72+). 입력 형태로 동작이 갈린다:

| 입력 | 동작 |
|---|---|
| 인터벌 + 프롬프트 (`/loop 5m /foo`) | **고정 cron** 스케줄 (`CronCreate`, 5필드 식) |
| 프롬프트만 (`/loop /foo`) | **dynamic / self-paced** |
| 없음 | 내장 유지보수 프롬프트, dynamic 페이싱 |

**일반(고정) vs dynamic의 차이:**

| | 고정 인터벌 | dynamic |
|---|---|---|
| 다음 실행 | cron 식대로 **항상 같은 간격**, 상태 무관 | **매 반복 끝에 모델이 다음 delay를 직접 선택**(1분~1시간) |
| 근거 | 사용자가 준 값 | 관찰된 활동 — 빌드/PR 진행 중이면 짧게, 유휴면 길게. delay와 **이유를 매 반복 출력** |
| 종료 | 취소(`CronDelete`)/7일 만료까지 | task가 확실히 끝나면 **다음 wakeup을 안 잡아 스스로 종료** 가능 |
| 내부 | `CronCreate` | ScheduleWakeup식 자가 스케줄(cron 아님), `Monitor` 직접 사용도 가능 |

**캐시-윈도우 고려(도구 명세 기준, 공개 문서엔 미기재):** 프롬프트 캐시 TTL이 5분이라 delay 선택에 트레이드오프가 있다 —
- `60~270s`: 캐시 유지. 외부 상태(CI·배포·원격 큐)를 적극 폴링할 때.
- `300~3600s`: 캐시 미스 감수. 더 일찍 볼 이유가 없을 때 / 유휴 / 긴 fallback 하트비트.
- **`300s`(정확히 5분)는 최악** — 미스를 감수하면서 amortize도 안 됨. "5분 쉬자" 충동은 270s(캐시 유지) 또는 1200s+(한 번의 미스로 긴 대기 구매)로.
- 유휴 틱 기본값은 1200~1800s 권장.

> Bedrock·Vertex·Foundry에서는 인터벌 없는 `/loop`가 자가페이싱 대신 **고정 10분**으로 동작.

**Workflow 도구와의 대비:** Workflow는 *공간적* 팬아웃(한 번에 많은 에이전트, 배리어/파이프라인) 오케스트레이터다. `/loop` dynamic은 *시간적* 자가페이싱(언제 다시 깰지) 단일 흐름이다. 전자는 "지금 병렬로 얼마나", 후자는 "다음에 언제". 본 리서치 범위상 `/loop`는 실측하지 않았다(자가페이싱이 분~시간 단위라 표준 벤치 비용 대비 가치 낮음).

## 3. Workflow vs 다른 위임 수단

| | 서브에이전트(Agent/Task) | agent-team | **동적 워크플로우** | autopilot(이 repo) |
|---|---|---|---|---|
| 계획 보유 | Claude, turn 단위 | 리드 에이전트 | **스크립트** | SKILL.md(프롬프트) |
| 결과 위치 | 메인 컨텍스트 | 공유 task 리스트 | **스크립트 변수** | `.fsd/`·`.dispatch/` 상태 파일 |
| 규모 | turn당 몇 개 | 소수 장기 peer | **수십~수백/런** | wave 단위 |
| 반복 가능 단위 | 워커 정의 | 팀 정의 | **오케스트레이션 자체** | DAG/SPEC |
| 중단 복구 | turn 재시작 | 팀원 계속 | **동일 세션 resume** | 상태 파일 기반 |
| 컨텍스트 비용 | 결과가 메인에 복귀 | 중간 | **낮음(최종만)** | 낮음(CLI 서브프로세스) |
| 구동 | 모델 | 모델 | **JS 런타임** | bash + `claude --print` |

**언제 Workflow:** 한 대화가 조율 못 할 만큼 에이전트가 많음(수십~수백) / 오케스트레이션을 재사용·검사 가능한 스크립트로 / 적대적 교차검증·다각도 초안 같은 품질 패턴 / 중간 산출이 컨텍스트를 더럽히면 안 됨.
**언제 일반 서브에이전트:** turn당 몇 개의 위임, turn-by-turn 조종이 필요, 교차검증 불필요.
**언제 agent-team:** 공유 task 리스트로 소통하는 장기 peer들을 계획·배정·감독.

> 대비: 이 repo의 autopilot(fsd/dispatch/loop)은 **bash + `claude --print` 서브프로세스로 Claude가 Claude를 부르는** 프롬프트 구동 메타루프다. JS `agent()`/`parallel()` 프리미티브가 없다. 네이티브 Workflow는 같은 "팬아웃 위임" 문제를 **런타임 프리미티브**로 푼다 — 결정적 제어흐름(루프·조건·팬아웃)이 스크립트에 있고, 토큰·동시성·resume를 런타임이 관리.

## 4. 벤치마크

### 4.1 방법론

**Task(고정·재현·ground truth):** 8개 `SKILL.md`에서 `{skillName, subcommands[], purpose}`를 structured output(schema 강제)으로 추출. 성공 = `skillName` 일치 **AND** `subcommands` 집합 일치(`purpose`는 채점 제외). 전체 정의·정답표: [`benchmark/task.md`](./benchmark/task.md).

**전략 5종**(각 스크립트 [`benchmark/strategies/`](./benchmark/strategies/)):

| 전략 | 구조 | 분리하는 변수 |
|---|---|---|
| S0 Monolith | 1 에이전트가 8개 전부 | 팬아웃 안 함 베이스라인 |
| S1 Serial | per-file 8 에이전트, 순차 await | 동시성 없음 |
| S2 Parallel | `parallel(8)` 배리어 | 동시성 효과 |
| S3 Pipeline | `pipeline(extract, verify)` 무배리어 | pipeline 스트리밍 |
| S4 Parallel-2stage | `parallel(extract)`→배리어→`parallel(verify)` | 배리어 비용 |

**측정**(런타임 격리값을 1차로): `duration_ms`(벽시계), `subagent_tokens`(총 토큰), `agent_count`. 스크립트는 `budget.spent()` delta(출력 토큰)와 아이템을 반환. 전략당 2회, **순차 실행**(경합 방지). 측정 한계는 §5.

### 4.2 결과 (평균)

| 전략 | agents | 벽시계(ms) | 총 토큰 | 출력 토큰 | 성공 |
|---|---:|---:|---:|---:|---:|
| S0 Monolith | 1 | **22,450** | **33,124** | 2,961 | 100% |
| S1 Serial | 8 | **69,987** | 127,052 | 2,779 | 100% |
| S2 Parallel | 8 | **17,725** | 128,228 | 3,373 | 100% |
| S3 Pipeline | 16 | **34,752** | 263,169 | 6,516 | 100% |
| S4 Parallel-2stage | 16 | **41,648** | 263,192 | 6,519 | 100% |

### 4.3 분석

**(a) 동시성이 핵심 레버 — S1→S2.** 동일 작업·동일 토큰(127k↔128k)인데 벽시계 **69,987 → 17,725ms = 3.95× 단축**. 독립 작업에서 `parallel()`/`pipeline()`은 토큰을 거의 늘리지 않고 시간만 단축한다 — "거의 공짜 속도". (8개가 동시 상한 16 안이라 사실상 단일 wave. 항목 수가 상한을 넘으면 단축비는 ⌈N/상한⌉에 수렴.)

**(b) 무배리어 > 배리어 — S3 vs S4.** 동일 2단계·동일 토큰(~263k)인데 **pipeline 34,752 vs barrier 41,648ms — pipeline ~16.6%(≈6.9s) 빠름**. extract 항목 간 시간 편차가 있어, 배리어(S4)는 가장 느린 extract가 끝날 때까지 모든 verify를 막는다. pipeline(S3)은 각 extract가 끝나는 대로 verify로 흘린다. 편차가 클수록 격차는 더 커진다.

**(c) 토큰 비용 ∝ 에이전트 수.** 총 토큰은 에이전트별 컨텍스트(시스템 프롬프트·도구 정의 등) 오버헤드가 지배: 1/8/16 에이전트 = ~33k/128k/263k로 거의 선형. **출력 토큰 자체는 작다**(3~7k) — 즉 팬아웃의 비용은 "생성량"이 아니라 "에이전트마다 새 컨텍스트를 세우는 고정비"다. 모놀리스(S0)가 토큰 ~4배 싼 이유이자, 작은 작업을 굳이 팬아웃하면 안 되는 이유.

**(d) 품질은 작업 난이도에 종속.** 80개 아이템 추출 전부 `skillName`+`subcommands` 정답(100%). verify 단계(S3/S4)가 정정한 건 cosmetic `purpose` 1건뿐, subcommand 오류는 0. **이 난이도에선 팬아웃이 품질을 떨어뜨리지도, 검증 단계가 정확도를 올리지도 않았다.** 검증·적대적 교차검증 패턴의 값은 더 모호하고 고위험인 작업(버그 헌팅, 설계 판단)에서 나온다 — 쉬운 결정적 추출에 얹으면 비용만 2배.

### 4.4 결론 — 무엇을 언제

- **독립 항목 N개를 처리** → `parallel()`/`pipeline()`. N>동시상한이면 시간은 ⌈N/상한⌉ wave로, 토큰은 N에 선형으로 증가.
- **다단계** → 기본 `pipeline()`. 단계 N이 N-1의 **전체** 결과(dedup·merge·early-exit)를 봐야 할 때만 배리어(`parallel`).
- **작업이 작거나(몇 개) 한 컨텍스트에 충분** → 팬아웃 말고 모놀리스 1 에이전트(토큰 ~4배 절약).
- **품질 패턴(검증/다각도)** → 작업이 모호·고위험일 때만. 쉬운 결정적 작업엔 비용만 추가.
- **비용 관리** → 작은 슬라이스로 먼저 spend 가늠 → 약한 단계는 `{model}`로 작은 모델 라우팅.

## 5. 측정 한계 / 공개 문서 vs 추론 구분

**측정 한계:**
- 벽시계는 런타임 `duration_ms`(워크플로별 격리)를 썼다 — 외부 `date`보다 깨끗하나 모델·API 지연으로 런마다 ±5~10% 흔들린다. 본 벤치는 절대치가 아니라 **방향성**(S2<S1, S3<S4)을 본다.
- `budget.spent()`(출력 토큰)는 turn 전역 풀 공유라 메인루프 활동에 오염될 수 있어 2차 참고용. **총 토큰은 격리된 `subagent_tokens`** 사용.
- N=8, 2회 반복은 분산 추정엔 작다. 신뢰구간이 필요하면 반복을 늘려야(철저 규모).
- 단일 머신·단일 모델(opus-4-8) 측정. 동시 상한은 코어 수에 의존하므로 다른 환경에선 절대치가 달라진다.

**공개 문서 vs 추론(claude-code-guide 조사 기준):**
- **공개 문서**: 기능 정체(JS 스크립트 오케스트레이터), 백그라운드 격리 실행, 동시 16/총 1000 상한, 세션 내 resume·완료 에이전트 캐시, 비용/모델 가이드, 가용 버전(v2.1.154), `/loop` dynamic 범위(1분~1시간)·`CronCreate`/`CronList`/`CronDelete`, Workflow/서브에이전트/agent-team 비교표.
- **공개 문서 미기재 / 도구 명세·동작에서만 확인**: 스크립트 API 표면(`agent()`/`parallel()`/`pipeline()`/`phase()`/`log()`/`budget`/`workflow()`)의 정식 레퍼런스, `pipeline` vs `parallel`의 명시적 배리어 세만틱, `resumeFromRunId` 같은 API 파라미터명, `{schema}` structured output 옵션, 캐시-윈도우 기반 delay 선택 가이드("ScheduleWakeup"이라는 도구명 포함). 본 벤치는 이 중 다수를 **실측으로 교차확인**(8/16 에이전트 동시성, pipeline<barrier, schema 강제 출력, budget.spent() delta)했다.

# spec 시각 컴패니언 (visual companion)

## 무엇을 만들 것인가

spec 스킬의 명확화 인터뷰에, 화면·레이아웃·구조처럼 글보다 그림으로 볼 때 더 잘 판단되는 질문에서 사용자에게 **경량 정적 시각 미리보기(목업·구조 도식)**를 보여주는 옵트인 보조 기능("시각 컴패니언")을 추가한다. 컴패니언은 인터뷰를 돕는 도구일 뿐이며, 사용자의 선택·결정은 spec의 기존 명확화 흐름으로 확정되어 SPEC 문서의 확정 텍스트(완료 조건·제약)에 캡처된다. 보여준 시각물은 인터뷰가 끝나면 버린다.

## 목적 (왜)

spec의 명확화 인터뷰는 지금 텍스트 질문만으로 진행되어, 화면 레이아웃·구조 같은 시각적 주제에서는 사용자가 선택지를 머릿속으로 그려 비교해야 하는 부담이 있다. 시각 미리보기를 곁들이면 이런 질문에서 사용자가 더 빠르고 정확하게 판단해, UI·구조 성격의 작업에서 산출 SPEC의 품질이 올라간다.

## 완료 조건

- 인터뷰에 시각적 주제(화면·레이아웃·구조)가 예상될 때, spec은 시각 컴패니언 사용 여부를 **다른 내용과 섞지 않은 단독 1회 제안 메시지**로 사용자에게 묻는다.
- 사용자가 컴패니언을 거부하거나 제안 자체가 없으면, spec은 시각물 없이 텍스트 인터뷰만으로 진행한다.
- 컴패니언이 켜진 동안에도, spec은 질문마다 "글보다 그림이 더 나은가"를 판단해 시각이 도움이 되는 질문에서만 시각물을 보여주고 나머지는 텍스트로 묻는다.
- 시각물을 보여줄 때, spec은 라이브 서버·실시간 통신·브라우저 클릭 수집 없이 **정적 시각물(예: 터미널 텍스트 도식, 또는 사용자가 직접 여는 정적 파일)**만 사용한다.
- 시각물을 보여준 질문이라도, 사용자의 최종 선택은 spec의 기존 명확화 질문으로 받아 SPEC 문서의 확정 텍스트(완료 조건·제약)에 반영하며, 시각물 자체는 인수 기준이 되지 않는다.
- 인터뷰가 끝나면, spec이 만든 시각물·임시 파일은 폐기되어 SPEC 디렉토리·저장소에 남지 않고, 컴패니언은 task·이슈·브랜치·원격 등 어떤 외부 상태도 만들지 않는다.
- 자율 오케스트레이터가 호출했거나 사용자가 화면을 열 수 없는 비대화·헤드리스 맥락이면, spec은 컴패니언을 제안하지 않고 텍스트 인터뷰만 진행한다.
- spec의 SKILL.md에는 컴패니언의 계약(언제 제안·언제 켜고·산출물 위계)만 두고, 렌더링·파일 위치 같은 메커니즘 세부는 spec의 보조 문서(references) 한 곳에만 서술한다.

## 범위

포함:
- spec 명확화 인터뷰에 시각 컴패니언의 옵트인 제안과 질문별 시각/텍스트 판단을 배선한다.
- 컴패니언을 spec 스킬 내부의 자기완결 모듈로 구현한다(SKILL.md 계약 + references 메커니즘 가이드, 필요 시 경량 정적 렌더 보조).
- 경량 정적 렌더 방식으로 시각물을 제시한다.
- 활성화를 사람 대화 경로로 한정하고 자율·헤드리스 맥락에선 비활성으로 둔다.

비-목표 / 제외:
- superpowers brainstorming Visual Companion 코드(라이브 HTTP/WebSocket 서버·frame-template 등) 포팅 — 하지 않는다.
- 라이브 서버·실시간 통신·브라우저 클릭 수집·events 파일.
- 시각 아티팩트의 영속화(`.superpowers/brainstorm/` 류 디렉토리, SPEC 디렉토리 내 시각물 보존).
- brainstorm·review 등 다른 스킬로의 배선(향후 별도 작업).
- 별도 최상위 스킬(`visual-spec`/`visual-companion`) 신설.
- 구현 방법의 세부 결정 — 정적 렌더의 구체 형식·파일 배치 등은 구현 단계(autopilot:loop)가 정한다.

## 검증

이 SPEC의 인수 바는 위 **완료 조건**이다. 각 조건이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을 실행하는 진입 명령은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약

- **HOW는 비운다:** 이 SPEC은 무엇을(WHAT) 만들지만 규정하고 구체 구현 방법은 autopilot:loop에 위임한다. 단 아래 경계는 제약으로 고정한다.
- **경량 정적 한정:** 렌더링에 라이브 HTTP 서버·WebSocket·브라우저 클릭 events 수집을 쓰지 않는다.
- **산출물 위계:** 권위 산출물은 SPEC.md의 확정 텍스트(완료 조건·제약)뿐이다. 시각물은 인터뷰 보조이며 폐기 대상이고 인수 기준이 아니다.
- **계약 보존:** spec의 "외부 상태 무생성 / SPEC 문서만 산출" 계약을 보존한다.
- **패키징:** 컴패니언은 spec 스킬 내부에 구현하며 별도 최상위 스킬로 분리하지 않는다. 단 나중에 다른 스킬이 재사용할 수 있도록 spec 본체(SKILL.md 계약)와 분리된 자기완결 모듈로 둔다.
- **문서 중복 금지:** SKILL.md는 계약 수준만 담고 메커니즘은 references 한 곳에 둔다(단일 출처).
- **활성화 경계:** 사람 대화 경로 한정. 자율 오케스트레이터·헤드리스 맥락에선 제안하지 않는다.
- **제안 형태:** 옵트인 제안은 다른 내용과 섞지 않은 단독 메시지로 1회 한다.

## 위험

- 경량 정적 렌더는 brainstorming의 실시간 클릭-선택 UX를 제공하지 못한다 — 선택은 기존 명확화 질문으로 받으므로 인터랙티브 목업의 즉시성은 포기한다(의도된 트레이드오프).
- 정적 시각물을 사용자가 보는 방식(터미널 ASCII vs 정적 파일 열기)은 환경마다 달라, 구현 시 환경 도달성을 고려해야 한다.
- spec 인터뷰에 제안 단계가 늘어 경량 스킬의 단순성이 약간 희생된다 — 옵트인 + 질문별 판단으로 기본 텍스트 경로를 그대로 유지해 완화한다.

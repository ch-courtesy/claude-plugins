# context rules directory split and spec-time task creation

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->
프로젝트의 컨텍스트 관리 지침을 **두 관심사로 분리**하고, 단일 파일이 아니라 **디렉토리 구조**로 관리한다. 그리고 워크플로우 지침에 **"스펙 작성 시점의 task 정합"** 절차를 추가해, 지금까지 비어 있던 공백 — SPEC 문서가 막 작성된 순간에는 동기화할 task가 아직 없을 수 있다는 — 을 메운다.

- 컨텍스트 관리 지침을 **데이터 모델(구현체)** 관심사와 **워크플로우** 관심사 두 개의 분리된 지침으로 제공한다. 영속성·handoff라는 상위 프레이밍은 보존한다.
- 데이터 모델 관심사: 백엔드 매핑(태스크↔이슈 매핑, 이슈 body 구조, 상태 어휘). 이것이 시스템 전역에서 참조하는 "백엔드 매핑 단일 출처" 역할을 그대로 승계한다.
- 워크플로우 관심사: 태스크 우선 원칙(no-task-no-work), 작업 시작 신호, 상태 전이, 운영 규칙.
- 워크플로우 관심사에 신규 절을 둔다: **SPEC 문서가 최초로 작성된 직후, 호출자/오케스트레이터(SPEC 작성 주체 자신은 제외)가 대응 task의 존재를 확인하고 없으면 그 SPEC 내용으로 task를 생성·정합한다.** 생성·정합 분기와 body 동기화 절차의 단일 출처는 별도 orchestration 지침임을 명시한다.
- 위 분리로 경로가 달라지므로, "백엔드 매핑 단일 출처"를 가리키던 **라이브 규약 참조**들을 분리된 데이터 모델 지침으로 재지정한다.
- 컨텍스트 지침을 생성하는 **프로젝트 초기화 생성기**도 새 디렉토리 구조(백엔드별 데이터 모델 + 워크플로우 두 문서)를 산출하도록 맞춘다.

## 수용 기준 (EARS)
<!-- EARS 5패턴과 언어 규칙은 references/ears-patterns.md. 각 기준은 관찰 가능하고 독립 검증 가능해야 함. -->
- 시스템은 컨텍스트 관리 지침을 **데이터 모델 지침**과 **워크플로우 지침** 두 개의 분리된 문서로 제공해야 하며, 분리 이전의 단일 통합 문서는 더 이상 존재하지 않아야 한다.
- 데이터 모델 지침은 영속성·handoff 프레이밍과 백엔드 매핑(태스크↔이슈 매핑, 이슈 body 구조, 상태 어휘)을 포함해야 한다.
- 워크플로우 지침은 no-task-no-work 원칙, 작업 시작 신호, 상태 전이, 운영 규칙을 포함해야 한다.
- When SPEC 문서가 최초로 작성되면, the system shall 워크플로우 지침을 통해 "호출자/오케스트레이터(SPEC 작성 주체 제외)가 대응 task 존재를 확인하고 없으면 그 SPEC 내용으로 task를 생성한다"는 절차를 규정해야 한다. 그 절차는 생성·정합·동기화의 단일 출처가 orchestration 지침임을 명시해야 한다.
- 백엔드 매핑 단일 출처를 가리키던 모든 라이브 규약 참조는 분리된 **데이터 모델 지침**을 가리켜야 하며, 분리로 삭제된 단일 통합 문서를 가리키는 라이브 참조는 (제외 대상을 빼고) 하나도 남지 않아야 한다.
- When 프로젝트 초기화 생성기가 컨텍스트 지침을 생성하면, the system shall 선택된 백엔드에 대해 데이터 모델 지침과 워크플로우 지침 **두 문서를 디렉토리 구조로** 산출해야 한다.
- If 생성기가 기록하려는 컨텍스트 지침 문서가 이미 존재하면, the system shall 덮어쓰지 않고 차이를 보여 사용자에게 확인을 요청해야 한다.

## 범위
포함:
- 컨텍스트 관리 지침의 디렉토리 분할(데이터 모델 / 워크플로우 두 문서).
- 워크플로우 지침에 "스펙 작성 시점 task 정합" 절차 신설.
- "백엔드 매핑 단일 출처"를 가리키는 **라이브** 규약 참조 갱신(자율 실행 스킬·드라이버, 그리고 그 어휘에 정렬된 테스트 주석).
- 프로젝트 초기화 컨텍스트 생성기와 그 백엔드 템플릿을 디렉토리 산출 구조로 재작성(기존 덮어쓰기 금지·차이 확인 안전장치 보존).

비-목표 / 제외:
- orchestration 카테고리의 task 상태 정합·이슈 body 동기화 두 지침 파일의 이동·정합 — 사용자가 직접 수행(본 SPEC은 두 파일을 변경하지 않는다).
- 완료된 milestone 기록과 문서 아카이브의 경로 갱신(과거 기록 보존).
- `CLAUDE.md` 변경.
- task 백엔드 자체나 실제 task 생성 실행(본 SPEC은 지침·생성기 정의만 다룬다).

## 검증
<!-- 검증 기준의 단일 출처는 위 "수용 기준 (EARS)"다. 검증을 실행하는 진입 명령(테스트·lint·빌드)은 SPEC이 선언하지 않는다. -->
이 SPEC의 인수 바는 위 **수용 기준 (EARS)**이다. 각 기준이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을 실행하는 진입 명령은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약
- 분리된 데이터 모델 지침은 기존 "백엔드 매핑 단일 출처" 역할을 그대로 승계해야 한다(규약 참조의 의미 보존).
- 컨텍스트 카테고리의 디렉토리화는 카테고리 도출·잔여 카테고리 판정 로직이 이미 지원하는 디렉토리형 카테고리 규약을 따른다 — 해당 오케스트레이션 로직은 변경하지 않고 검증만 한다.
- 분리 후 삭제되는 단일 통합 지침 문서를 가리키는 라이브 참조가 남지 않아야 한다(dangling 금지).
- 기존 회귀 테스트의 의미(상태 어휘 정렬 등)는 보존되어야 한다.

## 위험
- **orchestration 정합 의존(후속 필수)**: 신규 워크플로우 절은 task 생성 시점을 "SPEC 작성 직후"로 규정하지만, 본 SPEC이 건드리지 않는 task 상태 정합 지침은 생성 시점을 "구현 단계"로 규정한다. 두 시점이 정합되지 않으면 지침 간 모순이 남는다 — 사용자의 후속 orchestration 이동/수정에서 일치시켜야 한다.
- **다중 영역 단일 문서**: 본 변경은 컨텍스트 룰·자율 실행 스킬·프로젝트 초기화 생성기 등 여러 영역에 걸치지만, 사용자가 승인한 단일 계획에 따라 하나의 SPEC으로 진행한다(분해 게이트 (b) 단일 강행).
- **다운스트림 규약 변경**: 컨텍스트 지침을 디렉토리로 바꾸는 것은 다운스트림 프로젝트가 따르는 규약을 바꾼다. 생성기 갱신이 함께 이뤄지지 않으면 신규 부트스트랩 프로젝트와 규약 참조가 불일치한다 — 본 SPEC이 생성기 갱신을 함께 포함해 완화한다.

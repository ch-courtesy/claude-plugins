# spec 명확화 인터뷰 자연화·자동화 핸드오프

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->

`autopilot:spec` 스킬의 명확화 인터뷰를 "정해진 칸(목적·성공기준·제약·위험)을 차례로 채우는" 방식에서 **사용자의 첫 문장에서 출발해 점점 깊이 파고들고 옆으로 파생되는 깔때기형 대화**로 전면 재설계한다. 동시에 세 가지를 함께 바꾼다.

1. **자연스러운 인터뷰** — 인터뷰는 사용자가 처음 한 말을 되짚는 데서 시작해, 직전 답에서 다음 질문이 파생되는 단일 흐름으로 진행한다. 목적·성공기준·제약·위험은 사용자에게 나열해 묻는 질문 카테고리가 아니라, 대화가 그 영역들을 충분히 짚었는지 확인하는 **내부 커버리지 체크리스트**로만 쓴다.

2. **쉬운 용어** — 사용자·SPEC 문서에 노출되는 어려운 용어(특히 "EARS")를 쉬운 말로 바꾼다. "수용 기준 (EARS)" 라벨은 **"완료 조건"**으로 바꾸고, 5가지 문장 패턴은 평이한 설명("항상 / …할 때 / …인 동안 / …이면(오류) / …기능이 켜지면")으로 안내한다. 검증 가능한 기준이라는 **내부 구조 자체는 그대로 유지**한다 — dispatch가 중간 질문 없이 검증할 수 있는 자기완결성은 보존된다.

3. **검토의 인터뷰 흡수** — 별도의 "섹션별 SPEC 승인" 단계(현 step 5)를 제거한다. 각 영역의 검토는 인터뷰가 진행되며 이해를 점진적으로 되짚어 확인하는 것으로 대체하고, 완성된 SPEC 전체를 **마지막에 한 번** 보여주고 승인받는다.

4. **자동화 핸드오프(옵트인)** — 인터뷰가 미해결 항목 없이 깨끗이 끝나고 사용자가 SPEC을 승인하면, "구현까지 자동으로 진행할까요?"를 구조화 질문으로 묻고, 사용자가 동의한 경우에 한해 구현 스킬(`autopilot:dispatch`)을 호출한다. 미해결 항목이 남아 자율 실행이 차단되는 경우에는 이 제안을 하지 않고 해결 방법을 안내한다.

5. **계약 테스트 정합** — 위 변경은 spec 스킬의 구조 계약을 정적으로 단언하는 기존 계약 테스트(`tests/autopilot/test-spec-skill.sh`, `tests/autopilot/test-skill-install.sh`)와 충돌한다(8단계 골격·"섹션별 SPEC" 문자열·"EARS" 마커 단언). 이 테스트들을 신 계약(섹션별 승인 제거로 줄어든 워크플로 단계 수, "완료 조건" 라벨, 옵트인 핸드오프)에 맞게 **정합 갱신**한다. 단언을 삭제·skip·약화하지 않고 신 계약을 동등한 강도로 단언하도록 재작성한다.

## 완료 조건
<!-- 각 기준은 관찰 가능하고 독립 검증 가능해야 함. -->

### 자연스러운 인터뷰
- 명확화 인터뷰는 사용자의 최초 진술을 되짚는 첫 질문으로 시작하며, 고정된 카테고리 목록(목적·성공기준·제약·위험)을 사용자에게 나열해 제시하지 않아야 한다.
- 두 번째 이후의 각 질문은 직전 답에서 파생(더 깊이 파고들거나 옆으로 분기)되어야 하며, 선행 답이 후속 질문을 가지치기해야 한다.
- 목적·성공기준·제약·위험은 사용자 대면 질문 슬롯이 아니라 인터뷰 커버리지를 점검하는 내부 체크리스트로만 기술되어야 한다.
- 모든 질문은 한 번에 한 주제씩 `AskUserQuestion`(추천 답을 첫 선택지)으로 전달되며, 자유 텍스트 질문 종결구는 쓰지 않아야 한다.

### 쉬운 용어
- 사용자에게 노출되는 어떤 질문·문구·SPEC 문서 본문에도 "EARS"라는 약어가 등장하지 않아야 한다.
- SPEC 문서의 수용 기준 섹션 제목은 "완료 조건"이어야 한다.
- 5가지 문장 패턴은 어려운 영문 용어(Ubiquitous/Event-driven 등) 대신 평이한 한국어 안내로 제시되어야 한다.
- 각 완료 조건은 여전히 관찰 가능한 결과를 담고 독립적으로 테스트 가능해야 한다(내부 검증 구조 보존).

### 검토의 인터뷰 흡수
- 섹션을 하나씩 따로 승인받는 단계가 더 이상 존재하지 않아야 한다.
- 인터뷰가 잠정 종결되면 완성된 SPEC 전체를 한 번 제시하고 단일 승인을 받아야 한다.

### 자동화 핸드오프(옵트인)
- SPEC이 미해결 명확화 마커(spec 스킬이 미결 항목에 남기는 마커) 없이 작성되고 사용자가 최종 승인하면, 구현까지 자동 진행할지를 `AskUserQuestion`으로 물어야 한다.
- 사용자가 자동 진행에 동의하면 `autopilot:dispatch`가 작성된 SPEC 경로(들)로 호출되어야 한다.
- 사용자가 동의하지 않으면 어떤 후속 스킬도 호출하지 않고 SPEC 경로와 다음 단계 안내만 남기고 종료해야 한다.
- SPEC에 미해결 항목 마커가 남아 있으면 자동 진행 제안을 하지 않고, 자율 실행이 차단된다는 사실과 `--resume` 해결 방법을 안내해야 한다.

### 계약 테스트 정합
- 모든 spec 계약 테스트(`tests/autopilot/test-spec-skill.sh`, `tests/autopilot/test-skill-install.sh`)가 신 계약 기준으로 통과해야 한다(exit 0).
- 계약 테스트는 "섹션별 SPEC" 승인 단계의 부재와 줄어든 워크플로 단계 수를 단언해야 한다(이전의 "섹션별 SPEC 존재 + 8단계" 단언을 대체).
- 사용자 노출 문구의 "EARS" 마커 부재와 "완료 조건" 라벨의 존재를 단언해야 한다(이전의 "EARS 마커 존재" 단언을 대체).
- 어떤 계약 테스트도 삭제·skip되거나 단언이 약화되지 않아야 한다(정합 갱신이지 커버리지 축소가 아니다).

## 검증
<!-- 검증 기준의 단일 출처는 위 "완료 조건"이다. 검증을 실행하는 진입 명령(테스트·lint·빌드)은 SPEC이 선언하지 않는다. -->
이 SPEC의 인수 바는 위 **완료 조건**이다. 각 조건이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을 실행하는 진입 명령은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약
- 기존 단일 출처 원칙을 유지한다: 인터뷰 방법론은 `clarification.md`, 검증 기준은 SPEC의 완료 조건, 진입 명령은 `rules/`가 각각 단일 출처다. 한 개념을 여러 파일에 복제하지 않는다.
- 평이화는 **사용자·문서 노출 용어**에 한정한다. 검증 가능한 기준의 내부 구조(관찰 가능·독립 테스트 가능)는 보존하며, 자기완결 SPEC이 dispatch가 중간 질문 없이 수행 가능해야 한다는 요건을 약화하지 않는다.
- 자동 핸드오프는 **반드시 사용자 옵트인**(명시적 동의)으로만 발동한다. 동의 없는 자동 dispatch 호출은 금지한다. 이는 기존 "후속 스킬을 자동 호출하지 않는다"는 원칙에 대한 유일하게 허용되는 예외이며, 그 예외 경계(미해결 마커 없음 + 최종 승인 + 명시 동의)를 스킬 문서에 명시한다.
- 모든 결정·승인·다음 단계 질문은 `AskUserQuestion`으로 받는다. 자유 텍스트 질문 종결구는 금지한다.
- 단일 SPEC으로 발행한다(세 면이 SKILL.md를 공유 편집하는 한 명충적 재설계이므로 분할하지 않는다).

## 위험
- 평이화 과정에서 "EARS" 약어를 사용자 노출 문구에서만 제거해야 하는데, 내부 구조 설명까지 함께 지워 검증 가능성 안내가 약해질 위험. → 완료 조건의 "내부 검증 구조 보존" 항목으로 가드.
- 자동 핸드오프 도입이 spec의 "외부 상태를 만들지 않는다"는 정체성과 충돌할 수 있음(dispatch는 worktree·run 등 외부 상태를 만듦). → 옵트인 경계를 제약으로 명시해, spec 자체는 여전히 상태를 만들지 않고 사용자 동의 시에만 외부 스킬로 위임하도록 한정.
- 카테고리 슬롯 제거로 인터뷰 커버리지(특정 영역 누락)가 떨어질 위험. → 내부 커버리지 체크리스트와 기존 clarity 점수 리드아웃으로 보완.

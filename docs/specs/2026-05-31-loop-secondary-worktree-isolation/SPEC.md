# loop 보조 워크트리 모드의 per-SPEC 격리 보장

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->

autopilot 자율 실행기(loop)의 "보조 워크트리 모드" 판정을 정교화해, **그 모드가 오직 "현재 작업 위치가 바로 이 SPEC을 위해 의도적으로 마련된 워크트리일 때"만 발동**하도록 한다. 그 외의 경우에는 SPEC마다 격리된 작업 공간·신호 영역을 갖는 기본(전용 워크트리) 모드로 동작해야 한다.

### 배경: 무엇이 잘못됐나

현재 loop의 보조 워크트리 모드는 "현재 작업 위치가 git 워크트리인가"라는 **위치 사실만** 보고 발동한다. 그래서 오케스트레이터(dispatch)가 **자신이 어떤 워크트리 안에서 실행되는 상황에서** 여러 SPEC을 자식으로 병렬 위임하면, 모든 자식이 같은 작업 위치를 물려받아 전부 보조 모드로 진입하고 **같은 작업 공간과 같은 신호 영역을 공유**한다. 이로부터 두 가지 데이터 유실이 실제로 발생했다:

1. **공유 작업 공간 충돌** — 같은 차수(wave)에서 병렬 실행된 두 자식이 동일한 작업 트리에 동시에 작업·커밋해, 한쪽의 산출물이 통합되지 못하고 유실됐다.
2. **공유 신호 오판** — 신호 영역이 공유되므로, 먼저 끝난 자식이 남긴 완료 신호가 영역에 누적되고, 나중에 시작한 자식이 시작 직후 "신호 영역이 비어 있지 않음"을 자신의 종료(terminal)로 오인해 **아무 작업도 하지 않고 즉시 종료**했다. 오케스트레이터는 이를 완료로 오판했다.

### 무엇을 보장해야 하나

- 보조 워크트리 모드는 **현재 작업 위치가 처리 대상 SPEC을 위해 의도적으로 마련된 워크트리일 때에만** 발동한다. 단순히 "현재 위치가 어떤 워크트리"라는 사실만으로는 발동하지 않는다.
- 위 조건이 아니면, loop은 그 SPEC 전용의 격리된 작업 공간과 격리된 신호 영역(SPEC 디렉토리 하위)을 사용한다 — 이는 오케스트레이터의 실행 위치(워크트리 안이든 밖이든)와 무관하다.
- 그 결과, 한 오케스트레이션 안에서 여러 SPEC이 병렬 위임돼도 자식들이 작업 공간·신호 영역을 공유하지 않으며, 한 자식의 누적 신호가 다른 자식의 종료 오판을 일으키지 않는다.
- 정당한 단일 사용 사례(사용자가 하나의 워크트리에서 그 워크트리의 대상 SPEC 하나를 직접 돌리는 경우)는 종전대로 보조 모드로 동작한다 — 이 변경은 그 사례를 깨뜨리지 않는다.

이 변경은 loop의 정의 파일 한 곳에 한정한다. 오케스트레이터(dispatch)·spec·기타 스킬은 건드리지 않는다.

## 수용 기준 (EARS)
<!-- EARS 5패턴과 언어 규칙은 references/ears-patterns.md. 각 기준은 관찰 가능하고 독립 검증 가능해야 함. -->

1. While 현재 작업 위치가 처리 대상 SPEC을 위해 의도적으로 마련된 워크트리일 때, 시스템은 보조 워크트리 모드로 동작해 그 위치를 작업 공간으로 재사용한다.
2. If 현재 작업 위치가 워크트리이긴 하나 그것이 처리 대상 SPEC을 위해 마련된 워크트리가 아니면, 시스템은 보조 모드로 진입하지 않고 그 SPEC 전용의 격리된 작업 공간을 사용한다.
3. When loop이 격리된 작업 공간을 사용할 때, 시스템은 그 SPEC의 신호 영역을 그 SPEC 디렉토리 하위에 두어 다른 SPEC의 신호 영역과 분리한다.
4. When 한 오케스트레이션이 여러 SPEC을 병렬로 위임해 각각 loop으로 실행할 때, 시스템은 어떤 두 SPEC도 같은 작업 공간이나 같은 신호 영역을 공유하지 않게 한다.
5. If 한 SPEC의 실행이 자신의 신호 영역에 완료 신호를 남긴 뒤 다른 SPEC의 실행이 시작되면, 시스템은 후자가 전자의 신호를 자신의 종료로 오인하지 않게 한다(각 SPEC은 자신의 신호 영역만 본다).
6. 시스템이 보조 모드 판정을 수행할 때, 그 판정은 처리 대상 SPEC의 식별(그 SPEC 디렉토리)을 입력으로 사용한다 — 작업 위치가 워크트리라는 사실 단독으로 판정하지 않는다.

## 범위
포함:
- `plugins/autopilot/skills/loop/references/loop.sh`의 보조 워크트리 모드 판정 정교화 — 현재 작업 위치가 "처리 대상 SPEC을 위해 마련된 워크트리"인지까지 확인하도록 강화. 그 외에는 SPEC 전용 격리 작업 공간·신호 영역을 사용.

비-목표 / 제외:
- dispatch(오케스트레이터) 코드 변경 — 본 수정은 loop 단독에서 격리를 보장한다(사용자 결정: loop 판정 정교화). dispatch가 어디서 실행되든 loop이 격리를 책임진다.
- spec·기타 스킬 변경.
- 보조 워크트리 모드의 정당한 단일 사용 사례 제거 — 그 사례는 보존한다.
- loop의 통합·push·PR 동작 신설 — loop은 종전대로 forge-비결합(통합은 호출 레이어 책임)을 유지한다.
- 이미 유실된 과거 실행 산출물의 복구 — 본 SPEC은 향후 재발 방지만 다룬다.
- `rules/` 변경.

## 제약
- 변경은 `plugins/autopilot/skills/loop/references/loop.sh` 한 파일에 한정한다.
- per-SPEC 디렉토리 레이아웃·격리 의도는 `rules/engineering/branch-and-slug.md`의 per-spec 디렉토리 절을 단일 출처로 따른다. loop의 격리 작업 공간·신호 영역은 그 SPEC 디렉토리 하위에 둔다.
- 보조 모드 판정은 현재 작업 위치가 "처리 대상 SPEC을 위해 마련된 워크트리"임을 확인해야 한다. 작업 위치가 워크트리라는 사실만으로 발동하면 안 된다.
- bash 3.2+ 호환을 유지한다(기존 loop.sh 제약).
- `feedback_no_self_apply_during_spec`: 본 SPEC을 구현하는 호출 중에 이 contract를 그 호출 자신의 실행 방식에 선행 적용하지 않는다 — 새 판정은 다음 loop 호출부터 적용된다.

## 위험
- **정당한 보조 사례 회귀**: 판정을 좁히다가 "사용자가 한 워크트리에서 그 대상 SPEC을 직접 돌리는" 정당한 사례까지 막을 위험. 판정 기준을 "현재 워크트리가 그 SPEC을 위해 마련된 것인가"로 명확히 묶어, 정당 사례는 통과하고 다중-위임 공유만 배제한다.
- **self-referential**: 본 SPEC은 loop 자체를 수정하므로, 이 SPEC을 loop으로 자율 구현하면 자기 구현을 고친다. `feedback_self_referential_verification`에 따라 검증은 verify 명령과 worktree source만 보고, runtime artifact(`.loop/`·워크트리·신호 영역)를 직접 검사하지 않는다.
- **격리 판정의 식별 기준 모호**: "이 SPEC을 위해 마련된 워크트리"의 판정 근거(예: 현재 워크트리가 그 SPEC 디렉토리를 포함·대응하는지)가 모호하면 오판이 재발한다. 판정은 처리 대상 SPEC의 디렉토리 식별을 입력으로 삼아 결정적으로 내린다.

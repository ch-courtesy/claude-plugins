# context-rule-creator 출력 디렉터리 분할 (task-model · task-ops)

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->
context-rule-creator 스킬의 출력 구조를 단일 평면 파일에서 컨텍스트 카테고리 디렉터리 아래 두 개의 sub-룰 파일로 바꾼다. 사용자가 컨텍스트 백엔드(filesystem·github-project)를 상호배타적으로 하나 선택하면, 스킬은 그 선택에 대응하는 컨텍스트 지침을 **백엔드 결합도**를 기준으로 둘로 갈라 기록한다 — 태스크 속성을 선택된 백엔드에 어떻게 매핑·적용하는지에 해당하는 백엔드 결합 내용은 `task-model` sub-룰로, 백엔드와 무관한 운영 규율·절차 전반(태스크 우선 원칙, 작업 시작 신호, 상태 전이 책임, 단계별 운영 규칙, append-only 기록 규율 등)은 `task-ops` sub-룰로 분리한다.

또한 스킬은 지금까지 템플릿에 하드코딩되어 있던 **태스크 상태 구성**을 생성 시점에 사용자에게 물어 수집한다. 수집은 세 단계로 분리한다 — ① 사용할 상태 집합(어떤 상태들이 존재하는가), ② 상태 전이 순서(상태들이 진행하는 순서), ③ 미리 정해진 전이 이벤트 각각에 대해 어느 상태로 전이할지(②와 분리된 별도 단계). ③에서 전이 이벤트 자체는 사용자가 서술하지 않는다 — 스킬이 제시하는 고정 이벤트 카탈로그에 대해 사용자는 각 이벤트의 목표 상태만 지정한다. 카탈로그는 작업 워크플로의 라이프사이클 이벤트(계획/스펙 문서 생성, 구현 시작, 검증 통과, 머지/완료, 차단 발견·해제 등)로 구성한다. 수집한 상태 집합과 그 백엔드 매핑은 task-model에, 전이 순서와 이벤트별 목표 상태는 task-ops의 전이 이벤트·운영 규칙에 반영된다.

디렉터리 구조를 채택해 향후 다른 컨텍스트 sub-룰이 같은 카테고리 아래 공존할 수 있게 한다. 출력 구조·상태 입력 변경에 직접 수반되는 스킬 설명(description)과 형제 스킬의 교차참조 서술만 함께 갱신하고, 그 밖의 생성 동작 규약(덮어쓰기 확인·사후 작업 처리)은 변경하지 않는다.

## 수용 기준 (EARS)
<!-- EARS 5패턴과 언어 규칙은 references/ears-patterns.md. 각 기준은 관찰 가능하고 독립 검증 가능해야 함. -->
- context-rule-creator 스킬은 한 번의 백엔드 선택에 대해 컨텍스트 카테고리 디렉터리 아래 두 개의 고정된 sub-룰 파일(`rules/context/task-model.md`와 `rules/context/task-ops.md`)을 함께 기록해야 한다.
- context-rule-creator 스킬은 태스크 속성을 선택된 백엔드에 매핑·적용하는 백엔드 결합 내용을 `task-model` sub-룰 파일에 기록해야 한다.
- context-rule-creator 스킬은 선택된 백엔드와 무관하게 성립하는 운영 규율·절차 전반을 `task-ops` sub-룰 파일에 기록해야 한다.
- context-rule-creator 스킬은 filesystem·github-project 두 백엔드를 상호배타적 단일 선택으로 제시해, 한 번의 실행에서 정확히 하나의 백엔드에 대한 분할 출력만 기록해야 한다.
- WHEN 스킬이 컨텍스트 지침을 생성할 때, 스킬은 사용할 태스크 상태 집합을 사용자에게 물어 수집해야 한다.
- WHEN 스킬이 컨텍스트 지침을 생성할 때, 스킬은 상태 전이 순서(상태들이 진행하는 순서)를 사용자에게 물어 수집해야 한다.
- context-rule-creator 스킬은 전이 이벤트 목록을 사용자 서술이 아니라 작업 워크플로 라이프사이클 이벤트(계획/스펙 문서 생성, 구현 시작, 검증 통과, 머지/완료, 차단 발견·해제 등)로 구성된 고정 카탈로그로 제시해야 한다.
- WHEN 스킬이 컨텍스트 지침을 생성할 때, 스킬은 고정 카탈로그의 각 전이 이벤트에 대해 어떤 상태로 전이할지를 전이 순서 입력과 분리된 별도 단계로 사용자에게 물어 수집해야 한다.
- context-rule-creator 스킬은 수집한 상태 집합과 그 백엔드 매핑을 task-model sub-룰에 반영해야 한다.
- context-rule-creator 스킬은 수집한 전이 순서와 이벤트별 목표 상태를 task-ops sub-룰의 전이 이벤트·운영 규칙에 반영해야 한다.
- IF 사용자가 상태 집합·전이 순서·이벤트별 목표 상태 입력 중 일부를 건너뛰면, THEN 스킬은 기존 입력 처리와 동일하게 해당 placeholder를 보존해야 한다.
- WHEN 스킬이 수집한 상태 구성을 반영해 생성 본문을 조립하면, 스킬은 그 생성 본문을 sub-룰 파일에 기록하기 전에 사용자에게 확인을 받아야 한다.
- WHEN 대상 컨텍스트 디렉터리(`rules/context/`)가 존재하지 않으면, 스킬은 파일 기록 전에 해당 디렉터리를 생성해야 한다.
- IF 대상 sub-룰 파일이 이미 존재하면, THEN 스킬은 기존과 동일하게 diff를 제시하고 사용자의 명시적 확인 없이는 덮어쓰지 않아야 한다.
- context-rule-creator 스킬은 출력 경로·분할·상태 입력 외의 기존 생성 절차(템플릿 frontmatter 제거 후 본문만 기록, 기존 정적 입력 치환과 누락 보존, on_create 사후 작업 수행)를 변경 없이 유지해야 한다.
- context-rule-creator 스킬의 frontmatter description은 출력 대상이 컨텍스트 디렉터리 아래 task-model·task-ops sub-룰 파일임을 반영해, 더 이상 단일 평면 파일을 가리키지 않아야 한다.
- engineering-rule-creator 스킬 문서의 형제 스킬(context-rule-creator) 설명은 context-rule-creator가 평면 파일 한 개를 만든다는 서술 대신 변경된 디렉터리 분할 출력 구조를 정확히 반영해야 한다.

## 범위
포함:
- context-rule-creator 스킬의 출력을 task-model·task-ops 두 sub-룰 파일로 분할하는 구조 변경
- 백엔드 결합도 기준에 따른 분할이 두 백엔드 옵션(filesystem·github-project) 모두에 적용되도록 반영
- 태스크 상태 집합·전이 순서·(고정 이벤트별) 목표 상태를 생성 시점에 각각 분리된 단계로 대화형 수집해 생성물(task-model·task-ops)에 반영
- 조립된 생성 본문을 파일로 기록하기 전에 사용자 확인을 받는 게이트
- 변경에 직접 수반되는 context-rule-creator frontmatter description 갱신
- engineering-rule-creator 스킬 문서의 context-rule-creator 교차참조 서술 갱신

비-목표 / 제외:
- 덮어쓰기 확인·on_create 처리 등 (상태 입력을 제외한) 경로·분할 외 동작 규약 변경
- filesystem/github-project를 상호배타에서 누적 sub-룰로 바꾸는 의미 변경
- 상태·전이 외의 다른 지침 항목까지 대화형 입력으로 일반화
- 이 프로젝트 자체의 기존 `rules/context.md`를 분할·이동하는 작업(rule 카테고리 산출물은 본 스킬 변경의 범위 밖)

## 제약 (있을 때만)
- 출력 sub-룰 파일명은 `task-model`·`task-ops`로 고정한다 — 템플릿 파일명에서 파생하지 않는다(두 백엔드가 같은 sub-룰 쌍을 공유하므로).
- 분할 기준은 백엔드 결합도다 — 태스크 속성의 백엔드 매핑은 task-model, 백엔드 무관 운영 내용은 task-ops.
- 입력 수집 확장은 태스크 상태 집합·전이 순서·이벤트별 목표 상태에 한정한다. 그 외 description·교차참조 갱신만 수반하고 덮어쓰기 확인·on_create 등 기존 동작 규약은 보존한다.
- 전이 이벤트는 워크플로 라이프사이클 이벤트로 구성된 고정 카탈로그이며 사용자가 서술하지 않는다 — 사용자는 각 이벤트의 목표 상태만 지정한다.
- 전이 순서와 이벤트별 목표 상태는 분리된 입력 단계로 수집한다 — 한 질문에 묶지 않는다.
- 조립된 생성 본문에 대한 확인 게이트는 기존 "이미 존재하는 파일" 덮어쓰기 diff 확인과 별개로, 새 파일·기존 파일 모두에 대해 기록 전에 적용한다.
- filesystem/github-project의 상호배타 단일 선택 의미를 유지한다.
- 상태·전이 입력은 기존 입력 처리 규약을 따른다 — 응답 누락·빈 값은 placeholder를 보존한다.

## 위험 (있을 때만)
- model/ops 경계에 걸치는 항목(예: 상태 집합 대 상태 전이 이벤트)이 있어, 백엔드 결합도 기준을 일관되게 적용하지 않으면 같은 내용이 두 파일에 중복되거나 누락될 수 있다.
- 상태 집합·전이 순서·이벤트별 목표 상태 세 입력이 서로 정합해야 한다(순서와 이벤트의 목표 상태가 모두 수집된 집합에 존재). 분리 수집이라 정합 검사가 없으면 존재하지 않는 상태를 가리키는 순서·목표 상태가 생성물에 남을 수 있다.
- 고정 이벤트 카탈로그가 사용자가 정의한 상태 집합과 맞지 않을 수 있다(예: 카탈로그 이벤트의 자연스러운 목표 상태가 집합에 없음). 사용자가 모든 카탈로그 이벤트에 목표 상태를 지정하지 못하면 일부 이벤트가 미매핑으로 남는다.
- engineering-rule-creator 외에 다른 문서·스킬·룰이 옛 출력 경로(단일 평면 파일)를 가정하고 있을 수 있어, 교차참조 갱신 범위가 누락되면 진부한 서술이 남는다.

# dispatch fan-out background driver routing

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->
dispatch의 **fan-out 단계**(준비된 SPEC마다 워커를 진행시키는 부분)를, 실행 환경의 역량에 따라
**두 가지 실행 드라이버** 중 하나로 구동할 수 있게 만든다.

- 한 드라이버는 실행 런타임이 병렬·스트리밍·동시성·재개를 네이티브로 소유하는 **강한 병렬 드라이버**다.
- 다른 드라이버는 워커를 **백그라운드로 띄우고 개별 완료마다 의존자를 즉시 해제**하는 드라이버다.

두 드라이버는 동일한 **결정적 코어**(의존성 그래프 준비도·상태 전이·실패 이행 격리·워커 계약·머지 게이트)를
공유하고 fan-out 진행 방식만 다르다. 호출자에게 노출된 **기존 dispatch 시작 인터페이스는 변하지 않으며**,
드라이버 선택은 dispatch 내부에서 일어난다. dispatch는 실행 환경의 역량을 **자동으로 판정해 선호 드라이버를
고르되**, 운영자가 **선택을 명시적으로 강제(override)** 할 수 있는 수단을 제공한다. 선호 드라이버가 가용하지
않으면 **안전 강등 사슬**(강한 병렬 → 백그라운드 → 포그라운드 병렬 배치)을 따른다.

## 목적 (왜)
<!-- 완료 조건의 종속 앵커일 뿐 검증 기준이 아니다. -->
현재 fan-out은 동기 spawn 배리어 때문에 "준비도 스트리밍"을 표방하면서도 빠르게 끝난 SPEC의 의존자가
같은 배치에서 가장 느린 무관한 형제가 끝나기를 기다린다. 환경이 더 강한 병렬·스트리밍 실행을 제공하면 그것을
쓰고, 아니면 안전하게 강등해, **의존자 해제 지연을 줄이고 처리량을 높이는 것**이 목적이다.

## 완료 조건
<!-- 5문장 패턴(항상 / …할 때 / …인 동안 / …이면(오류) / …기능이 켜지면). 각 조건은 관찰 가능·독립 검증 가능. -->
- **항상**: dispatch는 호출자에게 노출된 기존 시작 인터페이스(시작 명령·동시성 상한·대상 브랜치·재개 옵션)를
  **변경 없이** 받아들여야 한다.
- **시작할 때**: dispatch는 실행 환경의 역량을 판정해 선호 드라이버를 **자동 선택**해야 한다.
- **드라이버 override가 주어지면**: dispatch는 자동 판정을 무시하고 **지정된 드라이버**로 fan-out을 구동해야 한다.
- **선호(강한 병렬) 드라이버가 가용한 동안**: 한 SPEC의 모든 의존성이 충족되는 즉시, 같은 배치의 더 느린
  무관한 SPEC이 아직 진행 중이어도 그 SPEC의 워커가 시작돼야 한다(관찰: **느린 형제 완료 전에 의존자가 시작됨**).
- **선호 드라이버가 가용하지 않으면**: dispatch는 다음 가용 드라이버로 **안전 강등**해야 한다
  (강한 병렬 → 백그라운드 → 포그라운드 병렬 배치). 어느 드라이버로 강등됐는지 관찰 가능해야 한다.
- **한 SPEC이 비완료(머지 실패·반복 가드 소진·리뷰 불가)로 끝나면**: 그 **이행적 의존자만** 차단되고
  의존 관계가 없는 가지는 끝까지 진행돼야 한다(어느 드라이버에서든 동일).
- **머지할 때**: 워커는 승인(approve) 판정 **이후에만** 머지하고, force(push·merge·rebase)를 쓰지 않으며,
  fast-forward 전용으로 대상 브랜치에 머지해야 한다(어느 드라이버에서든 안전 불변식 보존).
- **워커가 끝날 때**: 각 워커는 **자기 SPEC을 식별 가능한 형태**로 구조화 결과(머지됨/비완료)를 보고해,
  dispatch가 그 완료를 **올바른 SPEC에 귀속**해 상태를 전이할 수 있어야 한다.
- **항상**: 한 워커의 내부 단계(구현 → 리뷰 → 재구현 → 머지)는 **데이터 의존 순서대로 차례로** 진행돼야 한다
  (이 내부 순서를 병렬·백그라운드로 바꾸지 않는다).
- **중단(stop)이 요청되면**: dispatch는 진행 중인 워커를 그 드라이버에 맞는 방식으로 정지하고, 해당 SPEC과
  그 이행적 의존자를 비완료로 처리해야 한다.

## 범위
포함:
- dispatch fan-out의 **드라이버 추상화**(강한 병렬 드라이버, 백그라운드 드라이버, 자동 감지/라우팅/강등).
- 두 드라이버와 공유 **결정적 코어**(준비도·상태·skip 전파·워커 계약·머지/리뷰 게이트)의 연결.
- 드라이버 선택의 **자동 감지 + override 수단**.
- 위 동작을 검증하는 self-test/검증 시나리오 추가·갱신.

비-목표 / 제외:
- 워커 내부 구현→리뷰→머지 순서를 병렬화하는 것(이 순서는 동기 유지).
- 워커 계약(`spec-subagent.md`)의 안전 불변식 변경.
- SPEC 작성·분해 책임(`spec` 스킬 소관).
- `rules/`·`milestones/`·`CLAUDE.md` 변경.

## 검증
<!-- 검증 기준의 단일 출처는 위 "완료 조건"이다. -->
이 SPEC의 인수 바는 위 **완료 조건**이다. 각 조건이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을
실행하는 진입 명령은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약
- 변경 범위는 autopilot **dispatch 스킬**(`plugins/autopilot/skills/dispatch/**`)에 한정한다.
- 강한 병렬 드라이버는 **dynamic Workflow 실행 메커니즘**을 사용한다 — 임의 `depends_on` DAG를
  promise 기반(노드별 의존성 충족 후 워커 실행)으로 표현하고 SPEC당 워커 1개를 둔다. 동시 실행·항목 수는 그
  런타임 상한(동시 ≤ min(16, cores−2), 단일 fan-out 항목 ≤ 4096, 총 워커 ≤ 1000)을 넘지 않는다.
- 백그라운드 드라이버는 워커를 **비동기로 띄우고 개별 완료 신호에 반응**한다. 완료 신호가 오케스트레이터를
  재호출하지 못하는 환경으로 판명되면 **포그라운드 병렬 배치**(한 턴에 동시 시작 → 배리어 → 준비도 재평가)로 강등한다.
- 드라이버 **자동 감지는 실행 환경(세션) 속성**이며 대상 리포의 파일로 결정적으로 probe할 수 없다 — 감지는
  실행 주체(모델)의 환경 판정에 둔다. **override는 기존 시작 CLI를 바꾸지 않도록 환경 변수로 받는다**
  (기존 `dispatch.sh`의 env 주입 관례 `DISPATCH_*`와 일치).
- **결정적 코어**(의존성 그래프·준비도·상태 전이·skip 전파·머지/리뷰 게이트)는 두 드라이버가 공유하며
  드라이버별로 복제하지 않는다. 기존 결정적 헬퍼·self-test의 상태 의미를 보존한다.
- **서브에이전트는 다른 서브에이전트를 spawn할 수 없다** — 워커는 자기 컨텍스트에서 `loop`·`review`를
  스킬 인터페이스로 호출한다(추가 서브에이전트로 나누지 않는다).
- 병렬 워커의 동시 git 변경은 워커별 격리(per-SPEC worktree)와 전역 락 없는 git ff-only 경합에 의존한다.

## 위험
- **자동 감지 오판**: 환경 판정에 의존하므로 잘못된 드라이버를 고를 수 있다 — override와 안전 강등 사슬로 완화.
- **백그라운드 완료 재호출의 환경 의존성**: 개별 완료가 오케스트레이터를 재호출하는지가 환경/버전에 좌우된다 —
  미지원 판명 시 포그라운드 병렬 배치로 강등해 완화. 폴백 경로는 실제 동작을 경험적으로 확인하는 검증이 필요.
- **드라이버 간 동작 일관성**: 스트리밍·실패 이행 격리·안전 불변식이 두 드라이버에서 동일하게 성립해야 하는
  유지 부담.
- **격리 의존**: 병렬 워커가 같은 리포 git을 동시에 건드릴 때 per-SPEC worktree 격리가 깨지면 머지 경합·오염 위험.

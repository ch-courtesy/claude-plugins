# Claude Review Workflow Stale Branch Handling

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->

Claude PR 리뷰 GitHub 워크플로가, **PR head의 리뷰 워크플로 파일이 현재 기본 브랜치(default) 버전과 다른 경우** — PR이 그 파일을 *직접 수정*했든, 수정하지 않았지만 default가 그 파일을 나중에 바꿔 *뒤처진(stale)* 경우든 — 권한 리뷰를 시도하다 하드 실패하지 않고, **기존의 생략(skip) 경로로 처리**해 PR 체크가 빨갛게 실패하지 않도록 한다. 이 경우 Claude 리뷰는 수행되지 않으며 명시적 생략 결과를 남긴다.

현재 워크플로는 "PR이 워크플로를 *수정*했는지"만 감지해 생략하므로, PR이 수정하지 않았지만 default가 앞서가 파일이 달라진 stale 경우를 놓쳐 권한 리뷰가 하드 실패한다. 이 단위는 그 감지를 "현재 default와 다른가"로 넓혀 두 경우를 같은 생략 경로로 보낸다.

## 목적 (왜)
<!-- 완료 조건의 종속 앵커일 뿐 검증 기준이 아니다. -->

리뷰 액션의 GitHub App 토큰 발급은 PR의 워크플로 파일이 현재 기본 브랜치와 동일할 것을 서버측에서 요구하며, 그 검증은 러너의 체크아웃과 무관하다. 그래서 기본 브랜치가 리뷰 워크플로를 갱신하면, 그 파일을 건드리지도 않은 옛 PR들이 동기화 전까지 모두 리뷰가 하드 실패한다. 하드 실패는 PR 체크를 빨갛게 만들어 혼란을 주므로, 그 경우 실패 대신 깔끔한 생략으로 처리한다.

## 완료 조건
<!-- 각 조건은 관찰 가능하고 독립 검증 가능해야 함. -->

1. **PR head의 리뷰 워크플로 파일이 현재 기본 브랜치 버전과 다를 때**(PR이 수정했든, 수정하지 않았지만 stale이든), 워크플로는 권한 리뷰를 수행하지 않고 명시적 생략 결과를 남겨야 하며, 이 사유만으로 PR 체크가 실패(빨간 상태)하지 않아야 한다. (검증: 기본 브랜치보다 뒤처졌고 워크플로를 건드리지 않은 PR에서, 그리고 워크플로를 수정한 PR에서, 모두 체크가 실패하지 않고 생략 결과가 남음이 관찰된다.)

2. **PR head의 리뷰 워크플로 파일이 현재 기본 브랜치 버전과 동일할 때**, 평소대로 Claude 리뷰가 수행되어야 한다. (검증: 최신 상태의 일반 PR에서 리뷰가 정상 수행됨이 관찰된다.)

3. **항상**: 리뷰가 실제로 수행되지 않았는데 승인 판정(거짓 green)을 만들어서는 안 된다. (검증: 생략된 PR에서 승인이 아니라 중립/생략 결과로 끝남이 관찰된다.)

## 범위
포함:
- Claude 리뷰 워크플로에서 "PR 워크플로 파일이 현재 기본 브랜치와 다른가"를 감지해 기존 생략 경로로 보내는 분기(stale·수정 모두 포함).

비-목표 / 제외:
- **stale PR에서 Claude 리뷰를 *계속 수행*하기**: 리뷰 액션 내부의 서버측 App-토큰 OIDC 검증 때문에 권한 리뷰는 stale PR에서 수행할 수 없다(체크아웃·러너 무관). 따라서 이 단위는 "리뷰 수행"이 아니라 "하드 실패 회피(생략)"를 목표로 한다.
- App 토큰 OIDC 보안 경계를 우회하거나 게시 신원을 바꾸는 변경(예: App ID 무시·기본 토큰만 사용).
- Codex 리뷰 워크플로(별도 파일), 리뷰 액션(`claude-code-action`) 자체, 리뷰 판정 로직·프롬프트.
- `rules/**`, `milestones/**`, `CLAUDE.md` 변경.

## 제약
- **대상 파일**: `.github/workflows/claude-review.yml` 한 파일만 변경한다.
- **감지 기준 확장**: 기존 "워크플로 변경 감지"의 비교 기준을 PR 분기점(merge-base) 대비에서 **현재 기본 브랜치 tip** 대비로 바꾼다 — PR head의 리뷰 워크플로 파일이 현재 기본 브랜치 버전과 다르면(수정이든 stale이든) "변경됨"으로 보고 기존 생략 경로로 보낸다. 이는 App-토큰 서버측 검증이 보는 "현재 기본 브랜치와의 동일성"과 일치한다.
- **기존 생략 경로 재사용**: 감지가 "변경됨"일 때 타는 기존 생략 결과 경로(생략 사유 게시·하드 실패 없음)를 그대로 재사용한다 — 새 생략 동작을 만들지 않는다.
- **구현 베이스**: 현재 `origin/main`의 `claude-review.yml` 위에서 변경한다(로컬 기본 브랜치가 뒤처져 있으면 `origin/main` 기준). 이 수정은 기본 브랜치에 있어야 이후 PR들에 적용된다.
- **버전 규칙**: 버전업 강제 워치 디렉토리는 `plugins`이며 `.github/` 변경은 그 대상이 아니다(`rules/engineering/versioning.md`).

## 위험
- **stale PR 리뷰 부재**: 비교 기준을 기본 브랜치 tip으로 넓히면, 기본 브랜치가 리뷰 워크플로를 바꾼 직후 동기화되지 않은 모든 PR이 Claude 리뷰를 *생략*한다(빨간 실패보다는 낫지만 리뷰는 없음). 그 PR들은 동기화(merge/rebase) 후에야 리뷰를 받는다 — 의도된 트레이드오프다.
- **기본 브랜치 식별**: 비교 대상은 PR base가 아니라 **기본 브랜치**여야 App-토큰 검증과 일치한다(대부분 PR base = 기본 브랜치이나, 스택 PR 등 다른 경우 기본 브랜치를 대상으로 해야 한다).
- **하드 실패 지점**: 하드 실패는 리뷰 액션의 *내부* App-토큰 교환에서 나므로, 감지가 그 액션 스텝이 **실행되기 전에** 생략 분기로 보내야 한다(액션이 돌기 시작하면 내부 실패를 워크플로의 continue-on-error로 잡지 못한다).

# loop stop 워커 트리 완결 종료 + orphan 워커 감지(거짓 "정상 정지" 근절)

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->
loop의 `stop`이 워커를 다 죽이지 못한 채 잠금을 풀고 "정상 정지"를 거짓 선언하는 구멍과, `start`가 드라이버는 죽었지만 워커가 살아있는 orphan 상태를 stale로 오인해 두 번째 워커를 띄우는 구멍을 메운다.

현재(전용 워크트리 모델 위에서도) 두 결함이 남아 있다:
- `stop`은 잠금에 기록된 **드라이버 PID에만** SIGTERM을 보내고 5초 안에 드라이버가 죽으면 잠금을 풀고 "정상 정지"를 출력한다. 추론 중인 워커(자식 실행기)가 SIGTERM에 즉시 죽지 않으면 **드라이버는 죽고 워커만 orphan으로 생존**하는데도 성공으로 보고한다.
- `acquire_lock`은 잠금 PID(드라이버) 생존만 본다. 드라이버가 죽고 워커만 남은 orphan 상태를 **stale 잠금으로 정리하고 진행**해, 같은 스펙에 두 번째 워커를 띄운다.

만드는 동작:
- **stop은 워커 프로세스 트리(드라이버·자식·자손)를 종료**하고, SIGTERM 후 미사망 프로세스에 SIGKILL을 에스컬레이션하며, **트리 전 프로세스의 사망을 확인한 뒤에만** 잠금을 해제하고 정상 정지를 선언한다. 생존이 남으면 잠금을 풀지 않고 비-0으로 실패를 보고한다(생존 중 "정상 정지" 금지).
- **start의 활성 판정은 드라이버뿐 아니라 워커 생존까지** 본다 — 드라이버가 죽고 워커만 orphan으로 남은 경우도 "실행 중"으로 판정해 두 번째 start를 거부한다.
- 드라이버·워커가 모두 죽고 잠금만 남은 stale 상태는 기존대로 정리 후 진행한다.

## 목적 (왜)
<!-- 이 변경을 왜 하는가(목표·동기)를 1–3문장으로. -->
stop이 워커를 다 죽였다고 거짓 보고하거나 orphan 워커를 못 보고 두 번째 워커를 띄우면, 같은 스펙의 두 워커가 같은 작업 공간·git HEAD를 동시에 건드려 노트·커밋이 서로를 덮어쓴다. 종료를 완결적으로 만들고 활성 판정에 워커를 포함시켜, 운영자의 실수(불완전 stop·더블 start)가 데이터 경합으로 번지지 않게 한다.

## 완료 조건
<!-- 각 조건은 관찰 가능하고 독립 검증 가능해야 함. -->
- stop은 워커 프로세스 트리(드라이버·자식·자손)를 종료하고, 그 트리의 모든 프로세스가 죽은 것을 확인한 뒤에만 잠금을 해제하고 정상 정지를 선언한다.
- stop 시 SIGTERM에 죽지 않는 프로세스가 있으면 SIGKILL로 에스컬레이션하며, 그래도 생존이 남으면 잠금을 유지한 채 비-0으로 실패를 보고한다(생존 중 "정상 정지" 선언 금지).
- start(잠금 획득)의 활성 판정은 잠금에 기록된 드라이버 PID뿐 아니라 그 워커(자식 실행기) 생존까지 포함한다 — 드라이버가 죽고 워커만 orphan으로 남은 경우에도 "실행 중"으로 판정해 두 번째 start를 거부한다.
- 드라이버와 워커가 모두 죽고 잠금만 남은 stale 상태면 start는 그 잠금을 정리하고 정상 진행한다.
- 위 종료·활성 판정 동작은 프로세스 생존·종료를 모사하는 주입 가능 인터페이스로 실제 워커·LLM 없이 결정적 selftest로 검증 가능하다.
- 단일 워커 정상 흐름(start→이터→terminal 신호→stop/cleanup)과 전용 워크트리 생성 동작은 회귀 없이 그대로다.

## 범위
포함:
- `stop`의 워커 트리 완결 종료(SIGTERM→SIGKILL)·전 프로세스 사망 확인 후에만 잠금 해제·성공 선언, 미사망 시 잠금 유지·비-0 보고
- `start`/`acquire_lock`의 활성 판정에 워커(orphan 포함) 생존 반영 — 워커 PID를 추적해 드라이버+워커 둘 다 확인
- stale(드라이버·워커 모두 사망) 정리 후 진행 동작 보존
- 위 동작의 결정적 selftest(프로세스 생존/종료 모사 주입)

비-목표 / 제외:
- 전용 워크트리 생성 정책(보조 worktree 재사용 제거) 변경 — 현행 모델을 그대로 전제한다.
- 잠금 파일 위치 변경(현행 `SPEC_DIR/.loop-lock` 유지) — 이 SPEC은 잠금 위치가 아니라 **활성 판정의 완전성(워커 포함)과 종료의 완결성**을 고친다.
- ralph 이터레이션 모델·신호 계약(`signals/DONE`·`BLOCKED`) 변경.
- dispatch 등 상위 레이어 변경.

## 검증
<!-- 검증 기준의 단일 출처는 위 "완료 조건"이다. -->
이 SPEC의 인수 바는 위 **완료 조건**이다. 각 조건이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을 실행하는 진입 명령은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약 (있을 때만)
- 현행 전용 워크트리 모델(보조 재사용 없음)을 전제로 한다 — 보조-모드·작업 공간 공유 가정을 재도입하지 않는다.
- 활성 판정은 드라이버 PID 생존만이 아니라 워커(자식 실행기) 생존까지 포함해야 한다(orphan 워커 누락 금지). 이를 위해 워커 PID를 영속·정리하는 최소 메커니즘을 둔다.
- 프로세스 생존 확인·종료(kill)·대기(sleep)는 주입 가능 인터페이스로 두어 selftest가 실제 프로세스 없이 결정적으로 검증할 수 있어야 한다.
- 프로세스 트리 자손 열거는 `pgrep`/`ps` 가용성에 의존한다 — 부재 시 보수적으로 처리하되, 사망 미확인이면 성공을 선언하지 않는다.
- force·테스트 약화 금지. 단일 워커 정상 흐름·전용 워크트리 동작·기존 selftest를 회귀시키지 않는다.
- 변경은 plugins/ 하위이므로 통합 시 autopilot 플러그인 SemVer 범프 + 루트 marketplace.json 미러 동기가 필요하다.

## 위험 (있을 때만)
- 전용 워크트리 모델에서는 서로 다른 스펙이 각자 워크트리를 가지므로 충돌 빈도는 낮으나, **같은 스펙의 더블 start**(같은 `SPEC_DIR/.loop-lock`)에서는 여전히 orphan·거짓 성공이 데이터 경합을 일으킨다 — 본 SPEC은 그 경로를 막는다.
- SIGKILL 에스컬레이션은 워커가 커밋 도중이면 부분 상태를 남길 수 있다 — stop은 잠금 해제 전 사망만 보장하고, 작업 공간 정합 복구는 호출자/다음 start의 책임 범위로 둔다(본 SPEC은 거짓 성공·중복 기동 방지에 한정).

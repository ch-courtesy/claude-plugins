# autopilot이 task-context 지침을 스킬로 소유하고 프로젝트 상태를 분리 저장

## 무엇을 만들 것인가
task 컨텍스트 관리에 대한 **지침(안정적·재사용 지식)**과 **프로젝트 상태(설치된 프로젝트마다 다른 값)**를 명확히 분리한다.

1. **지침은 autopilot 스킬이 소유한다.** task 모델 개념·운영 규율(task-ops)·백엔드별 매핑 변형(filesystem·github-project 등)의 본문을 autopilot 스킬의 번들 콘텐츠로 두어 단일 출처로 삼는다. 지금처럼 `context-rule-creator`가 설치된 프로젝트마다 `rules/context/task-model.md`·`task-ops.md`로 **지침 전문을 생성**하던 모델을 폐지한다 — 지침은 더 이상 프로젝트마다 복제되지 않는다.
2. **프로젝트 상태는 일반화된 벤더-중립 규약으로 consuming repo에 분리 저장한다.** 선택된 백엔드 id와 그 프로젝트 고유 값(예: project URL, status 옵션, 라이프사이클 이벤트→상태 매핑)만, 플러그인이 정의하는 **일반화된 규약**에 따라 **플러그인이 설치된 프로젝트 repo의 추적되는 벤더-중립 상대 경로**에 영속한다. 이 경로는 특정 벤더 dot-dir(`.claude/` 등)·특정 repo 구조를 가정하지 않고, 프로젝트 루트 기준 고정 상대 경로이며 모든 에이전트 벤더가 읽을 수 있다(프로젝트의 AGENTS.md/공통 지침 트리로 surfacing).
   - **상태 위치는 스킬 실행(생성) 시 인터뷰로 결정한다.** 스킬은 벤더-중립 기본 경로를 추천(첫 선택지)으로 제시하고 consuming 프로젝트가 자기 레이아웃에 맞게 확정·재정의할 수 있게 한다 — 기존 컨텍스트 규칙 생성의 입력 수집 인터뷰와 동형이다. 기본값을 그대로 쓰면 추가 선언 없이 그 경로가 곧 상태 위치다.
   - **나중에 읽을 때 위치가 결정적으로 해석돼야 한다.** 기본값이 아닌 위치를 고르면 그 경로가 **고정된 발견 가능한 자리**(프로젝트의 AGENTS.md 또는 약속된 키 한 줄 선언)에 기록되어, 다음 세션·다른 벤더가 그 선언을 읽어 실제 상태 파일을 일의적으로 찾는다. "어디에 있는지"를 찾기 위해 위치를 추측하지 않는다.
3. autopilot 워크플로 소비자(using-autopilot·dispatch·loop)와 컨텍스트 규칙 생성 흐름은 "지침=스킬 콘텐츠 + 상태=분리된 상태 파일"을 읽도록 정합한다.
4. 이 분리에 따라 `project-init`의 컨텍스트 규칙 생성 책임과 `project-init:bootstrap`의 자동 흐름, 두 플러그인·관련 스킬의 교차 참조를 새 모델에 맞게 정정한다.

## 목적 (왜)
task 라이프사이클 흐름(spec→dispatch→loop)은 이미 autopilot에 있는데 task 지침의 본문은 프로젝트마다 `rules/context/`로 복제 생성되어, 같은 지침이 설치처마다 흩어지고 드리프트한다. 지침을 스킬이 단일 출처로 소유하면 복제가 사라지고, 프로젝트마다 진짜로 다른 것(어느 백엔드를 쓰는지 등 **상태**)만 consuming repo에 남긴다. autopilot이 멀티-벤더로 가는 만큼 그 상태 저장은 한 벤더에 묶이지 않는 일반화된 규약이어야 한다.

## 완료 조건
- autopilot 스킬을 호출하면 task 모델·운영 규율·백엔드별 매핑 지침 본문이 스킬 자신의 콘텐츠로 제공되며, 그 지침 본문이 consuming 프로젝트의 `rules/context/`로 복제 생성되지 않는다.
- 둘 이상의 task 백엔드(예: filesystem·github-project) 지침 변형이 스킬 안에 단일 출처로 존재하고, 선택된 백엔드에 해당하는 지침이 식별·사용된다.
- task 백엔드 선택과 그 프로젝트 고유 값(project URL·status 옵션·이벤트→상태 매핑 등)이 **플러그인이 설치된 프로젝트 repo의 추적되는 상대 경로**의 상태 파일에 영속되고, 새 세션·다른 에이전트가 그 파일을 읽어 동일 백엔드·값을 복원한다.
- 상태 파일 경로 규약이 특정 벤더 dot-dir·특정 repo 구조에 의존하지 않고, 임의의 consuming 프로젝트에서 동일하게 해석되며, Claude·Codex 등 서로 다른 벤더가 모두 그 위치를 읽을 수 있다.
- 스킬 실행(생성) 시 상태 저장 위치를 묻는 인터뷰가 벤더-중립 기본값을 추천으로 제시하고, 비-기본 위치를 선택하면 그 위치가 고정된 발견 가능한 자리에 선언되어 이후 읽기에서 위치가 일의적으로 해석된다.
- 상태 파일은 지침 본문을 포함하지 않는다(지침과 상태가 물리적으로 분리되어 있다).
- 컨텍스트 규칙 생성 책임이 이전된 결과, `project-init`은 task 컨텍스트 지침 본문 생성을 더 이상 소유하지 않으며, `project-init:bootstrap` 자동 흐름에 task 컨텍스트 지침 생성이 후보·호출로 나타나지 않는다. 나머지 카테고리 rule-creator의 열거·호출은 이전과 동일하다.
- repo의 라이브 스킬·문서에서 옛 "지침 생성" 모델(`context-rule-creator`가 `rules/context`로 지침 전문 생성)을 가리키는 교차 참조가 새 모델(지침=스킬, 상태=분리 저장)에 맞게 정정되어 있고, 깨진 참조가 남지 않는다.
- autopilot(및 변경된 경우 project-init) 플러그인 버전이 프로젝트 버전 관리 규칙에 따라 올바르게 범프되어 있다.

## 범위
포함:
- task 지침 본문(task 모델·task-ops·백엔드별 매핑 변형)을 autopilot 스킬 소유 콘텐츠로 이전 — 단일 출처화, 프로젝트별 지침 전문 생성 폐지.
- 프로젝트 상태(백엔드 선택 + 고유 값)를 일반화된 벤더-중립·추적 상대 경로에 영속하는 규약 정의와, 그 상태를 쓰고/읽는 스킬 동작.
- autopilot 소비자(using-autopilot·dispatch·loop) 및 컨텍스트 규칙 생성 흐름이 "스킬 지침 + 분리된 상태"를 읽도록 하는 정합.
- `project-init`의 컨텍스트 규칙 생성 책임 이전과 `project-init:bootstrap` 자동 흐름 정합, 두 플러그인·관련 스킬의 교차 참조 정정.
- 소유 플러그인 변경에 수반되는 매니페스트·버전 메타데이터 갱신.

비-목표 / 제외:
- 상태 파일의 **구체 파일명·직렬화 포맷 확정**(합리적 기본값 또는 마커로 남기고, 본 SPEC은 "추적·벤더중립·프로젝트 상대 경로·지침과 분리"라는 규약 속성만 고정).
- task 지침의 **의미 내용 재작성**(소유 위치·전달 방식을 바꿀 뿐, 지침이 규정하는 task 모델·운영 규율 자체의 정책 변경은 아님).
- 기존에 `rules/context/`로 이미 생성된 지침 파일의 일괄 마이그레이션 도구화(이전은 별도 관심사 — 본 SPEC은 새 모델의 동작을 규정).
- project-init의 나머지 5개 rule-creator(engineering·review·version-control·workflow·workspace)의 위치·동작 변경.
- Claude·Codex 외 벤더의 실제 실행 지원 추가.
- 과거 `docs/specs/**` 이력 문서의 언급 정정(이력 보존).

## 검증
이 SPEC의 인수 바는 위 **완료 조건**이다. 각 조건이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을 실행하는 진입 명령은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약
- 상태 저장 위치는 **플러그인이 설치된 프로젝트 repo**(이 claude-plugins repo가 아니라)를 기준으로 하는 **프로젝트 루트 상대의 고정 규약**이어야 한다 — 스킬 설치 경로(플러그인 캐시, 버전 디렉터리, 업데이트 시 휘발)나 벤더 전용 dot-dir(`.claude/`·`.codex/` 등)에 두지 않는다.
- 상태 저장 위치는 git 추적되어 팀 공유·이식이 가능해야 하고, 모든 에이전트 벤더가 읽을 수 있도록 프로젝트의 공통 지침 트리(예: `rules/`) 또는 AGENTS.md가 가리키는 벤더-중립 자리에 둔다.
- 지침 본문은 스킬이 단일 출처로 소유하며, 같은 본문을 consuming 프로젝트에 복제 저장하지 않는다.
- 버전 범프·변경 통합 절차는 프로젝트 규칙(`rules/engineering`·`rules/version-control`)을 단일 출처로 따른다.
- 본 설계는 진행 중인 멀티-벤더(codex) 작업과 정합해야 한다 — 공통 계약은 한 곳, 벤더 차이만 어댑터로.

## 위험
- "지침 생성 폐지"는 컨텍스트 규칙을 소비하던 기존 경로(using-autopilot·dispatch·loop·project-init:bootstrap)를 모두 건드리므로, 일부 소비자가 여전히 생성된 `rules/context` 본문을 가정하면 깨진다 — 소비자 정합을 빠짐없이 해야 한다.
- 벤더-중립 상태 경로 규약이 모호하면 벤더마다 다른 위치를 읽어 상태가 분기될 수 있다 — 규약은 프로젝트 루트 상대 고정 경로로 일의적이어야 한다.
- `project-init`/autopilot 양쪽과 멀티-벤더 작업이 같은 영역을 건드리므로, 교차 참조·생성 흐름 정정이 불완전하면 컨텍스트 규칙 설정이 어느 경로에서도 동작하지 않을 수 있다.

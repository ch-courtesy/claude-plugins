# Streaming dispatch + structured loop handoff

## 무엇을 만들 것인가
autopilot `dispatch`의 다중 SPEC 실행 스케줄러를, 위상 wave 단위 **배리어** 방식에서 **SPEC별 의존성 준비도(readiness) 기반 스트리밍** 방식으로 바꾼다. 각 SPEC은 자신의 `depends_on`이 모두 완료되는 즉시 — 같은 위상 단계의 무관한 SPEC이 아직 실행 중이어도 기다리지 않고 — 동시성 상한 이내에서 시작된다. 한 SPEC이 실패하면 그 **이행적 의존자만** 차단되고 의존 관계가 없는 가지는 끝까지 진행된다.

더불어 `dispatch`가 자율 실행기(`loop`)의 **종료 상태를 판정하는 경로**를, 출력 표의 텍스트 컬럼 파싱에서 **`loop`의 공개 인터페이스가 제공하는 구조화된(기계 판독 가능) 상태**로 바꾼다.

## 목적 (왜)
현재 `dispatch`는 wave 배리어로 한 위상 단계의 모든 SPEC이 끝나야 다음 단계를 시작한다. 단계 내 실행 시간 편차가 크면 빠른 가지가 느린 무관 작업의 완료를 기다리며 벽시계를 낭비한다. 네이티브 Claude Code Workflow 벤치마크(`docs/research/2026-06-03-claude-code-dynamic-workflows/`)에서 무배리어 pipeline이 단계 배리어보다 빠름이 실측됐다(S3 34.8s < S4 41.6s, 동일 작업·토큰). 이 이점을 dispatch에 흡수해 "의존 관계가 실제로 요구하는 만큼만 대기"하게 하여 다중 SPEC 실행의 벽시계를 줄이는 것이 목적이다. 구조화 핸드오프는 그 스케줄링 판정이 의존하는 `loop` 상태 신호를 컬럼 위치·부분 문자열 일치 같은 취약한 텍스트 파싱에서 벗어나 신뢰 가능하게 만들기 위함이다.

## 완료 조건
- **…할 때**: 어떤 입력 SPEC의 `depends_on`이 모두 `done` 상태가 될 때, 시스템은 같은 위상 단계의 무관한 SPEC들이 아직 실행 중이어도 그 SPEC을 즉시(무관 SPEC의 완료를 기다리지 않고) 시작해야 한다.
- **항상**: 시스템은 각 SPEC을 그 자신의 `depends_on`이 모두 `done`이 되기 전에는 시작하지 않아야 한다.
- **…이면(오류)**: 한 SPEC이 `failed`로 끝나면, 시스템은 그 SPEC의 **이행적 의존자만** `failed`/skipped로 표시하고, 그 SPEC과 의존 관계가 없는 SPEC들은 끝까지 실행해야 한다.
- **항상**: 시스템은 `loop`의 종료 상태(완료 vs 차단)를 `loop`의 공개 인터페이스가 제공하는 구조화된(기계 판독 가능) 상태로 판정해야 하며, 출력 표의 컬럼 위치나 자유 텍스트 부분 문자열 일치에 의존하지 않아야 한다.
- **…할 때**: 동일 run-id로 재개할 때, 시스템은 이미 `done`인 SPEC을 재실행하지 않고 미완 SPEC만 스트리밍 스케줄에 따라 진행해야 한다.
- **…인 동안**: 다중 SPEC이 실행되는 동안, 시스템은 동시에 실행 중인 SPEC 수를 지정된 동시성 상한 이내로 유지해야 한다.
- **항상**: 시스템은 기존 운영 인터페이스(목록 조회·상태 조회·정지·완료 대기)와 run-id 출력 계약(`run-id: <id>` 줄)을 호출자가 기존과 호환되게 쓸 수 있도록 보존해야 한다.
- **…이면(오류)**: `depends_on`에 순환이 있으면, 시스템은 실행을 시작하지 않고 순환 구성 요소를 보고하며 비-0으로 종료해야 한다.

## 범위
포함:
- dispatch 다중 SPEC 실행 스케줄러의 wave-배리어 → SPEC별 준비도 스트리밍 전환(기본 동작).
- 실패 시 이행적 의존자만 차단하고 독립 가지는 계속하는 실패 전파 정책.
- loop→dispatch 종료 상태 핸드오프의 구조화(텍스트 컬럼 파싱 제거).
- 위 변경에 따른 dispatch·loop SKILL.md 동작 서술 갱신과 관련 테스트 갱신/추가.

비-목표 / 제외:
- `loop`의 Ralph 이터레이션 내부 로직·객관 게이트(테스트 해시·scope diff·oscillation 등) 변경 없음.
- 적대적/다각도 verify 도입 없음 — Ralph 단일 워커 모델에 fit이 약하고 loop은 결정적 게이트로 그 슬롯을 이미 점유(별도 후속: review 레이어).
- `fsd`의 review/merge/poll 등 forge 레이어 변경 없음.
- `fsd`→`dispatch`의 run-id stdout 계약 변경 없음(보존 대상이지 변경 대상 아님).
- `rules/`·`milestones/`·`CLAUDE.md` 변경 없음.

## 검증
이 SPEC의 인수 바는 위 **완료 조건**이다. 각 조건이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을 실행하는 진입 명령(테스트·lint)은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약
- `dispatch`는 `loop`의 **공개 인터페이스로만** 종료 상태를 판정하며, `loop` 내부 signals/·worktree 파일을 직접 읽지 않는다(dispatch 불변식 보존).
- 구조화 상태는 `loop`의 공개 인터페이스 확장으로 노출한다(기계 판독 가능 상태 출력). 기존 사람용 텍스트 출력과의 공존 여부는 구현이 정하되, dispatch의 판정 경로는 구조화 상태를 단일 출처로 삼는다.
- bash 3.2 호환(연관 배열 금지). 기존 `build_dag`의 인덱스 기반 DAG·`extract_depends_on`/`resolve_dep` 기법을 재사용한다.
- WAVES.txt 등 위상 정보 산출물은 **진단용으로 보존**하되, 실제 실행 스케줄은 wave 배리어가 아니라 SPEC별 준비도로 구동한다.
- 구조화 상태 파싱은 이미 의존성에 있는 도구(`yq`)를 사용하고, 도구 부재·레거시 텍스트 상태에 대한 처리 정책을 명시한다.
- 동시성 상한은 기존 `--max-parallel` 의미(전역 동시 실행 상한)를 보존한다.
- 플러그인 코드(`plugins/`) 변경이므로 버전 SoT(`plugin.json`)와 루트 `marketplace.json` 미러를 같은 변경에서 SemVer로 올린다(0.y.z 초기 개발 단계: 동작 변경을 MINOR에 담을 수 있음). 이 버전 범프는 통합 단계에서 수행될 수 있다.

## 위험
- 기본 동작 교체로 기존 dispatch wave 기반 테스트가 깨질 수 있다 — 테스트를 스트리밍 의미(준비도 기반 시작·이행적 실패 차단)에 맞게 갱신해야 한다.
- 실패 시 "독립 가지 계속" 정책은 기존 fail-fast(첫 실패가 다음 wave 전체 차단) 대비 운영자 기대를 바꾼다 — 0.x라 호환 깨짐은 허용되나 SKILL.md·운영 가이드에 동작 변화를 명시해야 한다.
- 구조화 핸드오프가 `loop` 공개 인터페이스를 확장하므로, `loop` 상태를 소비하는 다른 주체(있다면)와의 호환을 확인해야 한다.
- bash에서 "SPEC별 준비도 스케줄링 + 전역 동시성 상한 + 이행적 실패 전파"를 동시에 다루는 제어 복잡도 — 폴링 루프·PID 추적·상태 전이의 경합을 주의.

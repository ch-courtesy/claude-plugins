# Workflow Replica Skill

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->

이미 구현된 Workflow Replica 하니스(독립 DAG 오케스트레이터)를 **autopilot 플러그인의 스킬**로 감싼다. 사용자·에이전트가 Skill 호출로 이 하니스를 구동해, 작성된 워크플로 정의를 받아 **스트리밍 fan-out·동시성 상한·실패 이행 격리·저널 resume·결과값 전달**로 실행하고 기계 판독 가능한 결과를 받을 수 있게 한다.

스킬은 하니스 엔진을 **얇게 감싸는 래퍼**다 — 엔진의 동작을 바꾸지 않고, ① 명령으로 구동 가능한 **진입점(러너)**과 ② 하니스 사용 계약을 노출하는 **스킬 정의(SKILL.md)**를 제공한다. 진입점의 입력→구조화 출력 계약은 다른 스킬(예: dispatch)이 내장 dynamic Workflow 도구가 미가용인 환경의 폴백으로 프로그램적으로 호출할 수 있어야 한다.

## 목적 (왜)
<!-- 완료 조건의 종속 앵커일 뿐 검증 기준이 아니다. -->

하니스는 라이브러리(import) 인터페이스만 가져 사람·에이전트가 일관된 방식으로 호출하거나 다른 스킬이 폴백 드라이버로 채택하기 어렵다. 내장 dynamic Workflow 도구가 막힌 환경에서도 동일한 오케스트레이션을 **표준화된 스킬 진입점**으로 손쉽게 구동하기 위해, 하니스를 autopilot 4-skill 패밀리와 같은 호출 규약으로 노출한다.

## 완료 조건
<!-- 각 조건은 관찰 가능하고 독립 검증 가능해야 함. -->

1. **항상**: 스킬은 작성된 워크플로 정의를 입력으로 받아 하니스 엔진으로 실행하고, 노드별 상태(성공·실패·스킵)와 노드 결과값을 포함한 기계 판독 가능한 결과를 출력해야 한다. (검증: 알려진 워크플로를 구동하면 성공/실패/스킵 노드 집합과 결과가 구조화 출력으로 관찰된다.)

2. **워크플로 정의 경로를 받아 실행을 요청하면**, 스킬은 그 워크플로를 끝까지 실행하고 결과를 구조화 출력으로 돌려줘야 한다. (검증: 다중 노드 워크플로 입력에 대해 전 노드가 처리되고 결과가 출력됨이 관찰된다.)

3. **자체 검증 실행을 요청하면**, 스킬은 하니스의 테스트 묶음을 실행해 통과/실패 수를 보고해야 한다. (검증: 자체 검증 진입점이 하니스 테스트를 돌려 통과 수를 출력함이 관찰된다.)

4. **워크플로 정의 경로가 존재하지 않거나 읽을 수 없으면**, 스킬은 오류를 보고하고 실행을 시작하지 않아야 한다. (검증: 없는 경로 입력에 대해 실행이 시작되지 않고 오류가 보고된다.)

5. **항상**: 스킬은 명시된 서브커맨드만 실행하고 다른 서브커맨드를 임의 추론하지 않으며, 각 결과를 사용자에게 요약해야 한다. (검증: 미정의 서브커맨드 요청이 실행되지 않음이 관찰된다.)

6. **항상**: 스킬 정의(SKILL.md)는 하니스의 사용 계약(노드·의존성·동시성 상한·실패 이행 격리·저널 resume·결과 전달·에이전트 노드)을 중간 질문 없이 사용할 수 있을 만큼 자기완결적으로 노출해야 한다. (검증: 스킬 정의만 읽고 워크플로를 작성·구동할 수 있음이 관찰된다.)

7. **항상**: 스킬은 autopilot 플러그인의 스킬로 등록되어 플러그인 스킬 목록에서 발견되고 Skill 호출로 구동 가능해야 한다. (검증: 플러그인의 스킬 목록에 새 스킬이 나타나고 호출되면 러너가 동작함이 관찰된다.)

8. **항상**: 진입점의 입력→구조화 출력 계약은 다른 스킬이 프로그램적으로 호출해 결과를 판정할 수 있는 형태여야 한다 — 자유 텍스트 부분 문자열 일치에 의존하지 않는다. (검증: 러너 출력이 구조화 포맷으로 파싱되어 성공/실패 판정에 쓰일 수 있음이 관찰된다.)

9. **내장 dynamic Workflow 도구가 미가용인 동안**, 위 실행은 외부 서비스나 특수 런타임 없이(표준 라이브러리만으로) 충족되어야 한다. (검증: Workflow 도구 없이 표준 환경에서 위 조건들이 통과함이 관찰된다.)

## 범위
포함:
- 스킬 정의(SKILL.md) — 하니스 사용 계약을 자기완결적으로 노출.
- 명령으로 구동 가능한 CLI 러너 진입점(워크플로 실행 + 자체 검증 서브커맨드).
- 하니스 코드(현 위치)를 스킬의 참조 코드 위치로 이동(테스트 포함).
- autopilot 플러그인·마켓플레이스 등록 + 버전 갱신.

비-목표 / 제외:
- **하니스 엔진 자체의 기능 변경**: 엔진은 이미 구현·검증되어 있으며 이 단위는 래핑만 한다(엔진 동작 수정 없음).
- **dispatch의 폴백 드라이버 채택 구현**: dispatch가 이 스킬을 strong-parallel 불가 환경의 드라이버로 실제 라우팅하는 작업은 별도 단위다. 이 단위는 그 채택을 **가능하게 하는 호출 계약**까지만 책임진다.
- 새 오케스트레이션 기능(토큰 budget·워크플로 중첩 등)은 범위 밖(하니스 SPEC의 비-목표 승계).
- `rules/**`, `milestones/**`, `CLAUDE.md` 변경.

## 검증
<!-- 검증 기준의 단일 출처는 위 "완료 조건"이다. -->
이 SPEC의 인수 바는 위 **완료 조건**이다. 각 조건이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을 실행하는 진입 명령은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약
- **스킬 위치·이름**: autopilot 플러그인의 스킬로 `plugins/autopilot/skills/flow/` 에 둔다(spec/loop/dispatch/review 형제). 스킬 호출 이름은 **`flow`**(`Skill(skill="flow")`)로 확정한다.
- **하니스 코드 이동**: 하니스 코드(현 `tools/workflow-replica/`, PR #373)를 스킬의 참조 코드 위치(`skills/<skill>/references/`)로 **이동**한다(원본 위치 제거 포함, 중복 금지). 이동 후 import 경로와 하니스 테스트가 그 새 위치에서 깨지지 않고 통과해야 한다.
- **진입점 형태**: 진입점은 `loop.sh`/`dispatch.sh`와 동형으로 **Bash로 구동 가능한 CLI 러너**(run·selftest 등 서브커맨드)로 둔다. 출력은 기계 판독 가능한 구조화 포맷.
- **표준 라이브러리만**: Python 3.9+ 표준 라이브러리만 사용한다(외부 패키지 의존 0 — 하니스 제약 승계).
- **버전 갱신**: `plugins/`는 워치 디렉토리이므로, 이 변경과 **같은 머지 안에서** 버전 SoT(`plugins/autopilot/.claude-plugin/plugin.json`)와 그 파생(`.claude-plugin/marketplace.json`의 autopilot 항목)을 갱신한다. 규약·절차의 단일 출처는 `rules/engineering/versioning.md`다.
- **스킬 정의 frontmatter**: SKILL.md는 `name`·`description`·`allowed-tools`(러너 구동에 필요한 Read·Bash 권한)를 갖춘다.

## 위험
- **하니스 의존(시퀀싱)**: 하니스 코드는 현재 PR #373(미머지)에만 존재하고 기본 브랜치에는 없다. 이 스킬 구현은 이동할 원본 코드를 전제하므로, **PR #373이 기본 브랜치에 먼저 머지된 뒤** 진행하는 것이 안전하다. 미머지 상태에서 기본 브랜치 기준으로 구현하면 이동할 원본이 없어 막힌다.
- **코드 이동 중복**: 이동이 원본(`tools/workflow-replica/`) 제거를 포함하지 않으면 두 위치에 하니스가 중복된다. 이동은 단일 정본을 보장해야 한다(완료 조건 7·제약의 "이동").
- **러너의 워크플로 스크립트 신뢰 경계**: 러너가 임의 워크플로 스크립트를 실행하므로, 입력 스크립트는 신뢰된 작성자 산출물이라는 전제 위에서 동작한다(임의 비신뢰 코드 실행 방어는 이 단위 범위 밖, 운영 규칙 소관).

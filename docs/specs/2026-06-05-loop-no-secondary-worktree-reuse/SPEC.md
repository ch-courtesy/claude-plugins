# loop은 항상 전용 워크트리를 생성한다 (no-secondary-worktree-reuse)

## 무엇을 만들 것인가
<!-- WHAT/HOW 방어선: 무엇을 만들지만 적고 구현 방법·파일·라이브러리·클래스명은 제약으로 이동. -->
loop이 한 SPEC을 실행할 때, 그 SPEC 파일이 보조(secondary) git 워크트리 안에 있더라도 그 enclosing 워크트리를 작업 공간으로 재사용하지 않고, 호출 위치와 무관하게 **항상 자신의 전용 워크트리를 새로 생성**해 그 안에서 작업하도록 동작을 바꾼다.

현재 loop은 보조 워크트리 안에서 호출되면 새 워크트리를 만들지 않고 현재 워크트리를 그대로 작업 공간으로 재사용한다. 이 "재사용" 동작을 제거하고, 주 작업트리에서 호출될 때와 동일하게 스펙 디렉토리 옆의 전용 워크트리를 새로 만들어 실행마다 격리한다. 전용 워크트리를 만들 수 없는 경우에는 작업을 진행하지 않고 실패로 멈춘다.

## 목적 (왜)
<!-- 이 변경을 왜 하는가(목표·동기)를 1–3문장으로. -->
loop 실행이 호출자의 현재 워크트리를 절대 건드리지 않도록 보장하기 위해서다. 워크트리를 재사용하면 중첩·병렬 호출 시 호출자의 작업 공간이 loop의 산출물·변경으로 오염될 수 있으며, 항상 전용 워크트리를 새로 만들면 매 실행이 완전히 격리된다.

## 완료 조건
<!-- 각 조건은 관찰 가능·독립 검증 가능. -->
- **항상**: loop 실행 시, 시스템은 스펙 디렉토리 하위의 전용 워크트리를 새로 생성하고 그 안에서 작업해야 한다.
- SPEC 파일이 보조 워크트리 안에 있을 때, 시스템은 그 enclosing 워크트리를 작업 공간으로 재사용하지 않고 전용 워크트리를 새로 생성해야 한다.
- 전용 워크트리 생성이 실패하면(오류), 시스템은 작업을 진행하지 않고 0이 아닌 코드로 중단해야 한다.
- **항상**: 시스템은 생성한 전용 워크트리와 그 내부 실행 산출물이 enclosing 워크트리·주 작업트리에서 추적되지 않은(untracked) 변경으로 노출되지 않도록 기존 제외 상태를 유지해야 한다.
- loop 정리(cleanup)를 실행할 때, 시스템은 자신이 생성한 전용 워크트리를 제거해야 한다 — 어느 호출 위치에서 생성됐든 "사용자 워크트리"로 간주해 보존하지 않는다.
- **항상**: loop의 사용자 문서는 "보조 워크트리 안에서는 새로 만들지 않고 현재 워크트리를 사용한다"는 서술을 더 이상 포함하지 않고, 항상 전용 워크트리를 생성한다는 동작과 일치해야 한다.

## 범위
포함:
- loop의 워크트리 준비 경로에서 보조 워크트리 재사용 동작 제거(항상 전용 워크트리 생성).
- 전용 워크트리 생성 실패 시 중단(abort) 동작.
- loop 정리 경로를 항상 생성-워크트리 제거로 일원화.
- 위 동작 변경과 모순되는 loop 사용자 문서 서술 갱신.
- 변경된 동작을 반영하는 loop 자체 테스트 갱신.

비-목표 / 제외:
- 같은 SPEC에 대한 동시 병렬 실행 지원, SPEC당 다중 워크트리 풀(`.worktrees/<id>/`), run-id 기반 식별 인터페이스 — 이번 변경 대상 아님(작업 공간 경로는 스펙 디렉토리 하위 단일 워크트리를 유지).
- 동시성 락의 단위 변경(스펙 디렉토리 단위 락 유지).
- 워크트리 생성 실패 시의 대체 위치 폴백(`.worktrees/` 등) — 실패는 abort로 처리하므로 비-목표.
- 플러그인 버전 번호 갱신 — 통합(머지) 시점에 프로젝트 버전 관리 규칙이 단일 출처로 처리(SPEC 범위 밖).

## 검증
<!-- 검증 기준의 단일 출처는 위 "완료 조건". -->
이 SPEC의 인수 바는 위 **완료 조건**이다. 각 조건이 관찰 가능하게 충족되면 충족된 것으로 본다. 검증을 실행하는 진입 명령은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처로 정의한다.

## 제약
- 현재 보조 워크트리 재사용은 워크트리 준비 단계의 보조-오버라이드 경로로 구현돼 있다. 이 재사용 분기를 제거하고 호출 위치와 무관하게 전용 워크트리 생성 경로를 타게 한다.
- 작업 공간은 기존과 동일하게 스펙 디렉토리 하위의 **단일 전용 워크트리**를 유지한다 — 새 풀 디렉토리나 SPEC당 다중 워크트리를 도입하지 않는다.
- 생성한 워크트리와 실행 산출물의 untracked 제외(공통 git 디렉토리 제외 등록)는 기존 동작을 보존한다.
- 정리(cleanup)는 loop이 항상 자신의 워크트리를 소유하므로, 호출 위치로 "사용자 워크트리"를 추정해 보존하던 분기를 제거하고 항상 생성 워크트리를 제거한다.
- loop의 정체성(스펙 파일 절대 경로)·신호 계약(`.loop/signals/`의 DONE·BLOCKED)·동시성 락 계약은 변경하지 않는다.
- bash 3.2+ 호환을 유지한다.

## 위험
- SPEC이 보조 워크트리 안에 있을 때, 전용 워크트리를 enclosing 워크트리 내부 경로에 만드는 것을 git이 거부하거나 경고할 수 있다 — 정상 경로에서 성공함을 확인하고, 실패 시 abort 동작과 정합해야 한다.
- 기존에 보조 워크트리에서 재사용으로 동작하던 흐름(예: SPEC이 `.claude/worktrees/` 안에 있는 경우)이 이제 중첩 워크트리를 만들므로, 그 흐름에서 상태 조회·정리가 새 워크트리를 올바로 인식·제거하는지 확인이 필요하다.

# 역PRD — autopilot `dispatch` 스킬

> **문서 성격**: 현재 구현에서 제품 요구사항을 역추출한 재구현 기준서(역PRD). 구현 방법(HOW)은 싣지 않는다.
>
> **근거 소스 범위**: 이 리포지토리 `plugins/autopilot/skills/dispatch/`의 `SKILL.md`와 `references/` 하위 모듈 전체(결정적 오케스트레이션 헬퍼, per-SPEC 워커 계약, 통합·리뷰 반복·머지 헬퍼, per-SPEC 통합 상태 헬퍼). 헬퍼 구현부에서는 사용자 가시 동작(서브커맨드·플래그·주입 변수·산출물 경로·판정 규칙·오류 동작)만 추출했다.
> **기준 플러그인 버전**: autopilot `0.38.1` (작성 시점 스냅샷 — 이후 스킬 변경 시 본 문서와 드리프트가 생길 수 있다).

## ① 개요·배경·목적

`dispatch`는 하나 이상의 SPEC 파일을 받아 frontmatter `depends_on` 의존성을 풀고, **준비된(모든 의존이 done) SPEC마다 서브에이전트(워커)를 정확히 1개 띄우는 모델 주도 오케스트레이터**다. 각 워커는 자기 컨텍스트에서 그 SPEC의 전 생애 — 구현(`autopilot:loop`)→리뷰→재구현→대상 브랜치 머지 — 를 소유하고, dispatch 자신은 **준비도 스케줄링·동시성 상한·워커 생성/회수·done(=머지) 전이에 의한 의존자 해제·실패의 이행적 격리**만 책임진다.

배경: 여러 SPEC을 자율 구현으로 흘릴 때 ⑴ 의존 SPEC은 의존성이 머지된 갱신 브랜치 위에서 분기해야 하고 ⑵ 한 SPEC의 실패가 무관한 가지를 멈추면 안 되며 ⑶ 통합·리뷰·머지를 무인 스크립트 파이프라인으로 돌리면 판단이 필요한 지점(리뷰 채택·에스컬레이션)이 깨진다. dispatch는 결정적인 부분(상태 전이·준비도 계산·머지 게이트)은 검증 가능한 헬퍼에, 판단이 필요한 부분(구현·리뷰 대응)은 SPEC당 한 컨텍스트의 워커에 두는 역할 분리로 이를 해결한다.

목적(존재 이유):

- SPEC 묶음의 **의존성·동시성·실패 격리 총괄**만 한다 — 통합·리뷰·머지를 직접(무인 파이프라인으로) 수행하지 않는다.
- `done`의 의미를 "대상 브랜치에 머지됨"으로 고정해, 의존자가 항상 머지 반영된 대상 브랜치 위에서 시작하게 한다.
- SPEC 작성 도구·작성 형식에 비결합 — **파일로 존재하고 읽을 수 있는 SPEC이면** 무엇이든 입력으로 받는다.

## ② 사용자·호출 시나리오

| 시나리오 | 호출자 | 흐름 |
|---|---|---|
| 여러 SPEC 일괄 구현·머지 | 사람·상위 워크플로(spec 스킬의 옵트인 핸드오프) | `start <spec...>` → 의존 순서대로 워커들이 구현→리뷰→머지, 전부 done이면 0 exit |
| 단일 SPEC 구현·머지 | 사람 | SPEC 1개로 `start` — 동일 절차(머지까지)로 진행 |
| 중단된 run 재개 | 사람·오케스트레이터 | `start --resume <run-id>` → 이미 done인 SPEC은 재실행하지 않고 미완만 이어서 스케줄 |
| 진행 관찰 | 사람 | `list`(모든 run 요약), `status <run-id>`(per-SPEC 상태 표), `watch <run-id>`(터미널 도달까지 폴링), `driver <run-id>`(선택된 fan-out 드라이버 확인) |
| run 중지 | 사람 | `stop <run-id>` → 진행 중 워커를 멈추고 failed 처리, 이행적 의존자 skipped |
| 누적 stale 브랜치 정비 | 사람(명시 요청) | `sweep [--target-branch <b>]` → dispatch 자기 출처 브랜치 중 머지 확인된 것만 일괄 삭제 |
| 결정적 동작 검증 | 개발·CI | 외부 인터페이스(구현 스킬·git·forge)를 주입 mock으로 치환한 자체 검증 서브커맨드로 실제 PR·머지 없이 스케줄링·게이트 규칙을 검증 |

## ③ 기능 요구사항 (동작 정의)

### 입력·DAG 구성

- 입력은 1개 이상의 SPEC 파일 경로(가변 인자)다. 각 경로가 파일로 존재하고 읽을 수 있어야 하며, 하나라도 누락이면 보고 후 즉시 중단한다.
- 의존 관계는 각 SPEC frontmatter의 `depends_on:`(sibling slug 또는 경로) 항목만으로 구성한다 — 외부 DAG 명세 파일을 요구하지 않는다.
- cycle이 발견되면 cycle 구성 요소를 보고하고 실행을 시작하지 않는다(0이 아닌 종료).
- 위상 정보는 진단용으로만 산출물에 남기고, 실제 실행은 wave 배리어가 아니라 SPEC별 준비도로 구동한다.
- 입력 SPEC의 frontmatter 형식·내용 검증은 하지 않는다(워커·구현 스킬 책임).

### 상태 모델·준비도 스트리밍

- per-SPEC 상태는 `pending`/`running`/`done`/`failed`/`skipped`의 5값이다. `done`은 "대상 브랜치에 머지됨"을 뜻하며, 워커의 머지 보고로만 전이한다.
- **준비도 스트리밍**: 각 SPEC은 자신의 `depends_on`이 모두 `done`이 되는 즉시 — 같은 위상의 무관한 SPEC이 아직 실행 중이어도 기다리지 않고 — 동시성 상한 이내에서 시작된다. 기본 동시 실행 상한은 없고 `--max-parallel N`으로 전역 상한을 줄 수 있다.
- **이행적 실패 전파**: 한 SPEC이 `failed`로 끝나면 그 SPEC의 **이행적 의존자만** `skipped`로 차단하고, 의존 관계가 없는 가지는 끝까지 실행한다(전면 fail-fast 아님).
- 호출마다 결정성 있는 `run-id`(타임스탬프 + 입력 SPEC 집합 해시 7자)를 만들고 진행 상태를 run 디렉토리에 보관한다. SPEC 식별 키는 `<slug>-<sha7>`(slug는 가독용, sha7은 SPEC 절대경로 해시)로 다른 날짜·디렉토리의 동명 SPEC 충돌을 방지한다.
- `--resume <run-id>`로 재호출되면 보관된 manifest로 재개한다: `done`인 SPEC은 재실행하지 않고 미완 SPEC만 다시 스케줄하며, run 전역 사실(서브모드·대상 브랜치·동시성 상한·드라이버)은 run 디렉토리 마커로 영속되어 현재 환경 변수·플래그보다 **우선한다(sticky)**.

### 워커 위임 — 준비된 SPEC당 정확히 1개

- 준비된 SPEC마다 워커를 **정확히 1개** 띄우고, 그 워커가 한 컨텍스트에서 구현→리뷰→재구현→머지를 닫는다. 워커 절차의 단일 출처는 **워커 계약 문서**이며, dispatch가 그 전문을 워커 생성 프롬프트에 그대로 포함(embed)한다.
- 워커는 **범용 서브에이전트 타입**으로 띄운다 — 부모 세션 권한을 상속해 백그라운드에서도 구현 스킬·결정적 헬퍼를 권한 거부 없이 호출할 수 있어야 한다(독립 권한 컨텍스트의 전용 에이전트 타입은 쓰지 않는다; 계약 강제가 프롬프트 전달로 약해지는 대신 dispatch가 결과·격리를 관찰해 보완한다).
- 워커 생성 시 입력으로 `spec`(SPEC 경로)·`target-branch`·`run-dir`·`key`를 넘긴다.
- 워커의 결과(머지됨/비완료)는 **구조화된(기계 판독) 보고**로 받아 판정한다 — 자유 텍스트 부분 문자열 일치에 의존하지 않는다.
- **블랙박스 경계**: dispatch는 워커가 내부에서 호출하는 `loop`·`review`의 내부 신호 파일·워크트리·하니스를 직접 들여다보지 않는다. 워커 자신도 loop 종료를 loop의 공개 구조화 상태(`status --json`의 `.state`·`.signals[]`)로만 판정한다.

### 워커 계약 (워커가 따라야 하는 요구사항)

- **구현은 오직 격리 구현 스킬로**: 구현은 반드시 `Skill(skill="autopilot:loop", args="start <spec>")`로 한다. 이 호출은 **포그라운드 블로킹 단일 실행**이다 — 워커는 반환될 때까지 자기 턴을 끝내지 않으며, 같은 호출을 백그라운드로 띄우거나 완료를 기다리며 턴을 종료하지 않는다(백그라운드로 띄우면 워커 턴 종료 시 실행이 죽어 산출 없이 실패한다). 이 원칙은 워커가 직접 구동하는 임의의 장시간 스킬·구동에 동일하게 적용된다. 단 호출 세션이 디스크 아티팩트로 진행을 비차단 관찰하는 것은 금지 대상이 아니다.
- 워커는 대상 파일을 직접 편집하거나 git 명령으로 직접 구현하지 않으며, 구현 스킬의 내부 구동부를 직접 실행하지 않는다(구현 스킬이 전용 격리 워크트리를 만들고 소유한다).
- **통합·리뷰 반복·머지는 오직 결정적 헬퍼로** 수행한다. raw forge PR 생성·머지 명령, raw `git push`, 임의 머지를 직접 수행하지 않는다.
- **서브모드 = 백엔드 가용성**: forge CLI 가용 여부로 run 시작 시 한 번 판정되어 run 전역으로 영속된다(resume sticky).
  - **forge(가용)**: 로컬 `autopilot:review` 스킬을 호출하지 않는다. 작업 브랜치를 push해 PR을 생성/재사용하고 **PR의 호스팅측 리뷰**를 받는다. 호스팅 리뷰는 비동기로 도착하므로 리뷰 미도착(pending)은 transient이며 에스컬레이션 사유가 아니다 — 도착까지 기다린다. 워커는 **자기 PR을 스스로 리뷰·승인하지 않는다**(자기승인 우회 방지; 승인은 분리 신원의 호스팅 리뷰 담당). **approve(머지 가능)의 정의**: ⑴ PR 리뷰 지적 중 타당한 것이 모두 해결되고(블로킹뿐 아니라 — `rules/change-adoption.md` 기준 채택) ⑵ approve 상태 변경 또는 승인 코멘트가 있는 상태 — 둘 다 만족할 때만 머지한다.
  - **direct(미가용)**: 로컬 `autopilot:review` 스킬로 적대 리뷰·판정하고 `approve`일 때만 머지한다. forge CLI·원격 push가 필요 없다.
- **승인 후에만 머지**: 승인이 없거나 판정이 `request_changes`면 같은 작업 브랜치 위에서 구현 스킬로 재구현→재리뷰를 반복하되, 무한루프 가드에 걸리면 **머지 없이 에스컬레이션**한다. 거짓 green 금지.
- **보고**: 워커의 마지막 메시지는 사람 대상 산문이 아니라 정확히 JSON 한 개다 — `{"key", "result": "merged"|"escalated", "target_branch", "work_branch", "pr", "detail"}`. `result="merged"`는 실제로 대상 브랜치에 머지된 경우만 쓴다.

### 통합 (loop 종료 → 리뷰 요청의 다리)

- 워커 종료 의도는 구현 스킬의 공개 구조화 상태로만 읽어 분기한다: **DONE(차단 없음)** → 대상 브랜치 기준 base 동기화(fast-forward 가능할 때만 rebase) → 작업 브랜치 push → PR 생성/재사용(같은 head의 open PR이 있으면 재사용) → 리뷰 단계로. **BLOCKED `spec-gap`** → push·PR 없이 스펙 보강 재개 안내로 분기. **BLOCKED 그 외 하드 범주** → push·PR 없이 사람 에스컬레이션으로 분기.
- 작업 브랜치 이름은 `feat/<run-id>-<slug>` 규칙을 따른다(브랜치·slug 규칙은 프로젝트 규칙이 단일 출처).
- 어떤 경로에서도 force push·force rebase를 하지 않는다.

### 리뷰 반복 (한 호출 = 한 라운드)

- 리뷰 생산자(`autopilot:review` 또는 호스팅 리뷰)의 단일 머신리더블 판정(approve/request_changes/unavailable)과 분류된 재작업 브리프(must_adopt/defer/wont_adopt)를 소비한다 — 채택 분류 규칙은 리뷰 생산자가 적용하며 재정의하지 않는다.
- 판정 분기: `request_changes` → 반드시-반영(must_adopt) 지적을 run 디렉토리 하위 SPEC 델타로 만들어 **같은 head 브랜치 위에서** 자율 구현하고 같은 브랜치로 push한다(새 PR 미생성·force 금지). 라운드 카운터 증가. defer 지적은 현 PR에 섞지 않고 run 디렉토리에 별도 기록(백로그 분리). `approve` → 머지 진행 가능(추가 라운드 미시작). `unavailable` → 에스컬레이션.
- **사람/head 게이트**: 열린 PR의 최신 정식 리뷰가 **사람** 리뷰어의 변경 요청이면 자동수정하지 않고 에스컬레이션한다. head가 직전 처리분과 같으면 멱등 no-op.
- **무한루프 가드(세 겹)**: 라운드 상한(기본 3) 초과 / 반드시-반영 지적이 0인데 request_changes(무진전) / 차단성 지적 집합이 직전 라운드와 동일(핑퐁) — 어느 하나면 에스컬레이션한다.

### 머지 (파이프라인 종착)

- **버전 범프 게이트**: 머지될 변경이 워치 디렉토리(기본 `plugins/`)를 건드리면 같은 변경 안에서 플러그인 버전이 올랐는지 단언한다. 안 올랐으면 머지를 차단한다(비완료 종착; 버전 규칙은 프로젝트 규칙이 단일 출처).
- 머지는 대상 브랜치에 **fast-forward 전용**으로만 수행한다(머지 커밋·force 금지). 한 run 안의 머지 구간은 **직렬화**되어 동시 머지 레이스가 발생하지 않아야 한다.
- 분리 승인 신원(approver)을 머지 전제로 요구하지 않는다 — 승인 수렴 판정은 리뷰 게이트 책임이고, 머지는 버전 게이트 통과 시 가용한 forge 토큰으로 수행한다. direct 서브모드는 PR 없이 로컬 작업 브랜치를 ff 머지한다.
- 머지 확인되면 해당 SPEC의 통합 단계를 merged로 기록하고(오케스트레이터가 done으로 전이), 작업 공간 정리를 위임한다.

### 정리 정책 (비대칭 — 결정적 헬퍼가 단일 출처)

- **작업 브랜치**: 머지 성공 시에만, ff-머지 확정 **이후** force 없는 일반 삭제로 정리한다(원격, 있으면 로컬). 실패/비완료로 끝나면 **보존**한다(재개·디버깅). 워커·dispatch 모두 raw 원격 명령으로 직접 삭제하지 않는다.
- **워크트리**: 터미널 도달 시 작업이 **원격 브랜치로 보존돼 있으면** 구현 스킬의 공개 cleanup 위임으로 그 고아 워크트리를 정리하고, **미보존(워크트리가 유일 사본)이면 보존**한다. 비터미널이면 정리하지 않는다. 워커·dispatch는 워크트리를 직접 삭제하지 않는다(블랙박스 경계).
- 워커가 에스컬레이션으로 종료하면 통합 단계가 위 조건부 워크트리 정리를 자동 수행하고, dispatch가 워커를 timeout/stop으로 `failed` 종료시킨 직후에도 **동일 정책**의 정리 진입점을 호출한다.
- **정리 실패는 경고로 표면화**되며(조용한 실패 금지) 머지·완료 판정을 뒤집지 않는다.

### fan-out 드라이버 (실행 환경 역량 라우팅)

- fan-out 단계(준비된 SPEC마다 워커 1개 진행)는 환경 역량에 따라 세 드라이버 중 하나로 구동된다: `strong-parallel`(런타임이 병렬·스트리밍·재개를 네이티브 소유 — 의존성 충족 즉시 노드별 워커 실행) / `background`(워커를 비동기로 띄우고 개별 완료 신호마다 상태 전이·의존자 해제) / `foreground-batch`(준비분 동시 시작 → 배리어 → 준비도 재평가; 안전 폴백).
- 세 드라이버는 동일한 **결정적 코어**(준비도·상태 전이·skip 전파·워커 계약·머지/리뷰 게이트)를 공유하고 fan-out 진행 방식만 다르다 — 호출자에게 노출된 시작 인터페이스는 드라이버와 무관하게 동일하며, 선택은 내부에서 일어난다.
- **기본 선호는 `strong-parallel`**이다(신호 없으면 동적 시도). 자동 감지는 실행 환경(세션) 속성이라 대상 리포 파일로 결정적 판별이 불가하므로 오케스트레이터(모델)가 세션 가용 역량으로 판정하고, 동적 실행이 불가할 때만 강등 신호를 주입한다. **안전 강등 사슬**은 `strong-parallel → background → foreground-batch` 순(건너뛰기 없음)이다. fan-out 항목이 1개여도 동적으로 구동한다.
- 운영자는 환경 변수 override(`DISPATCH_DRIVER`)로 드라이버를 강제할 수 있다(기본 선호·자동 판정 무시; 무효 값이면 즉시 중단). 어느 드라이버로 갔는지는 `driver`·`status` 서브커맨드로 **관찰 가능**해야 하며, 최초 결정은 run 디렉토리 마커로 영속되어 resume에서 sticky하다(마커 없는 레거시 run은 `foreground-batch`로 표시).
- 워커 **내부 단계(구현→리뷰→재구현→머지)는 어느 드라이버에서든 데이터 의존 순서대로 동기** 진행되며, 실패 이행 격리·승인 후 ff-only 머지 같은 안전 불변식도 드라이버와 무관하게 동일하다.

### 백그라운드 워커 진행 모니터

- 워커를 백그라운드로 띄울 때 dispatch는 워커가 남기는 **디스크 아티팩트**(구현 스킬의 상태/신호, 작업 브랜치 커밋, PR·리뷰 판정, dispatch SPEC 상태)에 기반해 진행을 관찰하는 모니터를 자동 설치한다. 가용한 환경 수단으로 설치하되 특정 모니터링 도구에 하드 종속하지 않는다.
- 모니터는 **읽기 전용**이다(워커·워크트리·신호·하니스 불변경). 관찰 상태가 바뀔 때만 진행을 표면화하고(중복 방출 금지), 워커가 산출 없이 죽거나 정지한 조용한 실패가 드러나게 한다.
- run(또는 해당 SPEC)이 종료 상태에 도달하면 모니터를 종료한다 — 고아 모니터를 남기지 않는다.
- 모니터 수단이 없는 환경에서는 자동 설치를 안전하게 생략하며, 진행은 여전히 디스크 아티팩트 폴링으로 관찰 가능하다(**아티팩트가 진행의 단일 출처**).

### stale 브랜치 일괄 정리 (sweep)

- 머지 시점 단건 정리가 다루지 못하고 누적된(정책 도입 이전·외부 수동 머지) dispatch 작업 브랜치는 **명시 요청** `sweep`으로만 소급 청소한다(자동 무인 파괴 아님).
- **자기 출처(provenance)만 대상**: dispatch 전용 네이밍 시그니처(`feat/<run-id>-<slug>`, `<run-id>`=`<YYYYMMDDTHHMMSS>-<sha7>`)에 맞는 브랜치만 대상으로 하며, 사람·타 도구가 만든 브랜치는 이름이 유사해도 제외한다.
- **머지 확인된 것만 삭제**: 대상 브랜치의 조상(=머지됨)인 것만 force 없이 일반 삭제(원격, 있으면 로컬)하고, 미머지 브랜치는 절대 삭제하지 않는다.
- 식별·삭제는 결정적 헬퍼가 소유한다(raw 원격 명령 직접 삭제 금지). 한 브랜치 삭제 실패는 경고로 격리되어 다른 브랜치 처리를 막지 않으며, 어떤 브랜치를 지웠고 어떤 것을 건너뛰었는지(미머지·실패) 보고한다.

### 타임아웃·중지·오류 동작

- 한 워커가 per-SPEC 실행 시간 상한(`DISPATCH_WAVE_TIMEOUT_SECONDS`, 기본 7200초)을 초과하면 그 워커를 정상 종료 시도 후 강제 종료로 정리하고 `failed`로 마킹한다(이미 done이면 보존). 직후 실패-경로 조건부 워크트리 정리를 적용한다.
- `stop`은 진행 중 SPEC을 `failed`로 표시하고 이행적 의존자에 skipped를 전파하며, 해당 워커 중지는 살아있는 오케스트레이터가 수행한다. stop으로 failed가 된 SPEC에도 동일한 실패-경로 정리를 적용한다.
- 입력 파일 누락·cycle·알 수 없는 서브커맨드/상태 값·무효 드라이버 override는 표준 에러 보고와 함께 0이 아닌 코드로 중단한다.

## ④ 인터페이스 (호출 형태·입력·출력·산출물)

### 호출 형태

`Skill(skill="dispatch", args="<subcommand> [<args>]")`.

| subcommand | 인자 | 역할 |
|---|---|---|
| `start` | `<spec...> [--max-parallel N] [--resume <run-id>] [--target-branch <branch>]` | 새 run 시작(또는 재개). run-id를 출력하고 준비도 순으로 워커를 진행 |
| `list` | — | 모든 run-id와 진행 요약 |
| `status` | `<run-id>` | per-SPEC 상태 표(진단용 wave 번호 포함) + 선택된 fan-out 드라이버(`driver:` 라인) + 구현 스킬 라이브 상태 |
| `driver` | `<run-id>` | run의 fan-out 드라이버 출력(자동 선택·override·강등 결과의 관찰 진입점) |
| `stop` | `<run-id>` | 진행 중 워커 중지 위임·failed 처리·의존자 skipped 전파 |
| `watch` | `<run-id>` | 모든 SPEC이 터미널(done/failed/skipped)에 도달할 때까지 읽기 전용 폴링 후 결과를 exit code로 대표 |
| `sweep` | `[--target-branch <branch>]` | dispatch 자기 출처·머지 확인 브랜치만 일괄 삭제(명시 요청 정비) |
| `selftest` | — | 주입 mock 기반으로 결정적 스케줄링·게이트 규칙을 검증 |

- `--target-branch`는 머지·동기화 대상 브랜치를 지정한다(미지정 시 기본 브랜치). run 전역으로 결정되어 모든 워커의 base 동기화·리뷰·ff 머지에 일관 적용된다.
- 하위 호환을 위해 `--integrate`/`--no-integrate`를 받되 무시한다(no-op).

### 입력

- 1개 이상의 SPEC 파일 경로(파일로 존재·읽기 가능하면 형식 불문). 의존 관계는 SPEC frontmatter `depends_on`만 사용.
- **주입 가능 환경 변수**(외부 인터페이스 — 운영자 설정·mock 검증용): `DISPATCH_POLL_SECONDS`(watch 폴링 간격, 기본 2초) · `DISPATCH_WAVE_TIMEOUT_SECONDS`(per-SPEC 실행 상한, 기본 7200초) · `DISPATCH_DRIVER`(드라이버 강제) · `DISPATCH_NO_STRONG_PARALLEL=1`/`DISPATCH_NO_BACKGROUND=1`(강등 신호) · `FORGE_BIN`(서브모드 판정용 forge CLI) · `DEFAULT_BRANCH`(기본 브랜치) · `LOOP_CMD`/`GIT_CMD`/`FORGE_CMD`(구현 스킬·git·forge 호출 치환, forge 기본 `gh`) · `REVIEW_ROUNDS_MAX`(리뷰 라운드 상한, 기본 3) · `WATCH_DIRS`(버전 게이트 워치 디렉토리, 기본 `plugins/`) · `SWEEP_BRANCH_SIGNATURE_RE`(sweep 대상 시그니처).

### 출력·산출물

- `start`는 run-id를 출력한다. `status`는 per-SPEC 상태 표를, `driver`는 드라이버 이름 한 값을 출력한다.
- 종료 코드(start·watch): `0`=전부 done, `1`=failed/skipped 있음, `2`=timeout.
- run 상태 산출물: `<project_root>/.dispatch/runs/<run-id>/` 아래에 manifest·진단용 위상 정보·per-SPEC 실행 상태(`<slug>-<sha7>` 키)·로그·run 전역 마커(서브모드·대상 브랜치·동시성 상한·드라이버)·per-SPEC 통합 상태(branch/pr/head/리뷰 라운드/판정/단계)·리뷰 재작업용 SPEC 델타·defer 백로그를 보관한다. run 디렉토리는 git 추적에서 제외한다(`.gitignore` 권장).
- forge 부수효과(서브모드·진행에 따라): `feat/<run-id>-<slug>` 작업 브랜치, PR, 대상 브랜치 ff 머지 커밋, 머지 후 작업 브랜치 삭제.
- 워커 보고(내부 인터페이스이지만 run 판정의 계약): `{"key", "result": "merged"|"escalated", "target_branch", "work_branch", "pr", "detail"}` JSON 한 건.

## ⑤ 비기능 요구사항·제약

- **결정성·검증 가능성**: 오케스트레이션의 결정적 부분(준비도·상태 전이·skip 전파·통합 분기·리뷰 반복 가드·버전 게이트·ff-only 머지·sweep 식별)은 외부 인터페이스(구현 스킬·git·forge)를 주입 mock으로 치환해 **실제 PR·push·머지 없이** 독립 검증 가능해야 한다(모듈별 자체 검증 + 스케줄링 자체 검증).
- **안전 불변식(드라이버·경로 불문)**: force push/rebase/머지 금지, 머지는 ff-only만, 새 PR 남발 금지(같은 head 재사용), 자기승인 금지(forge), 승인 없이 머지 금지, 미머지 브랜치 삭제 금지, 비터미널 워크트리 정리 금지.
- **블랙박스 경계**: dispatch·워커는 `loop`·`review`의 내부 신호 파일·워크트리·하니스를 열람·변경하지 않고 공개 인터페이스(구조화 상태·cleanup 위임)만 쓴다.
- **상태 격리**: 자체 작성·갱신 영역은 run 디렉토리(`.dispatch/runs/<run-id>/`)와 본 스킬 정의 파일뿐이다. forge 부수효과를 제외하면 이 외 경로를 만들지 않는다.
- **단일 출처 원칙**: 브랜치·slug 네이밍은 프로젝트 규칙, 버전 게이트는 버전 관리 규칙, 리뷰 채택 분류는 `rules/change-adoption.md`를 실행자로서 따르고 재정의하지 않는다. 워커 절차는 워커 계약 문서가, 정리 정책은 결정적 헬퍼가 단일 출처다.
- **의존성**: 결정적 헬퍼는 git·bash 3.2+ 수준 셸 호환(연관 배열 비의존)·sha256 해시 유틸·YAML frontmatter 파싱 도구(`depends_on` 파싱, start만 요구)를 쓴다. 워커는 `autopilot:loop`·`autopilot:review` 스킬과 JSON 처리 도구를 쓰며, forge 서브모드만 forge CLI(기본 `gh`, 주입 가능)를 추가로 요구한다 — direct 서브모드는 forge CLI·원격 push 비의존.
- **재진입성**: 같은 run-id 재호출·resume은 완료분을 재실행하지 않아야 하며, 리뷰 라운드는 head 동일 시 멱등이어야 한다.

## ⑥ 비-목표 (Out of scope)

- SPEC의 작성·분해(여러 SPEC으로 나누기) — SPEC 작성 도구(`autopilot:spec` 등)의 책임. dispatch는 이미 만들어진 SPEC들만 받는다.
- SPEC frontmatter 형식·내용의 검증 — 워커·구현 스킬 책임.
- 구현 자체 — `autopilot:loop`이 격리 워크트리에서 소유한다. dispatch·워커는 대상 파일을 직접 편집하지 않는다.
- 리뷰 생산(판정·지적 생성) — `autopilot:review` 또는 호스팅 리뷰의 책임. dispatch 계열은 판정을 소비만 한다.
- 통합·리뷰·머지의 무인 스크립트 파이프라인 직접 수행 — SPEC당 한 컨텍스트의 워커가 소유한다.
- 리뷰 원칙·채택 분류·브랜치 네이밍·버전 규칙의 정의 — 프로젝트 규칙이 단일 출처.
- `loop`·`review` 내부 상태의 열람·조작 — 공개 인터페이스만 사용.
- stale 브랜치의 자동(무인) 정리 — sweep은 명시 요청 진입점일 뿐이다.

## ⑦ 성공 기준

- 의존 관계가 있는 SPEC 묶음에서 각 SPEC이 자신의 의존이 **모두 머지된 뒤에야** 시작되고, 무관한 SPEC은 서로를 기다리지 않는다(wave 배리어 없음).
- 한 SPEC의 실패는 그 이행적 의존자만 skipped로 만들고, 독립 가지는 끝까지 실행되어 머지된다.
- `done`으로 전이된 모든 SPEC은 실제로 대상 브랜치에 머지되어 있다 — 워커의 구조화 보고 `merged` 없이 done이 되는 경로가 없다.
- 승인 게이트(forge: 타당 지적 전부 해결+승인 / direct: 로컬 approve) 없이 머지되는 경로가 없고, 어떤 경로에서도 force·비-ff 머지·자기승인이 발생하지 않는다.
- 리뷰 반복은 가드(라운드 상한·무진전·핑퐁) 안에서만 돌고, 가드 소진·unavailable·사람의 변경 요청에서는 머지 없이 에스컬레이션된다.
- 같은 run-id의 재개는 완료분을 재실행하지 않으며, 서브모드·대상 브랜치·드라이버가 최초 결정대로 유지된다(sticky).
- 머지 성공한 작업 브랜치는 정리되고 실패분은 보존되며, 워크트리는 원격 보존 시에만 정리된다 — 미머지 브랜치·유일 사본 워크트리가 삭제되는 사례가 없다.
- sweep은 dispatch 자기 출처·머지 확인 브랜치만 삭제하고 그 외(사람·타 도구·미머지)는 이름이 유사해도 보존하며, 삭제·건너뜀을 보고한다.
- 선택된 fan-out 드라이버가 항상 관찰 가능하고, 드라이버가 무엇이든 워커 내부 순서·안전 불변식·최종 결과가 동일하다.
- 결정적 스케줄링·게이트 규칙이 실제 PR·머지 없이 mock 주입만으로 재현·검증된다.
- run 종료 후 run 디렉토리·forge 부수효과 외의 새 파일·고아 모니터가 남지 않는다.

# 역PRD — autopilot `using-autopilot` 스킬

> **문서 성격**: 현재 구현에서 제품 요구사항을 역추출한 재구현 기준서(역PRD). 구현 방법(HOW)은 싣지 않는다.
>
> **근거 소스 범위**: 이 리포지토리 `plugins/autopilot/skills/using-autopilot/`의 `SKILL.md` 전체(이 스킬은 `references/` 하위 모듈을 갖지 않는다).
> **기준 플러그인 버전**: autopilot `0.38.1` (작성 시점 스냅샷 — 이후 스킬 변경 시 본 문서와 드리프트가 생길 수 있다).

## ① 개요·배경·목적

`using-autopilot`은 autopilot이 설치된 프로젝트의 **세션 시작 시 활성화되는 워크플로 진입점(라우터)**이다. 사용자 발화에서 새 코드 변경 신호를 감지하면, 다른 어떤 응답·도구 호출·탐색보다 먼저 `spec` 스킬로 라우팅하는 것을 강제한다.

배경: autopilot의 파이프라인은 "새 코드 변경은 의도를 먼저 자기완결적 SPEC 문서로 뜨는 것"에서 출발한다. 그러나 에이전트는 "일단 코드를 보고", "사소하니까 바로 짜고" 같은 합리화로 이 첫 단계를 건너뛰기 쉽다. 이 스킬은 그 라우팅 누락을 규범 수준에서 차단한다.

목적(존재 이유):

- 새 코드 변경 작업이 SPEC 없이 시작되는 것을 방지한다 — 의도(검증 가능한 완료 조건) 없이 구현하지 않는다.
- 일반 규칙(brainstorming-first 류의 창작 작업 사전 탐색 강제)을 autopilot 설치 프로젝트의 새 코드 변경에 한해 **명시적으로 대체(override)**해, spec이 첫 단계가 되도록 우선순위를 고정한다.

## ② 사용자·호출 시나리오

| 시나리오 | 동작 |
|---|---|
| 세션 시작 | autopilot 설치 프로젝트에서 세션이 시작되면 이 스킬의 라우팅 규범이 활성화된다 |
| 사용자가 기능 추가·수정·생성을 요청 | 다른 응답에 앞서 `Skill(skill="spec", args="<자연어 task 설명>")` 호출 |
| 사용자가 기존 SPEC 구현을 요청 | 코드-변경 신호로 간주, spec 먼저 |
| 사용자가 문서·지침 편집을 요청 | 코드-변경 신호로 간주, spec 먼저 |
| 순수 질의·코드 읽기·검색·단순 디버깅·운영 명령 | 라우팅하지 않고 그대로 응답 |
| 사용자가 spec 생략을 명시 지시 | 라우팅하지 않는다(사용자 지침 최우선) |

## ③ 기능 요구사항 (동작 정의)

### 라우팅 강제

- 새 코드 변경 신호를 감지할 때, 시스템은 **다른 어떤 응답·도구 호출·탐색보다 먼저** spec 스킬을 자연어 task 설명과 함께 호출해야 한다.
- 새 코드 변경일 가능성이 조금이라도(1%라도) 있으면 즉시 spec으로 라우팅해야 한다. 사용자가 직접 다른 경로를 지정하지 않는 한 코드·탐색·다른 도구보다 spec이 먼저다. 이 규칙은 협상 대상이 아니다.

### 트리거 (하나라도 해당하면 코드-변경 신호)

- **기능 추가** — "X 기능 만들어줘", "X 추가해줘", "X 붙여줘".
- **동작 수정** — "X 동작 바꿔줘", "X 고쳐줘"(버그 수정 포함; 단순 디버깅은 예외 참조).
- **지침 작성·문서 편집** — 새 규칙·지침 작성 요청과, 기존 지침·문서의 편집·압축·축약·수정·삭제. 문서·지침을 바꾸는 일은 동작·지침을 바꾸는 코드-변경 신호이지 "코드 변경 아님"이 아니다.
- **SPEC 구현** — 기존 SPEC 파일의 구현·구현 확인 요청("`<경로>/SPEC.md` 구현", "이 SPEC 구현해줘"). SPEC 파일의 읽기/검증은 예외지만 구현은 코드-변경 신호다.
- **새로 만들기** — 스킬·플러그인·모듈 등의 신규 생성 의도.

### 합리화 구멍 차단

다음 세 합리화는 분기 누락의 전형이며, 셋 모두 코드-변경 신호로 취급해 spec을 먼저 실행해야 한다(합리화가 옳아 보여도 라우팅한다):

1. **"먼저 코드를 파악·이해하고"** — 이해 필요는 라우팅 예외가 아니다. 탐색·이해는 spec의 컨텍스트 탐색 단계(코드-우선 원칙)가 수행한다.
2. **"기존 SPEC을 구현/확인하는 것뿐"** — SPEC 읽기/검증(예외)과 구현(신호)을 구별한다. 구현 요청은 spec이 먼저다.
3. **"문서·지침 편집은 코드 변경이 아니야"** — 지침·문서의 편집·압축·축약·수정·삭제는 코드-변경 신호다.

또한 다음 사고가 들면 멈추고 spec을 먼저 실행해야 한다(red flags): "일단 brainstorming부터", "너무 사소해서 SPEC까지는", "바로 코드부터", "먼저 코드베이스를 둘러보고", "사용자가 그냥 만들라고 했으니"("만들어줘"는 WHAT이지 HOW가 아니다).

### 일반 사전-탐색 강제와의 관계 (명시적 override)

- 범용 지침이 창작 작업에 brainstorming-first 류의 사전 탐색 단계를 강제하더라도, autopilot이 설치된 프로젝트에서 위 트리거에 해당하는 새 코드 변경 작업에 한해 **그 강제를 대체**하고 spec을 첫 단계로 삼아야 한다.
- 우선 근거: ⑴ specificity — "autopilot 설치 + 새 코드 변경 신호"가 더 좁은 조건이므로 일반 규칙을 이긴다. ⑵ 기능 동치 — spec의 명확화 인터뷰가 의도·범위·제약 탐색을 수행하므로 설계 탐색이 누락되지 않고 spec 안으로 들어온다. ⑶ 파이프라인 정합 — 산출물(자기완결 SPEC)이 곧바로 execute-task의 입력이 된다.
- 마일스톤 규모(다중 독립 서브시스템)도 spec의 범위 분해 게이트가 처리하므로 별도 사전 brainstorming이 필요 없다.

### 예외 (라우팅 불필요)

- 이미 진행 중인 spec 워크플로의 연속, 또는 `--resume` 마커 해소.
- 새 코드 변경이 아닌 작업: 순수 질의응답, 코드 읽기·설명, 검색, 단순 디버깅(원인 조사·로그 분석), 운영 명령(테스트 실행·상태 조회).
- 사용자가 spec 생략을 **명시적으로** 지시한 경우(사용자 지침 최우선).
- 예외 적용의 대칭 규칙: 합리화 구멍 차단의 세 경우를 예외로 끌어오는 것도, 정당한 예외(질의·읽기·검색·디버깅·운영)를 게이트로 끌어오는 것도 모두 오류다.

## ④ 인터페이스 (호출 형태·입력·출력·산출물)

- **활성화 형태**: 세션 시작 시 자동 활성화되는 라우팅 규범(사용자가 서브커맨드로 직접 호출하는 스킬이 아니다). 사용자 가시 동작은 "새 코드 변경 요청 → spec 인터뷰가 먼저 시작됨"이다.
- **입력**: 사용자의 자연어 발화(의도 신호).
- **출력**: 트리거 일치 시 `Skill(skill="spec", args="<자연어 task 설명>")` 호출. 그 외에는 통상 응답.
- **산출물**: 자체 산출물 없음. 후속 파이프라인은 `새 코드 변경 신호 → autopilot:spec → docs/specs/<날짜>-<slug>/SPEC.md(자기완결 SPEC) → (옵트인) execute-task`이며, spec은 외부 상태(이슈·브랜치·원격)를 만들지 않고 SPEC 문서만 산출한다.
- **오류·차단 시 동작**: 이 스킬은 자체 오류·차단 상태를 갖지 않는다(순수 라우터 — 파일·프로세스·외부 상태가 없어 실패 모드가 없다). 라우팅 판단이 불확실하면 차단·오류가 아니라 spec 라우팅 쪽으로 기운다(민감도 우선). 라우팅 이후의 오류·차단 처리(마커에 의한 자율 실행 차단, 구현 중 BLOCKED 등)는 후속 스킬(spec·execute-task·loop·review)이 소유한다.

## ⑤ 비기능 요구사항·제약

- **선응답 강제 강도**: 라우팅은 다른 어떤 응답·도구 호출보다 선행해야 하며 최고 우선 규범으로 표기된다(협상 불가).
- **민감도 우선**: 위양성(불필요한 spec 인터뷰)이 위음성(SPEC 없는 코드 변경)보다 낫다는 설계 — "1%라도 가능성이 있으면 라우팅".
- **사용자 주권**: 사용자의 명시적 생략 지시가 항상 이긴다.
- **무산출·무상태**: 이 스킬 자체는 파일·외부 상태를 만들지 않는 순수 라우터다.

## ⑥ 비-목표 (Out of scope)

- SPEC 작성·인터뷰 수행 — spec 스킬의 책임이다(이 스킬은 라우팅만 한다).
- 구현·리뷰·머지 오케스트레이션 — execute-task/loop/review의 책임.
- 새 코드 변경이 아닌 작업(질의·읽기·검색·디버깅·운영 명령)의 처리 방식 규정.
- spec 이후 단계로의 자동 진행 결정 — execute-task 핸드오프는 spec의 옵트인 절차가 소유한다.

## ⑦ 성공 기준

- autopilot 설치 프로젝트에서 트리거에 해당하는 모든 새 코드 변경 요청이 코드·탐색·기타 도구 사용 전에 spec 인터뷰로 진입한다(라우팅 누락 0).
- 세 합리화(이해-먼저, SPEC-구현, 문서-편집) 경로로 게이트가 우회되지 않는다.
- 정당한 예외(질의·읽기·검색·단순 디버깅·운영 명령, 진행 중 spec 연속, 명시적 생략 지시)는 라우팅 없이 즉시 처리된다(과차단 없음).
- 범용 사전-탐색 강제와 충돌할 때 본 규칙이 우선해, 새 코드 변경의 첫 단계가 항상 spec이 된다.

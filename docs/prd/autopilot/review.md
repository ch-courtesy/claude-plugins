# 역PRD — autopilot `review` 스킬

> **문서 성격**: 현재 구현에서 제품 요구사항을 역추출한 재구현 기준서(역PRD). 구현 방법(HOW)은 싣지 않는다.
>
> **근거 소스 범위**: 이 리포지토리 `plugins/autopilot/skills/review/`의 `SKILL.md`와 `references/` 하위 모듈 전체(lens dispatch brief, 출력 스키마, 결정적 중재 하니스). 하니스 구현부에서는 사용자 가시 동작(서브커맨드·판정 규칙·산출물 경로·오류 동작)만 추출했다.
> **기준 플러그인 버전**: autopilot `0.38.1` (작성 시점 스냅샷 — 이후 스킬 변경 시 본 문서와 드리프트가 생길 수 있다).

## ① 개요·배경·목적

`review`는 **원샷 리뷰 생산자**다. 한 작업의 변경(diff)을 입력으로 받아 여러 독립 관점으로 리뷰하고, 단 하나의 머신리더블 판정(`approve`·`request_changes`·`unavailable` 중 정확히 하나)과 근거 있는 지적 목록(findings), 그리고 차단성 지적이 있을 때는 분류된 재작업 브리프를 산출한다.

배경: 자율 구현 파이프라인에서 머지 게이트가 신뢰할 수 있으려면 ⑴ 리뷰 결과가 사람 해석 없이 기계가 소비할 수 있는 단일 판정이어야 하고 ⑵ 지적이 근거(증거·신뢰도) 기준을 통과한 것만 남아야 하며 ⑶ 같은 지적이 라운드마다 중복 게시되지 않아야 하고 ⑷ 판단이 LLM의 비결정성에 좌우되지 않는 결정적 규칙으로 합성되어야 한다. review는 이를 "LLM은 발견만, 판정은 결정적 중재 게이트가"라는 역할 분리로 해결한다.

목적(존재 이유):

- 한 작업의 변경에 대해 **리뷰를 생산하기만** 한다 — 재구현·재푸시·승인까지의 반복(iterate-until-approved), forge로의 자동 approve/merge, 머지 게이트 결정은 소유하지 않는다(오케스트레이터·머지 규칙의 책임). 판정은 머신리더블 산출물일 뿐이다.
- 독립 다관점 리뷰(합의 투표 아님)와 결정적 중재(증거 게이트·중복 제거·커버리지·판정 합성)를 분리해, 결정적 부분을 실제 PR·브랜치 아티팩트 없이 검증 가능하게 한다.

## ② 사용자·호출 시나리오

| 시나리오 | 호출자 | 흐름 |
|---|---|---|
| 머지 전 변경 리뷰 | 상위 오케스트레이터(dispatch의 워커 등) | `run --task <id>` → 단일 판정 JSON을 받아 머지 게이트 판단(게이트 결정은 호출자 몫) |
| 수동 리뷰 요청 | 사람 | 동일하게 `run` 호출 후 findings·재작업 브리프를 읽고 직접 조치 |
| 재작업 후 재리뷰 | 오케스트레이터 | 같은 작업으로 `run` 재호출 — 이전 라운드에 게시된 지적과 같은 지적은 중복으로 걸러지고 스레드 해소/유지가 보고됨 |
| 마지막 판정 조회 | 사람·오케스트레이터 | `status --task <id>`로 마지막 판정·라운드 수·지적 fingerprint 확인 |
| 전체 현황 요약 | 사람·오케스트레이터 | `list`로 리뷰 상태가 있는 작업들을 요약(빈 상태에서도 정상 종료) |
| 결정적 동작 검증 | 개발·CI | 외부 인터페이스를 주입 mock으로 치환한 자체 검증 서브커맨드로 실제 PR·브랜치 없이 판정 규칙을 검증 |

## ③ 기능 요구사항 (동작 정의)

### 단위·역할 분리

- 리뷰 단위는 **한 작업의 변경(diff)**이며 작업 식별자(또는 PR·diff 참조)로 입력한다.
- 역할은 둘로 분리된다: **LLM 다관점 lens 리뷰**는 워커가 서브에이전트로 수행하고, **결정적 중재**(diff 수집·fingerprint·신뢰도 게이트·판정 산출·스레드 라이프사이클)는 하니스가 수행한다. 하니스는 LLM을 호출하지 않는다.
- 상태는 자기 상태 저장소(작업별 디렉토리) 아래에만 보관하며, 스킬은 자기 상태·자기 정의 파일 **밖 경로를 만들지 않는다**.

### 리뷰 관점 (4 lens, 독립)

서로의 결론을 보지 못하는 **독립 판단**으로 수행한다(합의 투표 아님). 워커는 4 lens를 병렬로 dispatch한다.

1. **SPEC 수용기준 준수** (`spec_compliance`) — 각 수용기준에 대해 대응 변경의 존재(Existence)·실질(Substantive: stub/mock/TODO 아님)·연결(Wired: 실제 호출처 연결)을 검증하고, 충족 확인된 기준 id를 `verified_criteria`로 보고. 미충족·부분충족은 차단성 발견으로 보고.
2. **정확성·보안** (`bug`) — 변경 hunk 자체의 명확한 correctness/security/reliability 버그만. 스타일·취향·네이밍·포맷, 근거 없는 성능 추측, 범위 밖 기존 문제, 정적 도구가 잡을 문제는 보고하지 않는다. 보안·데이터 손실·계약 위반은 차단성.
3. **회귀·역사적 맥락** (`history`) — 과거에 의도적으로 만든 동작·계약·불변식을 현재 변경이 회귀시키는지. "중복처럼 보인다"는 load-bearing 강화를 제거할 근거가 되지 않는다.
4. **저장소 가이드라인 준수** (`guideline`) — `CLAUDE.md`·`rules/`·워크플로 문서 등 명시 지침과의 충돌을 규칙·라인 단위로 구체적으로 짚어 보고(막연한 불안 금지). 권한·scope·테스트·완료조건 같은 안전 경계 위반은 차단성.

규모 임계가 충족될 때만 가산 발동하는 적대 렌즈가 필요하면 그 정의는 spec 스킬의 페르소나 카탈로그(contrarian·minimalist·constraint-auditor — 단일 출처)를 **복제하지 않고 참조**한다.

### lens 공통 출력 계약

- 각 lens는 자기 관점의 **발견(findings)만 보고**한다 — 판정·승인·차단을 결정하지 않는다.
- 각 finding은 4증거를 **모두** 갖춰야 하며 하나라도 빠지면 만들지 않는다: ⑴ 변경 위치 링크(파일 + 변경 diff 라인의 양수 라인 번호, null 금지) ⑵ 실패/위험 경로 설명(실제로 무엇이 어떻게 깨지는지) ⑶ 파일·라인 인용(근거가 변경 라인 밖이면 본문 첫 줄에 실제 위치 명기) ⑷ 실행 가능한 제안(수정자가 바로 행동 가능).
- `confidence_score`(0–100)가 80 미만이면 보고하지 않는다(어차피 게이트가 제외).
- `severity`는 `blocking`(merge 전 필수: correctness·security·data loss·명백한 회귀) / `non_blocking` / `question`.
- 채택 힌트(`must_adopt`/`defer`/`wont_adopt`)는 선택 필드다. 안전경계 발견은 중재 게이트가 `must_adopt`로 고정하므로 힌트로 강등되지 않는다.
- lens는 `fingerprint`·`duplicate_of`를 직접 만들지 않는다 — 중재 게이트가 결정론적으로 부여한다.
- diff가 잘렸거나 필수 컨텍스트를 읽지 못하면 lens는 `context_incomplete`를 보고하고 **추정으로 finding을 만들지 않는다**.

### 워커 절차 (run)

- 워커는 작업의 SPEC 수용기준·변경 diff·기존 리뷰 스레드를 입력으로 모아 4 lens에 전달(각 brief는 자기완결)하고, lens 출력을 하나의 `{findings, verified_criteria, context_incomplete}`로 병합해 하니스에 주입한다. 이후의 합성은 전부 결정적 규칙이다.

### 중재 게이트 (결정적)

- **fingerprint**: 파일 + 리뷰 관점 + 정규화한 제목(대소문자·공백 정규화)으로 결정론적으로 계산하며 **라인 번호와 무관**하다 — 같은 지적은 코드 이동으로 라인이 바뀌어도 같은 fingerprint를 가진다.
- **신뢰도·증거 게이트**: 4증거(변경 위치·실패 경로 본문·파일·라인·실행 가능 제안)를 모두 갖추고 `confidence_score` 80 이상인 finding만 통과. 하나라도 미달이면 출력에서 **제외**한다.
- **중복 제거**: 같은 작업의 이전 리뷰에 이미 게시된 fingerprint와 같으면 출력 findings에서 제외하고 `skipped_duplicates`로 보고한다.
- **스레드 라이프사이클**: 기존 스레드 중 이번 라운드에 다시 제기된 지적은 `unresolved_threads`(동일 지적 유지), 더 이상 제기되지 않는 지적은 `resolved_threads`(해소)로 보고한다.
- **재작업 브리프**: 차단성(blocking) 지적이 하나라도 있으면 `rules/change-adoption.md`의 3분류 — 반드시 반영(`must_adopt`)·후속(`defer`)·반영 불필요(`wont_adopt`) — 로 분류한다. **안전 경계(보안·데이터 손실·계약·범위·권한) 지적은 `must_adopt`로 고정**되어 어떤 힌트로도 강등되지 않는다.
- **수용기준 커버리지**: `acceptance_coverage`(total·verified·unverified)를 산출한다. 미검증 수용기준이 남으면 판정은 approve가 되지 않는다.
- **판정**: 단일 `pipeline_verdict`를 산출한다 — 셋 중 정확히 하나.
  - diff가 잘렸거나 필수 컨텍스트가 불완전하면 `unavailable`(어떤 경우에도 approve하지 않는다).
  - 차단성 지적 또는 미검증 수용기준이 있으면 `request_changes`.
  - 그 외(컨텍스트 온전·차단성 없음·전 수용기준 검증)면 `approve`.
- **안전 기본값**: 외부 입력 인터페이스가 주입되지 않았을 때의 기본 동작은 컨텍스트 불완전으로 처리된다 — 미설정·미입력이 **절대 approve 쪽으로 기울지 않는다**.

### 상태 저장·조회

- `run`마다 작업별 상태에 마지막 판정·리뷰 라운드 수(실행마다 1 증가)·게시된 지적 fingerprint 목록·마지막 출력 전문을 기록한다. 라운드 수는 기록일 뿐, 몇 라운드를 돌릴지·수렴 가드는 호출 레이어가 소유한다.
- `status`는 해당 작업의 마지막 판정·라운드·fingerprint 목록을 출력한다. 리뷰 상태가 없는 작업이면 오류로 종료한다.
- `list`는 리뷰 상태가 있는 작업들을 한 줄씩(작업·판정·라운드) 요약한다. **빈 상태에서도 0 exit**으로 정상 출력한다.

### 오류·차단 시 동작

- 필수 의존 도구(JSON 처리 도구, sha256 해시 유틸) 부재, git 저장소 밖에서 상태 저장소 미지정, 알 수 없는 서브커맨드·인자, 필수 인자(`--task`) 누락은 모두 표준 에러 메시지와 함께 0이 아닌 코드로 중단한다.
- 컨텍스트 불완전(diff 잘림 포함)은 오류가 아니라 `unavailable` 판정으로 표현된다 — 출력 JSON은 정상 산출된다.

## ④ 인터페이스 (호출 형태·입력·출력·산출물)

### 호출 형태

`Skill(skill="review", args="<subcommand> [<args>]")`.

| subcommand | 인자 | 역할 |
|---|---|---|
| `run` | `--task <task-id>` | 한 작업의 변경 리뷰 → 판정·지적·(차단 시)재작업 브리프를 단일 JSON으로 stdout 출력 |
| `status` | `--task <task-id>` | 마지막 리뷰 상태(판정·라운드·fingerprint) 조회 |
| `list` | — | 리뷰 상태가 있는 작업 요약(없어도 0 exit) |
| `fingerprint` | `<file> <perspective> <title>` | 안정 fingerprint 계산(중복 판정 교차 확인용) |
| `selftest` | — | 내장 mock만으로 결정적 판정 규칙을 검증하고 0 exit |

### 입력

- 작업 식별자(task-id).
- **주입 가능 명령 변수**(외부 인터페이스 — 테스트·오케스트레이터가 mock/실제 구현으로 치환): `REVIEW_DIFF_CMD`(diff 컨텍스트: base/head, 잘림 여부, 컨텍스트 완전성, 리뷰 파일 목록) · `REVIEW_SPEC_CMD`(SPEC 수용기준 id 목록) · `REVIEW_LENS_CMD`(병합된 lens 출력) · `REVIEW_THREADS_CMD`(기존 게시 fingerprint, 한 줄에 하나).
- `REVIEW_STATE_DIR`: 상태 저장 루트(기본 `<git-root>/.review`).
- lens 병합 출력은 주입 변수 대신 작업별 상태 영역에 둔 파일로도 공급할 수 있다. 어느 쪽도 없으면 컨텍스트 불완전으로 처리된다.

### 출력·산출물

- `run`의 stdout: 출력 스키마를 따르는 **단일 JSON 한 건**. 주요 필드 — `eligibility`(reviewed/skipped/unavailable + 사유) · `pipeline_verdict`(approve/request_changes/unavailable) · `verdict`(공유 계약 호환 어휘: request_changes는 comment로 매핑) · `confidence` · `reviewed_context`(base/head·잘림 여부·리뷰/스킵 파일) · `automation_safety`(may_approve/may_request_changes + 사유) · `acceptance_coverage`(total/verified/unverified) · `findings[]`(severity·confidence_score·관점·파일·라인·제목·본문·제안·fingerprint) · `rework_brief`(must_adopt/defer/wont_adopt) · `resolved_threads`/`unresolved_threads` · `skipped_duplicates` · `context_requests`.
- 출력 스키마는 저장소가 공유하는 PR 리뷰 계약(4증거·신뢰도≥80·fingerprint·관점 어휘)을 단일 출처로 재사용하고, 파이프라인 전용 필드(`pipeline_verdict`·`acceptance_coverage`·`rework_brief`)만 가산한 것이다 — 계약을 새로 지어내지 않는다.
- 상태 산출물: `REVIEW_STATE_DIR` 아래 작업별 디렉토리(마지막 판정·라운드 수·fingerprint 목록·마지막 출력). 이 밖의 경로는 만들지 않는다.
- 종료 코드: 정상 산출(unavailable 판정 포함)·빈 list는 `0`, 사용법·환경·상태 부재 오류는 0이 아닌 코드.

## ⑤ 비기능 요구사항·제약

- **결정성·검증 가능성**: 판정 합성(게이트·중복 제거·분류·커버리지·판정)은 같은 입력에 같은 출력을 내는 결정적 규칙이어야 하며, 외부 인터페이스를 주입 mock으로 치환해 **실제 PR·브랜치 아티팩트 없이** 검증 가능해야 한다(자체 검증 서브커맨드 + 테스트).
- **안전 편향**: 불확실성은 항상 approve 반대 방향으로 처리한다 — 컨텍스트 불완전·입력 미주입·미검증 수용기준 잔존 시 approve 금지, 안전경계 지적의 채택 강등 금지.
- **독립성**: lens 간 결론 공유 금지(합의 투표 아님). 중재가 독립 발견들을 합성한다.
- **단일 출처 원칙**: 리뷰 9원칙(`rules/review.md`)·채택 분류 프레임(`rules/change-adoption.md`)을 재정의하지 않고 실행자로서 따른다. 적대 렌즈 정의는 spec 스킬의 페르소나 카탈로그를 복제하지 않고 참조한다. 출력 계약은 공유 PR 리뷰 계약을 재사용한다.
- **의존성**: git, 구형 호환 POSIX 셸 환경(bash 3.2 수준, 연관 배열 같은 신형 기능 비의존), JSON 처리 도구, sha256 해시 유틸. LLM lens 리뷰는 로컬 서브에이전트로 수행한다. **forge(`gh` 등) 연동은 본 스킬의 의존성이 아니다.**
- **상태 격리**: 자기 상태 저장소 밖 경로 생성 금지.

## ⑥ 비-목표 (Out of scope)

- 반복 수렴(iterate-until-approved)·재구현 위임·라운드 반복 결정·수렴 가드 — 오케스트레이터의 책임(스킬은 라운드 수를 상태로 기록만 한다).
- forge로의 자동 approve/merge·머지 차단 — 판정은 머신리더블 산출물일 뿐, 머지 게이트 결정은 호출 레이어가 한다.
- 리뷰 원칙·채택 분류 프레임의 정의·재정의 — 프로젝트 규칙이 단일 출처.
- 출력 계약(증거·신뢰도·fingerprint 규약)의 신규 발명 — 공유 계약 재사용.
- 중재 게이트에서의 LLM 호출 — 발견 생산만 LLM, 합성은 결정적.
- 변경의 작성·수정 — 리뷰 대상 코드를 고치지 않는다.

## ⑦ 성공 기준

- 어떤 입력에서도 `run`은 출력 스키마를 따르는 단일 JSON과 셋 중 정확히 하나의 `pipeline_verdict`를 산출하고, 호출 레이어가 그 JSON만으로(텍스트 해석 없이) 머지 게이트를 판단할 수 있다.
- 컨텍스트가 불완전하거나 수용기준이 하나라도 미검증이면 어떤 경로로도 approve가 산출되지 않는다.
- 출력에 남는 모든 finding은 4증거와 신뢰도 80 이상을 갖춘다 — 근거 없는 지적이 게이트를 통과하지 못한다.
- 같은 지적은 라인 번호가 바뀌어도 재게시되지 않고(라인 무관 fingerprint) 중복으로 보고되며, 라운드 간 스레드의 해소/유지가 구분되어 보고된다.
- 안전 경계에 해당하는 차단성 지적은 항상 재작업 브리프의 반드시-반영으로 분류된다(강등 사례 없음).
- 결정적 판정 규칙(차단성→request_changes, 전부 검증·무차단→approve, 컨텍스트 불완전→unavailable, 안전경계 고정)이 실제 PR·브랜치 없이 mock 주입만으로 재현·검증된다.
- 스킬 실행 후 자기 상태 저장소 밖에 새 파일·원격 상태(approve·merge·코멘트)가 생기지 않는다.

# 역PRD — autopilot `spec` 스킬

> **문서 성격**: 현재 구현에서 제품 요구사항을 역추출한 재구현 기준서(역PRD). 구현 방법(HOW)은 싣지 않는다.
>
> **근거 소스 범위**: 이 리포지토리 `plugins/autopilot/skills/spec/`의 `SKILL.md`와 `references/` 하위 모듈 전체.
> **기준 플러그인 버전**: autopilot `0.38.1` (작성 시점 스냅샷 — 이후 스킬 변경 시 본 문서와 드리프트가 생길 수 있다).

## ① 개요·배경·목적

`spec`은 자연어 task 의도를 **명확화 인터뷰**로 탐색해 **자기완결적 SPEC 문서**를 작성하고 구현 스킬(`autopilot:dispatch`)을 추천하는 경량 스킬이다.

배경: autopilot 파이프라인(spec → dispatch → loop → review)은 "의도를 먼저 검증 가능한 완료 조건이 있는 문서로 뜨고, 구현은 그 문서만 보고 자율 수행"하는 모델이다. 이 파이프라인의 첫 단계가 spec이며, 산출 SPEC의 품질이 후속 자율 실행 전체의 품질을 결정한다.

목적(존재 이유):

- 구현 스킬이 **중간 질문 없이** 수행할 수 있을 만큼 자기완결적인 SPEC을 산출한다.
- SPEC에는 의도(검증 가능한 완료 조건)만 싣는다. 검증을 실행하는 진입 명령(테스트·lint·빌드)은 SPEC이 아니라 프로젝트 규칙(`rules/`)이 단일 출처다.
- 책임은 정확히 셋이다: ⑴ 명확화 인터뷰, ⑵ SPEC 문서 작성, ⑶ 구현 스킬 추천.

## ② 사용자·호출 시나리오

| 시나리오 | 호출자 | 흐름 |
|---|---|---|
| 새 SPEC 작성 | 사람(세션 사용자), 보통 `using-autopilot` 라우팅 경유 | 자연어 task 설명을 받아 인터뷰 → SPEC 발행 → 최종 승인 → (옵트인) dispatch 핸드오프 |
| 미해결 마커 해소 | 사람 | 기존 SPEC 경로를 `--resume`으로 받아 `[NEEDS CLARIFICATION]` 마커 섹션만 재인터뷰·갱신 |
| 자율 오케스트레이터 하위 호출 | 상위 자율 오케스트레이터 | 인터뷰·자체 검토·SPEC 산출은 동일하되 사용자 대면 승인·핸드오프 프롬프트를 생략하고, **dispatch를 직접 호출하지 않고 SPEC 경로만 반환**한다 |
| 다중 서브시스템 의도 | 사람 | 범위 분해 게이트가 다중을 감지하면 한 번의 인터뷰로 N개 SPEC을 분해 발행하고 문서 간 의존성 메타데이터를 남긴다 |

## ③ 기능 요구사항 (동작 정의)

### 워크플로 골격

- 항상, 스킬은 7단계 워크플로(컨텍스트 탐색 → 범위 분해 게이트 → 명확화 인터뷰 → 접근법 비교 → SPEC 작성 → 자체 검토 → 최종 승인·추천)를 따르고, 호출 시 단계를 할 일 목록으로 등록해 진행을 가시화해야 한다.
- 항상, 사용자에게 받는 모든 결정·승인은 구조화 질문 도구(`AskUserQuestion`)로 받아야 하며, 자유 텍스트 질문으로 끝맺지 않아야 한다. 한 번에 한 주제, 한 호출의 관련 소문항은 최대 4개로 제한한다.

### 1. 컨텍스트 탐색

- 항상, 인터뷰 진입 전에 대상 프로젝트의 최근 이력·구조·규칙·테스트 컨벤션을 1회 일괄 탐색해 요약해야 한다(읽기 전용).
- 탐색이 부족할 때(적용 룰이 많음, 기존 SPEC 선례 다수, 다중 파일 영향, 자연어 의도만 있음), 시스템은 사실 수집 전용 보조 에이전트에 read-only 탐색을 위임할 수 있어야 한다. 보조 에이전트는 관련 룰·기존 SPEC·코드 영역·컨벤션·권고를 보고만 하며, SPEC 작성·범위 확대/축소·결정·합성은 항상 메인이 한다.

### 2. 범위 분해 게이트

- 인터뷰 전, 시스템은 사용자 의도가 **다중 독립 서브시스템**인지 감지해야 한다. 감지 신호(2개 이상이면 다중 가능성 높음): 서로 다른 명사를 잇는 접속사 다중, 명사 도메인 다양성, 관련 코드의 3개 이상 최상위 디렉터리 분산, 부분별 완료 조건의 상호 독립.
- 다중 감지 시, 시스템은 구조화 질문으로 ⒜ 분해 발행(이번 한 호출에서 N개 SPEC + 의존성 기록) ⒝ 단일 강행(위양성 대응으로 항상 제공, 위험 절에 사유 기록) ⒞ 다른 task로 분리(현재 호출 중단) 중 선택을 받아야 한다.
- 항상, 이 게이트는 **발행 문서 개수만** 결정하며 구현 스킬 추천을 가르지 않는다(추천은 개수와 무관하게 항상 dispatch).
- 분해 발행을 선택하면, 한 번의 명확화 인터뷰로 모든 단위를 수집한 뒤 단위마다 SPEC 문서를 만들고, 각 문서의 frontmatter `depends_on`에 선행 단위 slug 목록을 기록해야 한다. 단일 발행이면 `depends_on` 줄 자체를 제거해야 한다.
- 컨텍스트-윈도우 적합성처럼 런타임 실측이 필요한 분해 기준은 저작 휴리스틱으로만 쓰고 실측은 실행 측(loop/dispatch)에 남긴다.
- `--resume` 호출에서는 이 게이트를 생략한다.

### 3. 명확화 인터뷰

- 항상, 인터뷰는 사용자의 최초 진술을 되짚는 데서 출발해 직전 답에서 다음 질문이 파생되는 **깔때기형 단일 흐름**이어야 한다. 빈칸 채우기식 시작("무엇을 만들고 싶으신가요")과, 고정 카테고리 목록(목적·성공기준·제약·위험)을 사용자에게 나열해 묻는 방식은 금지된다.
- 항상, 목적·성공기준·제약·위험 네 영역은 사용자 대면 질문 슬롯이 아니라 **내부 커버리지 체크리스트**다 — 메인이 속으로 커버리지를 추적하고 빈 영역으로 질문을 파생시킨다.
- 항상, 인터뷰는 네 원칙을 따라야 한다:
  - **집요함** — 공유 이해까지 캐묻되 무한 추궁은 금지. 종결 조건: 목적이 모호성 없이 잡힘 + 미해결 결정 없음, 또는 사용자의 명시적 충분/중단 선언, 또는 마일스톤 규모 판정. 종결 시 남은 미세 항목은 `[NEEDS CLARIFICATION: <구체 질문>]` 마커로 SPEC에 위임한다.
  - **결정 트리** — 한 번에 한 질문, 상위 결정부터 해소하며 선행 답이 후속 질문을 가지치기한다.
  - **추천 답** — 매 질문에 추천 답을 첫 선택지로 제시(레이블에 "(추천)" 표기)하고 관찰된 코드·룰·선례 기반 한 줄 근거를 붙인다. 근거 없는 추천 금지.
  - **코드 우선** — 코드 탐색만으로 답할 수 있는 질문은 사용자에게 묻지 않고 직접 해소하고, 그 사실을 추천 근거로 인용한다. 가치 판단·우선순위·미래 의도가 필요한 결정만 사용자에게 묻는다. 1단계 일괄 탐색과 달리 인터뷰 중에는 떠오른 질문 한정의 표적 탐색만 하며 중복 탐색하지 않는다.
- 영역별 검토는 별도 승인 단계 없이 인터뷰 중 점진적 되짚음으로 흡수한다(섹션별 개별 승인 단계 없음 — 전체 단일 승인은 7단계).
- 구현-검증 관심사(검증 진입 명령·테스트 sweep 화이트리스트·리뷰 트리거)는 인터뷰에서 묻지 않는다 — 그 출처는 프로젝트 규칙(`rules/`)이다.
- 인터뷰가 잠정 종결에 이르면, 시스템은 차원별 **clarity 점수**를 메인 추론만으로(외부 채점기·모델 호출·신규 의존성 없이) 산정해 사용자에게 리드아웃으로 제시해야 한다:
  - 핵심 3차원(목적·제약·성공기준)은 항상, 보조 2차원(범위·위험)은 규모·복잡도에 따라 선택 산정. 차원별 0–5 정수 척도(5 = 구현 스킬이 중간 질문 없이 수행 가능).
  - 목적 차원은 인터뷰 합의 여부만이 아니라 그 목적이 발행 SPEC의 목적 섹션에 **문장으로 보존**되는지를 평가한다.
  - 권장 소프트 임계는 핵심 3차원 모두 4/5 이상. 한 차원이라도 미만이면 추가 명확화 라운드를 구조화 선택지로 권고한다.
  - 점수는 **소프트 권고**다 — SPEC 작성을 차단하지 않고, 사용자가 충분을 선언하면 점수와 무관하게 진행하며 남은 항목은 마커로 남긴다. 점수는 미해결 마커 시스템과 그 자율 실행 차단 동작을 보완할 뿐 대체하지 않는다.
- `--resume` 호출에서는 남은 마커 섹션만 다시 묻는다.

### 4. 접근법 비교

- 비자명한 결정(모호 요구, 둘 이상의 설계 패턴, 외부 의존성 선택)이 있을 때, 시스템은 2–3개 접근법과 trade-off, 추천을 제시해야 한다. 자명하면 생략한다.

### 5. SPEC 문서 작성

- 항상, 발행 SPEC 문서는 표준 골격을 가져야 한다: frontmatter(`scope.include`/`scope.exclude`, 분해 발행 시 `depends_on`, 선택적 완료 조건 언어 모드) + 본문 섹션 "무엇을 만들 것인가" → "목적(왜)" → "완료 조건" → "범위(포함/비-목표)" → "검증" → "제약(있을 때만)" → "위험(있을 때만)".
- 항상, "무엇을 만들 것인가"는 **WHAT/HOW 방어선**을 지킨다 — 무엇을 만들지만 적고 기술 스택·파일 경로·라이브러리·클래스명 같은 HOW는 제약 절로 옮긴다.
- 항상, 목적 섹션은 변경의 목표·동기를 1–3문장으로 담되 완료 조건의 **종속 앵커일 뿐 검증 기준이 아니다** — 목적을 완료 조건에 인코딩하지 않는다. 인터뷰에서 목적이 모호성 없이 잡히지 않았으면 목적 자리에 `[NEEDS CLARIFICATION: 왜 ...]` 마커를 남긴다.
- 항상, 수용 기준의 사용자 노출 라벨은 **"완료 조건"**이며 어려운 영문 약어를 쓰지 않는다. 각 조건은 가능하면 5문장 패턴(항상 / …할 때 / …인 동안 / …이면(오류) / …기능이 켜지면) 중 하나로 쓰고, 다음 작성 규칙을 지킨다: 관찰 가능한 결과와 검증 방법 포함, 조건당 하나의 검증 가능한 요구, 모호어("적절히"·"빠르게")를 수치·상태·출력으로 치환, 독립 테스트 가능, 구현 방법·파일명·클래스명·라이브러리명 배제.
- 완료 조건 언어는 frontmatter 언어 모드(`ko` 기본 / `en` / `hybrid`)를 따르며 사용자에게 다시 묻지 않는다.
- 항상, 검증 섹션은 진입 명령을 싣지 않는다 — "완료 조건이 인수 바의 단일 출처이고 진입 명령은 프로젝트 규칙이 정의한다"는 명시 문구만 둔다.
- 항상, 미해결 항목은 `[NEEDS CLARIFICATION: <구체 질문>]` 마커로 본문에 남긴다.
- 산출 경로: 이미 로드된 프로젝트 지침에 spec 경로 선언이 있으면 그 선언을 따르고, 없으면 기본값 `docs/specs/<YYYY-MM-DD>-<slug>/SPEC.md`를 쓴다(해석 규칙의 단일 출처는 프로젝트의 브랜치·slug 규칙 문서이며 스킬은 이를 중복 정의하지 않는다). 어느 경우에도 각 SPEC은 전용 디렉토리를 갖고 본문은 그 안의 `SPEC.md`에 둔다. `<YYYY-MM-DD>`는 로컬 작성일, `<slug>`는 SPEC 제목에서 파생한다.
- 빈 slug가 나오면, 시스템은 fallback 디렉토리를 만들지 않고 중단하며 제목 수정을 요청해야 한다.
- 해석된 산출 디렉토리가 없으면 생성하며, 기본값이 아닌 선언 경로에 대해서도 생성이 차단되지 않아야 한다. 본문을 디렉토리 없이 베이스 바로 아래 단일 파일로 두지 않는다.

### 6. 자체 검토

- 항상, SPEC 작성 후 사용자 Q&A 없이 1회 자체 검토를 수행해야 한다. 5축: ⑴ placeholder 잔존 없음 ⑵ 섹션 간 모순 없음(목적이 채워져 있고 검증 기준이 아닌 종속 앵커로만 쓰임 — 단, 목적이 실제로 모호해 마커를 남긴 경우는 허용하고 마커를 보존) ⑶ 범위 정합(scope가 필요한 변경을 포함하고 exclude와 충돌하지 않음, 분해 발행이면 `depends_on`이 실제 선행 slug를 가리키고 단일 발행이면 그 줄이 없음) ⑷ 모호성(이중 해석 가능 요구는 구체 질문 마커로) ⑸ 검증 가능성(각 완료 조건이 관찰 가능·독립 테스트 가능·구현 비강제).
- 발견 사항은 인라인 수정하거나 마커로 남기며, 사용자 재질의 라운드를 열지 않는다.
- 규모 임계(초안 100줄 이상 또는 미해결 마커 2개 이상) 충족 시, 시스템은 5축에 더해 세 **적대 렌즈** — contrarian(반대 가정: 암묵 전제가 틀리면 수용 기준이 깨지는 지점), minimalist(최소 해법: 의도를 충족하는 더 작은 변경), constraint-auditor(구속력 있는 제약: 어기면 인수 실패인 제약과 단순 선호·관습의 구별) — 를 가산 적용해야 한다. 임계 미만이면 발동하지 않는다(비용 통제).
- 적대 렌즈는 렌즈 태그별 **발견만 보고**하고 단일 패스로 종료하며, SPEC 편집·마커 삽입은 항상 메인이 한다. 렌즈는 5축을 약화·우회하지 않고 가산한다. 렌즈 정의는 단일 카탈로그가 출처이고 다른 스킬은 복제 없이 참조한다(정의 표류 방지).
- 임계 충족 시 자체 검토를 독립 보조 검토자(5축+적대 렌즈)에 위임할 수 있으나, 보조 검토자도 발견만 보고하고(심각도 Critical/Important/Minor 분류) 수정·마커 삽입은 메인이 한다.

### 7. 최종 승인 + 구현 스킬 추천 (옵트인 핸드오프)

- 항상, 완성된 SPEC **전체를 마지막에 한 번** 제시하고 구조화 질문으로 단일 승인을 받아야 한다(섹션별 개별 승인 단계는 없다).
- 항상, 발행 문서 개수와 무관하게 구현 스킬로 **`autopilot:dispatch`를 추천**한다(단일이면 N=1, 다중이면 SPEC set).
- 승인 후 옵트인 자동 핸드오프 판정:
  - 미해결 마커가 없고 사용자가 최종 승인했으면, "구현까지 자동으로 진행할까요?"를 구조화 질문으로 묻고, **명시 동의 시에만** SPEC 경로(들)로 dispatch를 호출한다. 동의하지 않으면 후속 스킬을 호출하지 않고 SPEC 경로와 다음 단계 안내만 남기고 종료한다.
  - 미해결 마커가 남아 있으면 자동 진행을 제안하지 않는다 — 마커가 자율 실행을 차단한다는 사실과 `--resume` 해결 방법을 안내하고 종료한다.
- **자율 오케스트레이터 호출 맥락**에서는 사용자 대면 프롬프트(최종 승인·핸드오프) 둘 다 생략하되, spec은 dispatch를 직접 호출하지 않고 미해결 마커가 없을 때 SPEC 경로(들)만 오케스트레이터에 넘기고 종료한다 — dispatch 기동은 오케스트레이터가 단독 수행한다(**같은 SPEC에 대한 이중 기동 방지**). 별도 신호 인자는 두지 않으며 호출 맥락만으로 분기한다. 마커가 남아 있으면 자율 맥락이어도 경로를 넘기지 않고 차단 사실과 `--resume`을 안내하고 종료한다(품질 게이트 보존). 사람 단독 호출이면 두 프롬프트를 그대로 띄운다(문서-only 검토 경로 보존).

### --resume 동작

- 대상 SPEC 경로를 인자로 받아 **그 자리에서** 갱신한다. 기본값 경로든 외부 선언 경로든, 구 형식(`docs/specs/<날짜>-<slug>.md`)이든 신 형식(per-spec 디렉토리)이든 모두 수용하며 특정 베이스·네이밍을 가정해 거부하지 않는다. 구 형식 문서를 신 레이아웃으로 옮기지 않는다(이전은 마이그레이션의 책임).
- 문서가 없으면 중단하고, `[NEEDS CLARIFICATION` 마커가 없으면 할 일이 없으므로 종료한다.
- 분해 게이트는 생략, 인터뷰는 남은 마커 섹션만, 작성·자체 검토는 마커 섹션만 갱신·재작성하고 최종 승인 단계로 종결한다. 새 외부 상태는 만들지 않는다.

## ④ 인터페이스 (호출 형태·입력·출력·산출물)

### 호출 형태

| 용도 | 호출 |
|---|---|
| 새 SPEC | `Skill(skill="spec", args="<자연어 task 설명>")` |
| 마커 해소 | `Skill(skill="spec", args="--resume <spec-path>")` |

### 입력

- 자연어 task 설명(새 SPEC) 또는 기존 SPEC 문서 경로(`--resume`).
- 대상 프로젝트의 디스크 상태(코드·`rules/`·기존 SPEC·git 이력) — 읽기 전용 컨텍스트.
- 인터뷰 중 사용자의 구조화 답변.

### 출력·산출물

- **SPEC 문서(들)**: 전용 디렉토리 + `SPEC.md` 레이아웃(기본 `docs/specs/<YYYY-MM-DD>-<slug>/SPEC.md`, 프로젝트 선언이 있으면 그 경로). 분해 발행 시 N개 문서 + frontmatter `depends_on` 의존성 메타데이터.
- 구현 스킬 추천(항상 dispatch)과 다음 단계 안내, 또는 (옵트인 충족 시) dispatch 호출.
- 자율 오케스트레이터 맥락에서는 산출 SPEC 경로(들)의 반환.
- **산출물은 SPEC 문서뿐이다** — task·이슈·브랜치·원격 등 외부 상태를 일절 만들지 않는다.

## ⑤ 비기능 요구사항·제약

- **경량성**: 새 런타임·엔진·외부 의존성을 도입하지 않는다. clarity 점수도 메인 추론만으로 산정한다(무인프라).
- **읽기 전용 탐색**: 컨텍스트 탐색은 프로젝트를 변경하지 않는 조회성 작업으로 한정되며, 스킬의 도구 권한도 그 범위(읽기·조회·SPEC 디렉토리 생성·문서 쓰기)로 제한된다.
- **비용 통제**: 적대 렌즈·보조 검토자는 규모 임계 충족 시에만 발동한다.
- **단일 출처 원칙**: 인터뷰 방법론, 렌즈 정의, clarity 점수 정의, 산출 경로 해석 규칙은 각각 단일 출처를 두고 복제하지 않는다(정의 표류 방지).
- **상호작용 규율**: 모든 사용자 결정은 구조화 질문으로, 한 번에 한 주제, 소문항 최대 4개, 추천 답 첫 선택지.
- **위임 경계**: 보조 에이전트는 사실 수집·독립 검토만 하며 결정·합성·SPEC 편집·마커 삽입·중첩 dispatch는 금지된다. 위임 brief는 자기완결이어야 한다(보조 에이전트는 메인 컨텍스트를 보지 못한다).

## ⑥ 비-목표 (Out of scope)

- 구현·테스트 실행·머지 — 구현 스킬(dispatch/loop)과 리뷰 스킬의 책임.
- 외부 상태 생성 — task·이슈·브랜치·원격 동기화는 호출자와 구현 스킬의 책임이며 절차의 단일 출처는 `rules/`다.
- 검증 진입 명령 정의 — `rules/`가 단일 출처. SPEC은 의도(완료 조건)만 싣는다.
- 후속 스킬 자동 호출 — 유일 예외는 사람 단독 호출 경로의 옵트인 핸드오프(미해결 마커 없음 + 최종 단일 승인 + 명시 동의 모두 충족)뿐이다. 자율 오케스트레이터 맥락에서는 경로 반환만 한다.
- 구 형식 SPEC의 신 레이아웃 이전(마이그레이션).
- 산출 경로 해석 규칙의 자체 정의(프로젝트 규칙 참조).

## ⑦ 성공 기준

- 산출 SPEC만 읽고 구현 스킬이 **중간 질문 없이** 구현을 수행할 수 있다(자기완결성).
- 발행 문서가 표준 골격(WHAT → 목적 → 완료 조건 → 범위 → 검증 → 제약 → 위험 + scope frontmatter)을 갖추고, 각 완료 조건이 관찰 가능·독립 테스트 가능하며 HOW를 강제하지 않는다.
- 미해결 사항이 전부 `[NEEDS CLARIFICATION]` 마커로 명시화되어 있고, 마커가 있는 SPEC은 자율 실행이 차단되며 `--resume`으로 해소 가능하다.
- 다중 서브시스템 의도가 한 번의 인터뷰로 N개 SPEC + 의존성 메타데이터로 분해 발행된다.
- 스킬 실행 전후로 SPEC 문서 외의 외부 상태 변화가 없다.
- 사람 경로에서는 명시 동의 없이, 자율 경로에서는 어떤 경우에도 spec이 dispatch를 기동하지 않는다(이중 기동 0건).
